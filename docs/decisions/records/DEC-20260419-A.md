## Decision

F-0-014 and F-0-018 closed out across Phases E3-E5 (2026-04-19). The project
now follows a single structured-logging standard across all API code paths.
The standard is documented here so new code matches it without re-litigating
choices:

1. **Transport.** Pino. Stdout JSON in dev, `@logtail/pino` to Better Stack in
   prod when `BETTER_STACK_SOURCE_TOKEN` is set. Exported as `log` from
   `apps/api/src/lib/log.ts`. No `console.*` calls in `apps/api/src/`
   (enforced by the `scripts/check-no-new-console.mjs` CI check).
2. **Helpers from `log.ts`.** `logError(label, err, ctx?)` for errors with
   Error objects, `logWarn(label, msg, ctx?)` for non-error warnings. Direct
   `log.info({ label, ...fields }, 'message')` for info/debug.
3. **Request context attached by middleware** at
   `apps/api/src/middleware/request-context.ts`: `request_id`, `method`,
   `path` at request start; `user_id` added by auth middleware; `status_code`
   and `duration_ms` on request-complete. Handlers access it via
   `c.get('log')`; never re-attach these fields manually.
4. **Labels are kebab-case tags** describing the emitter:
   `[topup-attempt]`, `[capability-onboarding]`, `[kyb-essentials-se]`. Label
   taxonomy is NOT normalised (intentionally, per the E4 decision). If
   inconsistency becomes a problem post-E5, a normalisation pass is
   structural work for later.
5. **Named structured fields only.** No template interpolation (no
   `log.info(\`user ${id} did ${x}\`)`). Always
   `log.info({ user_id, action }, 'did')`.
6. **PII scrub preserved (F-0-013).** Email/raw IP/token content is never
   logged. If a field is PII, log the ID instead and let operators join via
   request context.
7. **Jobs in `apps/api/src/jobs/`** generate a `job_run_id` at the cron entry
   point: `const jobLog = log.child({ job: 'slug', job_run_id: runId })`.
   Helpers called by the job use module-level `log` with their own context;
   over-threading correlation IDs into helper signatures is an anti-pattern.
8. **`hono/logger` removed (F-0-018).** Do not re-introduce it.

Exceptions live in `console-allowlist.json`: at adoption time, `app.ts` (4),
`index.ts` (10), `diagnostics/self-heal-check.ts` (2), and 19 one-off `db/`
scripts deferred to E2.1. Any new file added to the allowlist requires a
justification comment.

This supersedes ad-hoc `console.*` patterns. `DEC-20260319` (scoring
integrity) and `DEC-20260320-B` (capability onboarding) are orthogonal and
unchanged.

## Consequences

Status verified on 2026-09-04, against `main`:

- `apps/api/src/lib/log.ts` and `apps/api/src/middleware/request-context.ts`
  exist and match the transport, helpers, and request-context fields
  described in rules 1-3.
- The CI console-call guard moved: it now lives at
  `apps/api/scripts/check-no-new-console.mjs` (not `scripts/` at repo root,
  as an earlier draft of this citation would have named it), reading
  `apps/api/scripts/console-allowlist.json`.
- The allowlist has grown well beyond the four files named at adoption
  (`app.ts`, `index.ts`, `self-heal-check.ts`, 19 db/ scripts): it now lists
  24 files, including `index.ts` at a reduced count of 8 (was 10) and several
  `src/scripts/`, `src/db/`, and `test-support/` files not named in the
  original Decision text. This is drift in the allowlist's contents, not a
  contradiction of the standard — the check's stated purpose is exactly to
  let one file grow or shrink over time as it migrates, per its own header
  comment ("a new file added to the allowlist requires a justification
  comment").
- `hono/logger` is not reintroduced; `apps/api/src/app.ts` and
  `apps/api/src/middleware/request-context.ts` both carry F-0-018
  cross-references confirming the replacement is still in place.
- The `job_run_id` pattern (rule 7) is in active use, e.g.
  `apps/api/src/jobs/activation-drip.ts` and
  `apps/api/src/jobs/daily-digest.ts`.

## Reversal conditions

Reconsider the standard if a future logging-sink migration or a structural
label-taxonomy normalisation pass (flagged as future work in rule 4) changes
the transport, helper surface, or field-naming rules. Represent a change
through a new decision and an explicit `supersedes` or `amends` relationship
rather than editing this protected record in place.
