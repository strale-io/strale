## Decision

**Option B, selected.** `processing_location` and `data_jurisdiction` are
Strale-schema inventions, declared explicitly rather than borrowed from
regulatory text:

- `processing_location` keeps its current F-AUDIT-02 Contain behaviour
  (`DEC-20260425-B`): a single string, the region of the API replica that
  handled the request, read from `RAILWAY_REPLICA_REGION` via the unified
  helper (`apps/api/src/lib/processing-location.ts`, commit `d165ae2`).
- `data_jurisdiction` becomes a comma-joined set of ISO 3166-1 alpha-2 codes
  for every region where compute touched the data during the transaction,
  sourced from a manifest-declared field per capability, replacing the
  current `getProcessingJurisdictions` heuristic based on `capabilityType`
  and `transparencyTag`.

Both fields are documented in methodology surfaces as Strale-schema
concepts, not regulatory field names; the operational definitions are
explicit. The hardcoded `"EU"` in `buildFullAudit` and `buildFreeTierAudit`
is removed; all three audit builders use the same computed value from the
manifest-declared source.

**Scope of the Option B implementation (five steps):**

1. Remove the hardcoded `"EU"` in `buildFullAudit` and
   `buildFreeTierAudit`; replace with the computed value from the
   manifest-declared source.
2. Add a manifest field declaring the jurisdictions a capability's
   processing touches (the current heuristic's output as the default,
   overridable).
3. Update the 20-40 capabilities where the heuristic produces wrong values
   (e.g. algorithmic capabilities calling US-based APIs, `ai_assisted`
   capabilities using EU-only LLM endpoints).
4. Deprecate `getProcessingJurisdictions`' heuristic path, keeping it only
   as a fallback seeder for new capabilities.
5. Document both fields in a methodology page visible to customers.

Estimated CC effort: 2-4 hours across the onboarding pipeline, manifest
schema, capability defaults, and documentation.

**The five options considered:**

- **(A) Drop the fields**, replace with GDPR-native recipient/transfer
  vocabulary. Rejected as premature: requires subprocessor data Strale does
  not currently track (Anthropic DPF certification status, per-stage
  recipient identity, Chapter V safeguard mechanism per recipient). Remains
  a valid upgrade target when Strale moves toward compliance as a wedge;
  Option B's schema is compatible with an upgrade to A.
- **(B) Redefine both fields as narrow, honest strings with
  manifest-declared jurisdictions.** Selected.
- **(C) Rename to `provider_location` + `data_source_jurisdictions`, anchor
  to EU AI Act Art. 13(3)(a)/(b).** Rejected over B: C's regulatory-hook
  advantage is marginal, since Art. 13 is an instructions-for-use
  obligation, not a per-transaction audit-field obligation, so C's
  field-name improvement is cosmetic rather than substantive. C also
  required a full 290-capability manifest backfill for a renamed field
  delivering near-identical honesty, deprecated the F-AUDIT-02 Contain fix
  three days after shipping, and introduced a breaking schema change whose
  cost is low today (zero external consumers) but creates a
  historical-vs-new discontinuity in stored records.
- **(D) Layered per-stage jurisdiction_trace array.** Rejected as premature
  for the same subprocessor-data reason as A. Remains a valid upgrade
  target; Option B's schema is compatible with an upgrade to D.
- **(E) Status quo plus disclaimer.** Rejected because it papers over the
  F-AUDIT-01 divergence (see Context) without addressing it.

Option B was chosen over C because it delivers the same honesty with a
smaller manifest migration (only the roughly 20-40 capabilities where the
current heuristic is wrong, not all 290) and preserves the runtime-region
signal just shipped in F-AUDIT-02 Contain.

**Confidence: medium**, not high, because three real unknowns remain: the
regulatory-anchor question is unresolved (`DEC-20260425-F`, named as
pending/deferred at adoption time; Strale's provider/controller/processor
classification would refine whether the schema should graduate toward
Option A or D, and when); the manifest-declared approach introduces a new
legally-load-bearing artefact (if a manifest value is wrong, the audit
record is wrong); and the 20-40 heuristic-override estimate is a rough
count to be refined during R1 audit. Medium, not low, because the decision
is reversible: moving from B to D later is additive (add a per-stage
trace), not destructive, and the field-name continuity preserves existing
consumers.

## Context

Session F audit of Strale's audit infrastructure surfaced that
`processing_location` and `data_jurisdiction` fields in audit records are
hardcoded or inferred in ways that diverge from stored column values and
from each other across the three audit builders (`buildFullAudit`,
`buildFailureAudit`, `buildFreeTierAudit`). F-AUDIT-02's Contain phase
shipped 2026-04-24 to stop the factual falsehood of hardcoded
`"eu-west (Railway EU)"` when the API runs on Railway US East
(`DEC-20260425-B`). F-AUDIT-01 remained open at adoption time:
`data_jurisdiction` hardcoded `"EU"` in two builders while the failure
builder computed it.

Compliance research was commissioned to ground this decision
(`COMPLIANCE_RESEARCH_audit_fields.md`, 2026-04-21, 5,780 words, primary
sources EUR-Lex, NIST AIRC, Colorado Legislature, and the ISO catalogue).
Its foundational finding: neither `processing_location` nor
`data_jurisdiction` maps to any regulatory concept as a per-transaction
audit field. GDPR uses "recipient" (Art. 4(9)) and "third country transfer
identification including safeguards" (Art. 30(1)(d)/(e)). EU AI Act Art. 12
enumerates per-transaction fields only for Annex III point 1(a) biometric
identification and names neither location nor jurisdiction for general
high-risk systems. The Colorado AI Act operates at the program level, not
per-transaction. The two fields are Strale-schema inventions whose meaning
must be declared, not inherited from regulatory text.

Compliance positioning was also explicitly deprioritised in this strategic
context at adoption time: compliance is acknowledged as not Strale's
current wedge but is expected to become relevant when Strale moves
up-market toward liability-bearing buyers; marketing language was being
separately aligned to reflect actual confidence level.

The historical Notion scope field on this row was `global` in the
workspace's old vocabulary. It is recorded here as `scope: technical` under
this repository's decision-record vocabulary: this decision defines the
data-contract semantics of two audit-record fields, not a product or global
strategy decision.

Source: https://claude.ai/. Confidence: medium.

## Rationale

The rationale is the option analysis stated in the Decision section above:
Option B was chosen because it resolves the F-AUDIT-01 divergence with
honest, narrow, declared semantics, at a manifest-migration cost an order
of magnitude smaller than Option C, while preserving compatibility with a
future upgrade to Option A or D once subprocessor data becomes available.

## Consequences

Status verified on 2026-09-04, against `main`:

- **`processing_location`'s half of Option B is implemented and unchanged.**
  `apps/api/src/lib/processing-location.ts`'s `getProcessingLocation()`
  still reads `RAILWAY_REPLICA_REGION` (falling back to
  `STRALE_PROCESSING_REGION`, then `"unknown"`), exactly as this row
  affirms ("processing_location keeps its current F-AUDIT-02 Contain
  behaviour... read from RAILWAY_REPLICA_REGION via the unified helper").
  `config/env-manifest.yaml` documents `RAILWAY_REPLICA_REGION` as
  `required_in: [production, test]`, `set_in: [railway]`.
- **`data_jurisdiction`'s half of Option B, the manifest-declared-field
  replacement, was not implemented.** `getProcessingJurisdictions()` in
  `apps/api/src/lib/provenance-builder.ts` still composes
  `data_jurisdiction` from the `capabilityType`/`transparencyTag` heuristic
  this row's Decision explicitly says Option B replaces ("sourced from a
  manifest-declared field per capability, replacing the current
  getProcessingJurisdictions heuristic based on capabilityType and
  transparencyTag"). The function's own in-code comment confirms this
  directly: step 2, "'US' if the call invokes a US-hosted model provider,"
  is present; the "NOT YET captured (chunk 1.5 follow-up)" comment
  immediately below names exactly the gap this row's Decision closes on
  paper: "Per-capability vendor-side jurisdictions, e.g. Dilisense in
  Frankfurt (DE/EU), Browserless region, etc. These should be
  manifest-declared and merged in here." No `manifests/*.yaml` file
  declares a processing-jurisdiction field consumed by
  `getProcessingJurisdictions()`; a repository-wide search of `manifests/`
  for `jurisdiction` finds only unrelated output-field names (e.g.
  `jurisdiction_risk` on `aml-risk-score.yaml`, and per-country
  `jurisdiction:` fixture fields on company-data manifests), none of them
  wired into the audit-record composition path. Scope steps 1, 3, 4, and 5
  of the Decision (removing the hardcoded `"EU"`; updating the 20-40
  wrong-heuristic capabilities; deprecating the heuristic to a fallback
  seeder; and publishing a methodology page) are correspondingly unverified
  as complete on `main` today, because the manifest field they depend on
  does not exist. This is the class of drift the row's own medium
  confidence anticipated, not a surprise: the R1 remediation this row
  scoped may not have shipped as scoped, or may have shipped differently.
- **The actual `data_jurisdiction` value emitted today** is the deduped,
  ordered output of `getProcessingJurisdictions(capabilityType,
  transparencyTag)`: Strale's own jurisdiction (from
  `getStraleJurisdiction()`, itself derived from
  `RAILWAY_REPLICA_REGION`; today `"US"` on Railway `us-east-4`), plus
  `"US"` when the capability is `ai_assisted` or its `transparencyTag` is
  `ai_generated` or `mixed` (an Anthropic-hosted-model signal). The
  function's own docstring still calls this composition "NOT YET" complete
  relative to per-capability vendor jurisdictions such as Dilisense in
  Frankfurt. The hardcoded `"EU"` this row's Context names as the F-AUDIT-01
  bug is confirmed removed from the composition path (there is no literal
  `"EU"` fallback in `getProcessingJurisdictions`), so the specific factual
  falsehood F-AUDIT-01 named is fixed; the manifest-declared upgrade this
  row specified as the mechanism for fixing it is not the one that shipped.
- `apps/api/src/lib/platform-facts.ts` exposes `processing_region` (from
  `getProcessingLocation()`) and `processing_jurisdiction` (from
  `getStraleJurisdiction()`, a single coarse jurisdiction, not the
  per-transaction `data_jurisdiction` set this row defines) via
  `GET /v1/platform/facts`. This is a platform-level fact surface, distinct
  from the per-transaction `data_jurisdiction` field this row's Decision
  scopes; the two are related but not the same value.
- **Readiness and retention did not change the meaning of these fields.**
  Neither `DEC-20260812-A` (the readiness program and quality floor) nor
  `DEC-20260815-A` (the operating charter, including the 90-day content
  redaction rule) mentions `processing_location`, `data_jurisdiction`, or
  `processing_jurisdiction` in their formal records on `main`; both
  postdate this row and neither is evidenced to have touched the semantics
  it defines.
- The `DEC-20260425-F` regulatory-anchor decision this row names as
  pending/deferred at adoption time has no formal record on `main` and is
  not in `docs/decisions/id-collisions.yaml`; it is mentioned here in
  prose only, per this batch's relation-edge scope, and its resolution
  status is unverified.

## Reversal conditions

Reconsider this decision if the manifest-declared jurisdiction field Option
B specifies (Consequences: not yet implemented) ships and replaces the
`capabilityType`/`transparencyTag` heuristic, if `DEC-20260425-F` resolves
the regulatory-anchor question and points toward Option A or D, or if
Strale's provider/controller/processor classification is established in a
way that changes which option is compatible with it. Represent such a
change through a new decision and an explicit `supersedes` or `amends`
relationship rather than editing this protected record in place.
