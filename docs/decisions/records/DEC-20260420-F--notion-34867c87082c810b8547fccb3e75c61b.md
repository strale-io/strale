## Decision

`GET /v1/audit/:id?token=` requires an `expires_at` query param (default
90-day TTL; legacy pre-deploy tokens accepted until a 180-day-out sunset,
2026-10-17). `verifyAuditToken` tries the primary `AUDIT_HMAC_SECRET`
first, falling back to `AUDIT_HMAC_SECRET_PREVIOUS` during rotation grace.
An expired token returns `410 Gone` (`token_expired`), distinct from `401`
(HMAC mismatch). A new `POST /v1/transactions/:id/audit-token` endpoint
lets owners re-issue tokens on demand (1-365 day TTL, rate-limited 5/sec
per key, ownership-checked with a 404 on any mismatch). Re-issue does not
invalidate prior tokens (the scheme is stateless).

## Context

The row's own Rationale states the basis: "F-A-006/007.a audit surfaced 9
open questions; all 9 decided and shipped as F-A-006/007.b across 2
commits." Nine open questions were decided, among them: a 90-day default
expiry ("matches compliance-archive norms... and the existing retention
grace period"); the token shape as separate `token=`/`expires_at=` query
params rather than a self-contained dot-separated triple ("cleaner
parsing... trivial backwards-compat distinction"); `410 Gone` for expired
tokens ("signals to clients that re-issue is the right next action, not
retry-with-new-credentials"); a 180-day backwards-compat grace window
("Option B") over a hard break or a permanent dual path; a 365-day cap on
re-issued tokens; throwing at module load on a too-short
`AUDIT_HMAC_SECRET_PREVIOUS` ("Silent-failure on key validation is the
worst outcome for a rotation mechanism"); and accepting the minor timing
difference between primary- and fallback-key verification as having "no
practical attack surface." The row also records an unplanned hygiene
improvement: `apps/api/src/test-env-setup.ts`, added because the
pre-existing audit-token test suite depended on fragile file-ordering
assumptions for env-var loading.

## Rationale

The rationale, as the row states it: nine narrow, individually-argued
design choices close a compliance-critical gap (audit URLs that never
expired and had no rotation path) at a bounded operational cost (a 180-day
migration window for anyone who had embedded a pre-deploy audit URL in
their own records).

## Consequences

Status verified on 2026-09-05, against `main`.

**The lifecycle shipped essentially as designed and is still the live
mechanism.** `apps/api/src/lib/audit-token.ts` carries "F-A-007: optional
rotation fallback," "F-A-006: default token TTL. 90 days...," and "F-A-006
+ F-A-007: verify with expiry check and two-key ring fallback" at the
functions this row specifies. `apps/api/src/routes/audit.ts` carries "F-A-006:
expires_at is the new-format discriminator. Absent = legacy token
(pre-F-A-006 deploy), accepted during sunset window" and returns the
message "This audit URL was issued under a pre-F-A-006 format that has been
sunset. Re-issue via POST /v1/transactions/:id/audit-token" once the
sunset window closes, matching this row's 180-day grace design exactly.

**The re-issue endpoint's ownership and rate-limit design is unchanged**;
this record did not find a later decision or code change narrowing or
widening the 5/sec rate limit or the 1-365 day re-issue bound this row set.
