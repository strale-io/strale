## Decision

Store structured Provider-Coverage reference data in repository YAML rather
than maintaining a writable Notion mirror. The canonical key is
`(capability_slug, country, evidence_type)`, because one capability may return
multiple evidence types for the same country.

The repo owns the structured routing fields, including capability, country,
evidence type, provider, lifecycle status, sourcing pattern, manifest price,
evidence grade, tier coverage, verification date, product references, and
vendor-roster linkage. Provider terms, doctrine references, and notes travel
with each row as long-form YAML fields. Schema validation, filename/content
alignment, and generated-summary checks protect the surface.

The previous Notion matrix is historical migration evidence, not a second
writable authority. Prose, decisions, Journal entries, and other hand-curated
Notion content were outside this decision's structured-reference-data scope.

## Context

A reference-data cleanup made roughly fifty-five Notion writes. A fresh-context
audit then found twenty-two price mismatches, eight provider-doctrine
mismatches, one code/Notion slug mismatch, and stale live statuses on deprecated
rows. Manifests already defined the actual product while Notion was a mutable
mirror without programmatic round-trip verification.

The migration created `apps/api/coverage-matrix/`, one YAML file per composite
key, a schema, validation and summary tooling, CI checks, and an immutable
snapshot of the migration input. The former Notion matrix was archived.

## Rationale

Code-bound structured data benefits from typed schemas, reviewable diffs,
deterministic generation, and CI enforcement. Mirroring it manually into a
second store adds silent translation and partial-write failure modes without a
meaningful browsing benefit. Keeping historical source identities in the
migration snapshot preserves provenance without making the archive canonical.

## Consequences

Changes to this structured matrix occur through repository files and their
validation pipeline. Generated summaries are projections and must remain
reproducible; they are not independent sources of truth.

The 2026 source also instructed that the archived Notion database be trashed
after thirty days. That destructive cleanup was not carried out and is not
authorized by this candidate. Current workflow invariants prohibit deleting
Notion content, and the repo-native M2 plan preserves the historical workspace
as read-only evidence. This record retains the historical instruction as an
explicit migration conflict rather than silently dropping it.

The later repo-native operating-model migration may narrow Notion's role beyond
the prose/reference-data split described in 2026. That broader cutover remains
inactive and does not weaken the core rule that structured code-bound reference
data has one repository authority.

## Reversal conditions

Reconsider the storage choice if the founder's usage shifts materially toward
visual matrix browsing, or a typed programmatic synchronization path proves
reliable round-trip enforcement across repeated sessions. Any replacement must
retain schema validation, auditable diffs, provenance, and a single canonical
write surface. Represent a change through a new decision rather than editing
this protected record in place.
