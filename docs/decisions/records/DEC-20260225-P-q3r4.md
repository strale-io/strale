## Decision

Crypto: design for it, don't build it yet. Keypair identity from day one.
No blockchain, tokens, or on-chain settlement in the MVP.

## Context

The row's stated basis, from the row's own Rationale (quoted): "Crypto
solves real problems for Strale (portable reputation, trustless escrow,
tamper-proof transaction records) but not the problems we have NOW
(developer adoption, first transactions, proof of concept). Adding
wallets, gas fees, or tokens kills the '20 lines of code' promise and
loses 90% of developer audience. Instead: (1) agent identity as keypairs
from day one — just good security, zero UX friction, SDK handles it, (2)
transaction records as signed structured objects that COULD be anchored
on-chain later, (3) escrow abstracted behind interface (Stripe today,
smart contract later), (4) periodic Merkle root anchoring when reputation
data carries real economic weight, (5) full on-chain identity only when
cross-platform reputation sharing requires it."

The historical Notion scope field on this row was `global` in the
workspace's old vocabulary. It is recorded here as `scope: technical`:
this is a concrete identity and settlement architecture choice.

## Rationale

The rationale, as the row states it, is the five-part design quoted above
in full: keypair-based agent identity from day one at zero UX friction
(SDK-handled); signed structured transaction records that could later be
anchored on-chain; escrow behind an interface, Stripe today and a smart
contract later; periodic Merkle root anchoring once reputation data
carries real economic weight; and full on-chain identity deferred until
cross-platform reputation sharing actually requires it.

## Consequences

Status verified on 2026-09-04, against `main`.

**The specific keypair-based agent identity this row specifies was never
built; customer identity today is API keys, not keypairs.** A grep of
`apps/api/src/` for `keypair`, `ed25519`, and `secp256k1`
(case-insensitive) found matches only in unrelated code: crypto address
*validators* (`solana-address-validate.ts` checking address format, not
issuing identity), and `production-authority.ts` /
`production-authority.test.ts`, which use an ed25519 keypair exclusively
for founder-grant authorization signatures (`DEC-20260822-B`), not for
agent or customer identity. `apps/api/src/lib/auth.ts` confirms customer
identity is a random-hex API key (`sk_live_` + 32 hex chars, hashed with a
`key_prefix` for lookup, per CLAUDE.md's DEC-20), not a keypair the agent
holds and signs with.

**The on-chain settlement piece this row explicitly deferred did ship,
eventually, as the x402 rail, on Base mainnet rather than as an
abstracted-later "smart contract."** CLAUDE.md's "x402 Payment Gateway
(March 2026)" paragraph and `apps/api/src/lib/x402-gateway.ts`
(`USDC_CONTRACTS`, "Base mainnet" comment, `NETWORK` config) show USDC
payments on Base mainnet went live roughly one month after this row,
which is faster than the row's own "when providers want instant
settlement (month 3-6)" framing recorded on the sibling row
`DEC-20260225-P-s5t6`; x402 authenticates by payment itself rather than by
an agent keypair, so it does not implement this row's keypair-identity
design even though it does implement on-chain settlement.

**No Merkle-root anchoring of transaction or reputation records was found
on `main`.** This row's items (2) transaction records anchorable
on-chain and (4) periodic Merkle root anchoring were not found
implemented; `DEC-20260428-B`'s engineering bar for data services (a
different, later record) requires "Merkle-rooted ingest" for
regulatory-grade data services, which is a dataset-integrity mechanism,
not the transaction/reputation anchoring this row describes.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null in
the source). A future decision to introduce agent-held keypair identity,
distinct from the founder-grant ed25519 mechanism that exists today, would
need to specify how it interacts with the existing API-key auth model
(`apps/api/src/lib/auth.ts`) and the x402 payment-as-auth rail, and would
supersede this row's design rather than amend it in place.
