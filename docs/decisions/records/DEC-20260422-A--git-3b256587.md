## Decision

**Mandatory** for any session that touches a PR on a repo outside `strale-io/*`
or that publishes or modifies a `*-strale` package.

**Trigger:** the session prompt mentions a PR on a framework repo (Pipedream,
LangFlow, Flowise, pydantic-ai, langchain, crewAI, agno, composio,
semantic-kernel, awesome-list, etc.), or modifies files under
`packages/*-strale/`, or edits PyPI/npm publication metadata.

**Required steps (non-negotiable):**

1. **Verify every imported symbol before touching a distribution PR.** Before
   editing the PR body, inline comments, code examples, or any
   description-style text on a repo outside `strale-io/*`, fetch the
   referenced Strale package's `__init__.py` / entry point via
   `gh api repos/strale-io/strale/contents/packages/<pkg>/...` and grep for
   every symbol the PR imports. If any symbol is not in `__all__` or not
   exported, **STOP** and flag for Petter. Do not trim prose, do not fix bot
   findings, do not rebase, do not reply — nothing — while the PR contains a
   fabricated import.
2. **Run the distribution PR pre-flight checklist**
   (`docs/governance/protocols/DISTRIBUTION_PR_PREFLIGHT.md`). The four
   verifications — imports resolve against the currently published package,
   the package cited is on the approved list, the description matches what
   the code does, and the tone matches neighboring content — are the
   standard. All four must pass before the session opens or edits a
   distribution PR.
3. **Run the framework-package integrity check locally before shipping a new
   or modified `*-strale` package:**
   `node apps/api/scripts/check-framework-packages.mjs`. If the check fails,
   the package does not match its name. Either make the package live up to
   the name, rename it, or deprecate it — do not publish.
4. **Never batch-create framework packages.** One framework package per PR,
   each including (a) real framework-interface code importing from the
   framework, (b) at least one test exercising the framework's own
   primitives, (c) README content that only references what is in the
   module.
5. **Polishing is not a substitute for verification.** A cleaner-looking PR
   containing a fabricated import is worse than the original. If a bot
   finding points at prose but the code example has an import problem
   underneath, fix the import first and the prose second, or stop and flag.
6. **Run the production contract smoke test after every publish.** Install
   the published artefact the way a stranger would (`npx -y <pkg>@<version>`),
   run it against production, and record the observed startup values, not
   "looks fine." Look specifically for errors the program logs and then
   continues from: a caught, logged, non-fatal degradation is what CI cannot
   see and users never report. CI tests source against doubles; it never runs
   the published artefact against production, and that gap is where this
   class of defect lives. On 2026-08-22 this check found `strale-mcp` had
   shipped `0 cap trust, 0 sol trust` for roughly 3.5 months (routes deleted
   in May; the admin wall on their prefix answered 401 instead of 404; the
   client logged to invisible stderr and carried on). Procedure and the
   per-package contract: `docs/release/npm-publishing.md`.

## Rationale

Audit findings are typically reviewed for architectural correctness while
missing the runtime detail that actually failed — here, whether an import
statement in a PR's code example resolves against the currently published
package. Requiring verification of every imported symbol before any
prose-level edit removes the failure mode where a session polishes a PR's
wording while a fabricated import remains underneath: a cleaner PR
containing a broken import is worse than the unedited original, because it
reads as more trustworthy. The four-part pre-flight checklist, the
integrity check command, and the one-package-per-PR rule each target a
distinct way the same class of defect previously reached a maintainer's
inbox undetected. The production contract smoke test closes the remaining
gap: CI verifies source against doubles, never the published artefact
running against production, and that is exactly where the `strale-mcp`
silent-degradation incident lived for roughly 3.5 months.

## Consequences

**At session end, report:** every distribution PR touched, with the
verification result for each; every package published, with the observed
production smoke-test values; every `*-strale` package modified, with the
`check-framework-packages` output; anything that could not be verified and
why.

**Do NOT mark a distribution task as done if the pre-flight checklist did
not pass.** Report what is missing instead.

**This rule does not override:**
- The Capability Onboarding Protocol (`DEC-20260320-B`).
- Any PR-closure or code-change authorization that requires explicit
  Petter approval.

## Reversal conditions

Supersede this decision only with a new record that changes the trigger,
the six required steps, or the reporting obligations. An implementation
change that preserves the verify-before-polish ordering and every
numbered requirement above does not require supersession.
