## Decision

Composable architecture: build Strale as three independent, spinnable
units, a Capability Marketplace, an Agent Reputation Engine, and a
Commerce Protocol. Ride the giants on auth and identity; own the
reputation layer.

## Context

The row's stated basis, from the row's own Rationale: market research
found Visa (TAP), Ping Identity, WSO2, the OpenID Foundation, Incode,
Prove, and Vouched all building agent auth and identity infrastructure
(the row's "layer 1"). Nobody was found building agent reputation (the
row's "layer 2"), because that requires transaction data from an active
marketplace, which Strale's capability marketplace is positioned to
generate. Building the three units as independent, separately-APIed
pieces is framed as preserving the option to spin out any unit that gains
independent traction, rather than competing with the auth/identity giants
directly.

The historical Notion scope field on this row was `global` in the
workspace's old vocabulary. It is recorded here as `scope: product`: this
is a company-architecture strategy decision, not a single technical
integration.

## Rationale

The rationale, as the row states it: identity and auth for agents is
already a crowded, well-funded field (Visa, Ping, WSO2, OpenID Foundation,
Incode, Prove, Vouched); agent reputation is not, because it depends on
marketplace transaction data Strale is positioned to generate; the
three-unit split preserves optionality to spin any one unit out
independently later.

## Consequences

Status verified on 2026-09-05, against `main`.

**No separable "Agent Reputation Engine" or "Commerce Protocol" unit
exists on `main` as its own product with its own API.** A grep of
`apps/api/src` for "reputation" found matching capability names
(`domain-reputation`, `email-reputation-score`) and unrelated internal
uses, none of them an agent-facing reputation-scoring product as this row
describes. The commerce rail that did ship is x402
(`apps/api/src/lib/x402-gateway.ts`, CLAUDE.md's "x402 Payment Gateway
(March 2026)" paragraph: pay-per-use USDC payments on Base mainnet, "no
signup or API key needed, payment IS the auth"), a specific payment
protocol integration rather than a generalized, independently-spinnable
"Commerce Protocol" unit as this row frames it.

**The next day's `DEC-20260227-P-s9t0` explicitly revisits this row's
"three units" framing, reframing Unit 2 and questioning whether Unit 3 is
needed at all**; see that record for the fuller reconciliation of what
this row's architecture became.

**The "Capability Marketplace" unit, as a venue with buyer-facing
reputation for competing external operators, was also not built**; see
`DEC-20260224-P-a1b2`'s Consequences, which reach the same finding for
that same marketplace concept from a different, earlier row.
