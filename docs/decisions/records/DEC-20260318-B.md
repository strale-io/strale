## Decision

Upgrade the onboarding pipeline with three capabilities: (1)
execute-and-verify, which catches fixture mismatches at onboard time, (2)
`--fix`, which auto-corrects casing/synonym differences, and (3)
`--discover`, which inverts the flow: execute the capability first, then
generate fixtures from the real output. This is the workflow intended to
scale to third-party providers, who provide one input and let the pipeline
generate everything else.

## Context

`phone-type-detect` exposed a structural gap: manifest `expected_fields`
were written before the capability was ever executed, causing
`known_answer` test failures once the pipeline ran for real. The three
upgrades close that gap from different angles: execute-and-verify is a
safety check, `--fix` is a low-risk auto-correction, and `--discover` is
the structural fix that removes the human's need to guess output shape
before it exists.

The historical Notion scope field on this row was `global`. It is recorded
here as `scope: technical` under this repository's decision-record
vocabulary: this is a set of implementation upgrades to the engineering
onboarding pipeline.

## Rationale

Writing `expected_fields` before executing the capability requires
predicting the real API's output shape, which is unreliable. Executing
first and generating fixtures from the actual output (`--discover`)
removes that guesswork; execute-and-verify closes the remaining gap for
manifests still written by hand; `--fix` handles the class of mismatch
that is mechanical (field name casing, synonyms) rather than substantive.
Together they are, per the row's own text, "the workflow that scales to
third-party providers: they provide one input, the pipeline generates
everything else."

## Consequences

Status verified on 2026-09-04, against `main`.

**All three still exist in `apps/api/scripts/onboard.ts`.** Flag parsing
(`process.argv.slice(2)`) recognizes `--discover`, `--fix`, and `--strict`
(the flag that gates execute-and-verify: "Abort if execute-and-verify
fails," per the file's own header comment and CLAUDE.md's pipeline-flags
reference). The file contains dedicated execute-and-verify code (headed
"Execute-and-Verify (Enhancement 1)") and a `--discover` code path
(`abortIfDiscoveryFailedUnderStrict`) that runs before manifest fixtures
are finalized, matching this row's description of inverting execute-then-
generate. CLAUDE.md's "Adding New Capabilities (MANDATORY PIPELINE)"
section documents the same three mechanisms under the recommended
`--discover` workflow and the pipeline-flags reference (`--fix` "Auto-
correct high-confidence fixture mismatches," `--strict` "Abort if
execute-and-verify fails").

**phone-type-detect.** This row and `DEC-20260318-A` (recorded separately
in this batch) both name `phone-type-detect` as the capability that
motivated the change. See DEC-20260318-A's Consequences for the SQS-score
historicity note: the SQS engine that produced the 39.3 score named in
DEC-20260318-A no longer exists (deleted per DEC-20260503-B), so that
specific figure cannot be re-verified against a live scoring system today,
though the underlying `known_answer`-fixture gap it illustrates is what
this row's three upgrades address.

## Reversal conditions

Reconsider this decision if a future onboarding redesign removes
execute-and-verify, `--fix`, or `--discover` from the pipeline without
replacing the guarantee they provide (that fixtures are checked or derived
against real execution output rather than hand-guessed in advance).
Represent such a change through a new decision rather than editing this
protected record in place.
