## Decision

Fix `resolveInputRef` so it walks a nested path
(`stepOutput.license.spdx`) instead of doing a bracket lookup on a
dot-joined key (`stepOutput['license.spdx']`), which silently resolved
every nested cross-step reference to `undefined`.

## Context

The row's stated basis, from its own Rationale: `resolveInputRef` used
bracket lookup on a dot-joined key instead of walking the path, so all
nested cross-step references silently resolved to `undefined`. The fix
is a small path parser plus traversal supporting arbitrary depth,
bracket-integer array indices, and mixed syntax, with no wildcards or
filters. Arbitrary depth was chosen over one-level because real API
responses have 3-4 levels and the implementation cost difference is
roughly 20 lines. Structured errors at resolution time surface which
segment failed, replacing silent `undefined`. The row states the blast
radius was bounded because no nested-ref solution had been verified as
working end-to-end, but `dependency-risk-check` is in the catalog using
this syntax and needed it fixed. The row's Outcome: shipped.
`solution-executor.ts` now uses `parsePath()` + `walkPath()` that walk
dot notation and bracket indices to arbitrary depth, replacing the flat-
key lookup that had been silently returning `undefined` for nested
references since Phase 1.2 (commit `1726823`). 10 new test cases were
added covering 2-level and 4-level nested paths, array indices, mixed
dot+bracket syntax, type mismatches, wildcard rejection, and the
specific `dependency-risk-check` `$steps[0].license.spdx` pattern. Blast
radius check: exactly 1 solution in the catalog (`dependency-risk-check`)
used nested refs; no other solutions were affected; no out-of-scope
syntax (wildcards, quoted keys, negative indices, filters) was found
anywhere in the catalog. `dependency-risk-check` step 2 received the
actual `license.spdx` value instead of `undefined` for the first time
since it was created.

## Rationale

The rationale, as the row states it: arbitrary-depth path walking costs
roughly 20 more lines than a one-level fix and matches real API response
shapes (3-4 levels), so the deeper fix was chosen; structured
per-segment errors replace a silent failure mode that had been masking
the defect since Phase 1.2.

## Consequences

Status verified on 2026-09-05, against `main`.

**The fix is live and matches the row's description exactly.**
`apps/api/src/lib/solution-executor.ts`'s module header documents the
input-mapping syntax: "`$input.<field>` — resolves to caller's
`inputs[<field>]`", "`$steps[N].<field>` — resolves to step N's
`output[<field>]` (0-indexed by execution order)", "`$all_results` —
resolves to an object of ALL prior step outputs keyed by slug." The file
exports `parsePath()` and `walkPath()`, and `resolveInputRef()`'s own
doc comment states: "`$input.<path>` → walk path from inputs (supports
nested: `$input.company.name`)" and "`$steps[N].<path>` → walk path from
`completedSteps[N]` (supports nested: `$steps[0].license.spdx`)" —
matching the row's named example exactly.

This record did not independently re-verify the row's claimed commit
(`1726823`) marking when the flat-key defect was introduced, or its
"10 new test cases" figure; those are preserved as the row's own text.
