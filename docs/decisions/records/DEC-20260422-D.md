## Decision

Add four typed, optional fields to `RichProvenance` for attribution and
licensing disclosure:

- `attribution`
- `license`
- `license_url`
- `source_note`

Capabilities sourcing data from open-data APIs (the row's example: High-Value
Datasets, "HVD etc.") must populate all four.

The Notion row carries no separate Rationale, Outcome, Confidence rationale,
or Source beyond the Decision statement itself and `Confidence: high`. There
is no further text to preserve or compress.

## Context

The historical Notion scope field on this row was `global` in the workspace's

## Consequences

Status verified on 2026-09-04, against `main`:

- All four named fields exist on `RichProvenance` in
  `apps/api/src/lib/provenance-builder.ts` today, each optional
  (`attribution?: string`, `license?: string`, `license_url?: string`,
  `source_note?: string`), with an in-code comment naming the High-Value
  Dataset registries this decision's "HVD etc." example points at:
  "notably EU High-Value Datasets under Reg. (EU) 2023/138 such as
  Bolagsverket HVD, KVK HVDS, Brreg, CVR, PRH, ARES, Ariregister" and stating
  "Capabilities sourcing from open-data APIs should set all four." The
  comment also notes the fields are hash-anchored via
  `integrity-hash.ts` as part of the tamper-evident provenance payload, an
  integrity mechanism this Decision row does not itself describe, added
  after adoption.
- The population obligation is followed by a bounded set of capability
  executors on `main` today, not by every capability: 22 files under
  `apps/api/src/capabilities/` (including `providers/`) set `attribution:`,
  among them the two cited above (`swedish-company-data.ts`,
  `austrian-company-data.ts`) plus other European company-registry
  capabilities (Belgian, Brazilian, Czech, Danish, Estonian, Finnish,
  German, Irish, Latvian, Lithuanian, Polish, Slovak, Slovenian, Spanish,
  Swiss, Singaporean, UK, and US SEC/Cobalt sources). This is consistent
  with the Decision's own scope ("capabilities sourcing from open-data
  APIs"), not a contradiction of it: capabilities calling non-open-data
  sources (paid vendor APIs, AI-synthesis capabilities) have no obligation
  under this row and correctly leave the fields unset.
- No manifest schema field (`manifests/*.yaml`) carries `license_url` or
  `source_note`; population happens entirely inside the executor's
  `buildProvenance()` call, not through the onboarding manifest pipeline
  described in `CLAUDE.md`'s "Adding New Capabilities" section. This Decision
  row predates that pipeline's field-reliability and manifest-driven
  provenance conventions and is unaffected by them; the fields it added are
  still populated the same way (in-code) as when the Decision was written.

## Reversal conditions

Reconsider this decision if the four attribution fields are moved from
per-executor population into the manifest-driven onboarding pipeline (so a
capability declares its licence terms once, in `manifests/*.yaml`, instead of
in the executor body), or if the High-Value Dataset population obligation is
extended to require these fields for a data-source class the row did not
name. Represent such a change through a new decision and an explicit
`supersedes` or `amends` relationship rather than editing this protected
record in place.
