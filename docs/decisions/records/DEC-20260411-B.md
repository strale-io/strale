## Decision

Add Gate 5: path coverage enforcement to the capability onboarding
pipeline. Every multi-path capability must have fixtures covering all
entry points before going live. Two spec refinements accompany the gate:
(1) asymmetric fixture requirements — the ID path (PRIMARY) needs strict
coverage, the name path (SECONDARY) needs at least one fixture; (2) an
inward-trace heuristic — entry points are defined by the handler's dispatch
logic, not by exported functions, and cache/retry/fallback branches are not
entry points, avoiding false positives.

## Context

A path coverage audit on 2026-04-09 found 12 of 15 multi-path capabilities
had shipped with uncovered entry points. All 12 had ID-path fixtures but no
name-path fixtures. The named case: Polish company-data name search was
broken for weeks without detection because no fixture tested it. Gate 5
prevents recurrence at onboarding time.

The historical Notion scope field on this row was `global`. It is recorded
here as `scope: technical` under this repository's decision-record
vocabulary: this is an onboarding-pipeline gate, an engineering control.

## Rationale

A capability that accepts multiple kinds of input (an ID and a name, for
example) can pass onboarding while only one path is ever exercised by a
fixture, leaving the other path's correctness unverified in production
until a customer hits it. Gate 5 makes fixture coverage of every dispatch-
level entry point a precondition of shipping. The asymmetric rule (strict
on PRIMARY, at-least-one on SECONDARY) reflects that ID lookups are
usually the capability's core contract while name search is commonly a
convenience path. The inward-trace heuristic (dispatch logic, not exported
functions) exists specifically to avoid false positives from
cache/retry/fallback code that is not a real entry point — the row names
`bank-bic-lookup` as the case this avoids misclassifying.

## Consequences

Status verified on 2026-09-04, against `main`.

**Gate 5 exists in code today, under the same name.**
`apps/api/src/lib/gate5-path-coverage.ts` exists on `main`; its own header
comment states: "PRIMARY: ID-based lookup... SECONDARY: Name-based
search... Entry points are defined by the handler's dispatch logic (inward
trace), NOT by exported functions. Cache/retry/fallback branches are
excluded" — matching this row's Decision and both refinements verbatim in
substance. `apps/api/scripts/onboard.ts` references
"Gate 5 multi-path fixture coverage, DEC-20260411-B" directly by this
row's own id in multiple comments, and gates known_answer/schema_check
fixture generation on it for array-form (multi-entry-point) manifests.

**The asymmetric rule is implemented as described.** The gate5 module's
coverage check (`hasPrimary`/`hasSecondary` entry-point enumeration and
fixture matching) requires PRIMARY entry points to have fixtures and
SECONDARY entry points to have at least one, matching "ID path (PRIMARY)
needs strict coverage, name path (SECONDARY) needs at least one fixture."

**The inward-trace heuristic survives; the named false-positive case
does not appear in the code.** The module's header describes the
inward-trace/dispatch-logic rule in general terms; neither
`gate5-path-coverage.ts` nor `onboard.ts` names `bank-bic-lookup`, which
only this row's Rationale names (verified 2026-09-04 by grep).

**polish-company-data still exists on `main`** at
`manifests/polish-company-data.yaml` /
`apps/api/src/capabilities/polish-company-data.ts`, so the case study this
row cites remains a live, checkable capability rather than a since-removed
one.

## Reversal conditions

Reconsider this decision if a future onboarding redesign removes Gate 5's
path-coverage check or its asymmetric PRIMARY/SECONDARY fixture rule
without replacing the guarantee that every dispatch-level entry point of a
multi-path capability has at least one fixture. Represent such a change
through a new decision rather than editing this protected record in place.
