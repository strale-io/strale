## Decision

Whenever work creates, modifies, or onboards a capability, follow the complete
Capability Onboarding Pipeline regardless of how narrowly the prompt describes
the requested capability. The prompt defines what to build; the pipeline
defines how it enters Strale.

Before coding, read the pipeline specification. Create or update the manifest,
declare reliability for every output field, document at least one limitation,
validate the structure, set latency, run readiness, and report readiness and
smoke-test results. Do not mark onboarding complete while readiness fails;
name the missing step instead.

## Context

Capability requests arrived through human prompts, chat handoffs, and ad-hoc
instructions that rarely repeated the full onboarding specification. Without
an entrypoint rule, an agent could implement the requested executor while
omitting reliability, limitations, testing, or lifecycle controls.

The rule correctly made onboarding an always-enforce protocol. Its mechanism
description later proved inaccurate because it read as though the post-insert
hook populated reliability and limitations for every write path.

## Rationale

A system-level trigger makes process completeness independent of prompt
quality and session memory. Separating product intent from onboarding mechanics
prevents a short implementation request from implicitly waiving platform
quality controls.

## Consequences

Capability work gained a mandatory read-first pipeline, completion report, and
refusal boundary. The rule did not override the requested slug, schemas,
pricing, or behavior.

`DEC-20260423-B` superseded this record after an audit found that thirty-four
capabilities across six cohorts lacked fields the original mechanism implied
were universal. The always-enforce principle survived; the lifecycle and write
mechanisms were corrected. Current entrypoints still display this superseded
ID, a gap preserved in the capability-onboarding authority report.

## Reversal conditions

This record is already superseded. Its successor may be replaced only by a new
decision that preserves equivalent prompt-independent onboarding enforcement,
structural controls, observable readiness, and explicit incomplete-work
reporting. Do not reactivate this historical mechanism by editing the record.
