## Decision

Set the publication SQS threshold at 60 or above, ten points higher than
the automated qualification gate at 50 or above.

## Context

The row's stated basis, from its own Rationale: "Automated gate at SQS
50 = 'this works.' Publication gate at SQS 60 = 'this meets Strale brand
standard.' 10-point gap allows investigation of capabilities that
technically work but have quality concerns before going public."

The historical Notion scope field on this row was `global`. It is
recorded here as `scope: product`: it sets a brand-quality bar for what
the platform shows publicly, not a general company-wide strategic
decision. The row's own text does not name a specific Decision ID for
the "automated >= 50 qualification gate" it refers to; checking the
titles of the two batches of formal records this brief pointed at
(DEC-20260316-A "Eliminate Combined Trust Grade (A/B/C/D) from all
surfaces," DEC-20260316-B "SQS display hierarchy: number+word headline, QP/RP
letters as secondary detail only," DEC-20260318-A "ALL new capabilities
must use manifest-driven pipeline (scripts/onboard.ts), NEVER old seed.ts
+ onboarding hook," DEC-20260318-B
"Onboarding pipeline upgraded with --discover, --fix, and
execute-and-verify") finds none of them is the "automated >= 50 gate"
itself, so no relation edge is recorded here.

## Rationale

The rationale, as the row states it: passing the automated bar proves a
capability functions; publication is a brand claim, and the ten-point
gap between the two gates is deliberate headroom to catch capabilities
that pass mechanically but are not yet good enough to represent the
brand publicly.

## Consequences

Status verified on 2026-09-05, against `main`.

**Both SQS thresholds (50 and 60) and the qualification gate they
describe are gone.** CLAUDE.md states: "SQS scoring engine deleted per
DEC-20260503-B (PR1 shipped 2026-05-05). The dual-profile model (QP + RP
+ 5x5 matrix), the `min_sqs` request parameter on POST /v1/do, the
platform floor SQS gate, the floor-aware solution SQS rule, the public
`/v1/quality/:slug` endpoint, and the automatic lifecycle transitions ...
are all gone." A route-level check confirms this:
`apps/api/src/app.ts` carries the comment "/v1/quality/:slug retired
with the SQS engine (DEC-20260503-B)" at the point the route used to be
registered; no live route by that path exists today.

**What replaced the numeric-threshold model is a pass/fail floor with a
quarantine action, on measured production traffic rather than a
qualification score.** `apps/api/src/db/seed-solutions.ts` comments
directly on this history: "SQS-based qualification gate retired
(DEC-20260503-B). The replacement asked for 'at least one passing
test_result in the last 30 days' per step capability — and that rule is
wrong for anything we deliberately do not test." The current floor,
`apps/api/src/lib/quality-floor.ts`, quarantines a capability below 70%
success and proposes deactivation below 30%, gated on at least 10
eligible calls in 30 days (per DEC-20260812-A, CLAUDE.md: "armed in
prod, not dry-run"). There is no "publication" gate distinct from a
"works at all" gate any more: the floor is a single threshold applied
after the capability is already live and receiving real traffic, not a
pre-publication brand-quality bar checked before a capability goes
public.

**No publication threshold survives in code.** The only grade-style
computation left, `computeTrustGrade` in
`apps/api/src/lib/trust-grade.ts`, has no callers outside its own file (a
grep of `apps/api/src` for `computeTrustGrade` returns only that file), as
batch 9 first found.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null).
DEC-20260503-B deleted the SQS engine both thresholds in this row
depended on; DEC-20260812-A's quality floor (70%/30%, production-traffic
gated) is the mechanism doing comparable work today, though it operates
after publication rather than as a pre-publication gate.
