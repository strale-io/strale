## Decision

Luxembourg and Hungary remain in gap-recovery deferred status, pending
either the Openapi case 151296 outcome or revenue-justified per-country
vendor contracts. No multi-country aggregator backup remains after
`DEC-20260507-F`'s Kyckr rejection.

## Context

The same gap-recovery spike attributed to "CC, 2026-05-07, commit
84398f7" verified that neither country had a Tier-1 doctrine-clean
v1-economic path at the time: Luxembourg has only a paid LBR enterprise
API, sales-gated, recorded as conflicting with `DEC-20260506-G`; Hungary
has no government open-data publication, only Hungarian-native commercial
wrappers (`companyapi.hu` at EUR 42-100/month subscription, no
pay-as-you-go, recorded as conflicting with `DEC-20260506-G`). With Kyckr
rejected per `DEC-20260507-F`, the row states no multi-country aggregator
backup remains. Revival triggers are recorded as explicit per country
(without further detail in the row itself).

The historical Notion scope field on this row was `global` in the
workspace's old vocabulary. It is recorded here as `scope: technical`
under this repository's decision-record vocabulary: this is a per-country
gap-status classification.

## Rationale

The rationale is the same doctrine and cost-sequencing logic as the
row immediately before it (`DEC-20260507-G`): with the multi-country
aggregator fallback (Kyckr) rejected, and no doctrine-clean free or
pay-as-you-go path found for either country, both are classified deferred
rather than built on a fixed-cost commercial wrapper.

## Consequences

Status verified on 2026-09-04, against `main`.

**Commit `84398f7`, named as this row's source, does not resolve in this
repository's history**, for the same reason stated on `DEC-20260507-G`.

**Neither Luxembourg nor Hungary remained deferred; both were built on
the vendor aggregator this row's own logic set aside.**
`manifests/luxembourgish-company-data.yaml` and
`manifests/hungarian-company-data.yaml` both state `data_source: Openapi.com
WW-Top (Tier-3 vendor aggregator of EU company registries)`, added in the
same 2026-05-16 commit (`9ee19282`) as Bulgaria's and Cyprus's manifests.
Both capabilities carry the identical limitation: "Gated behind
`OPENAPI_ENABLED` flag pending resale addendum countersignature," citing
"Openapi case 151296," the same case this row names as one of its two
revival conditions. `config/env-manifest.yaml`'s `OPENAPI_ENABLED` row
confirms it "MUST stay 'false' in production until the resale addendum is
countersigned." So this row's stated deferred status did not hold either:
both countries were built, on the case-151296-gated Openapi path this
row's Rationale treated as unavailable rather than pending, and both
capabilities are inactive in production until that legal condition
clears, which is one of this row's own two named revival triggers.

**HU's status was independently refined the next day.** `DEC-20260508-A`
(migrated by this same batch) refines this row's Hungary portion, stating
explicitly "Refines HU portion of DEC-20260507-H; LU portion unchanged."
See that record's own Consequences for the OCCSZ Disztributor finding.

## Reversal conditions

The row's own two named triggers stand unedited: the Openapi case 151296
outcome, or a revenue-justified per-country vendor contract. Both
countries' current capabilities are gated on exactly the first of those
two triggers, per their manifests' limitations.
