## Decision

Hide component (capability) prices in the discovery UI. Solution prices
are shown everywhere; capability prices appear only on their own detail
pages. `TypeaheadResult.price_cents` is `null` for capabilities, and no
discovery API response carries a `component_sum_cents` field.

## Context

The row's stated basis, from its own Rationale: showing component
prices next to solution prices invites mental unbundling. A developer
seeing "€1.50 solution + €0.80 capability" calculates "36% markup"
instead of evaluating "€1.50 for KYC verification." The row's `Source`
field points to a shared specification page
(`https://www.notion.so/31967c87082c816d9d44cd4317386a30`), the same
page two other same-day rows in this batch (the "kill DIY calculator"
and "trust data must never be displayed with false confidence" rows)
cite as their source, consistent with all three having been logged
against one Discovery & Navigation specification.

This historical ID is reused by a second, unrelated Notion row (a
homepage v2.1 visual-polish decision made the same day) and was an
unresolved registry collision until this batch; the two rows are
resolved together in
`archive/sessions/2026-09-05-decision-collision-resolution-DEC-20260304-A.md`
with distinct source-qualified record keys. This record covers only the
component-price-hiding row.

## Rationale

The rationale, as the row states it: the correct comparison for a buyer
is the solution's own value ("€1.50 for KYC verification"), not an
implied markup over Strale's own cost of components; exposing the
component sum invites the wrong comparison and should never appear in
discovery surfaces.

## Consequences

Status verified on 2026-09-05, against the sibling `strale-frontend`
checkout, read-only.

**The `TypeaheadResult` interface matches the row exactly, with a
self-citing code comment.**
`strale-io/strale-frontend@04c9fca9:src/types/index.ts` defines
`TypeaheadResult.price_cents` as `number | null` with the inline
comment `// null for capabilities (DEC-20260304-A)`. The current code
names this decision directly.

**No `component_sum_cents` field exists on the discovery/suggestion
types.** `SuggestRecommendation` and `TypeaheadResult` in
`src/types/index.ts` carry no `component_sum_cents` field, matching the
row's "No component_sum_cents in any discovery API response" rule.

**A `component_sum_cents` field exists elsewhere, on a different
surface, but is not rendered.** `SolutionDetail` (the shape for
`GET /v1/solutions/:slug`, not a discovery/suggestion endpoint) does
carry a `component_sum_cents` field in both
`strale-io/strale-frontend@04c9fca9:src/types/index.ts` and the raw-shape
normalizer in `src/lib/api.ts`. Neither
`strale-io/strale-frontend@04c9fca9:src/pages/Solutions.tsx` nor
`src/pages/SolutionDetail.tsx` renders that field. This is a distinct
surface from the "discovery UI" the row's rule targets (typeahead and
suggest results), and this record does not treat it as a contradiction
of the row, but flags it as a field that exists on the wire without a
visible consumer, worth a future cleanup pass.

**Solution prices are shown, capability prices are not, on the pages
checked.** `src/pages/Solutions.tsx` sorts and displays solutions by
`price_cents`; no capability-level price rendering was found on that
page or on `SolutionDetail.tsx`.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null in
the source). A future decision to display component-level pricing
anywhere in the discovery UI, or to reintroduce a component-sum field on
a discovery response, would supersede this row.
