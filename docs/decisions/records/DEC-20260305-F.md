## Decision

Run a full test suite audit fixing all field mismatches, bad test data,
and capability bugs across all 98 tests that existed at the time, after
the same audit pattern had already been applied individually to
`sanctions-check`, `vat-validate`, and `swedish-company-data`.

## Context

The row's stated basis, from its own Rationale: applying the individual-
capability audit pattern platform-wide found 7 input field mismatches
(category A), 14 validation field mismatches (category A), 2 bad test
data entries (category B), 4 external flaky tests (category C,
documented), and 3 real bugs (category D, fixed). The remaining 4
failures were VIES rate limiting (a retry already existed) and Google
PageSpeed quota (HTTP 429), both genuinely external.

The row's own Outcome field states: "72/98 → 94/98 passing (96%). 21
field/data mismatches fixed, 3 capability bugs fixed, 4 external flaky
tests documented. email-deliverability-check: added resolve6 fallback.
whois-lookup: added IANA root fallback."

The historical Notion scope field on this row was `global`. It is
recorded here as `scope: technical`: it is a one-time test-infrastructure
remediation project, not a company-wide strategic or positioning
decision.

## Rationale

The rationale, as the row states it: the individual-capability audit
pattern (already proven on three capabilities) generalizes to the whole
suite, and doing it once platform-wide is cheaper than repeating the
same fixes capability-by-capability as bugs surface.

## Consequences

Status verified on 2026-09-05, against `main`.

**The five-test-type structure this audit operated on survives today.**
CLAUDE.md's Capability Onboarding pipeline section states the pipeline
"generates all 5 test types (known_answer, schema_check, negative,
edge_case, dependency_health)," and `apps/api/scripts/onboard.ts` is the
canonical, sole sanctioned path for capability creation and test
generation per the same section. This is the same five-type taxonomy
this row's audit was fixing test data and field mismatches against.

**The test-count baseline this row audited (98) is long superseded by
platform growth**, not by a further audit of the same 98 tests; the
platform runs 342 capability manifests today (`ls manifests/*.yaml`,
2026-09-05), each contributing its own test suite, so a like-for-like
re-audit of "98 tests" does not apply to the current test population.
This record does not claim today's test pass rate; per this batch's
brief, no bare test count is asserted without a receipt, and this row's
audit predates the receipts regime entirely (DEC-20260504-A/T15).

**DEC-20260503-B changed how tests are scheduled after this row's audit
ran.** CLAUDE.md's "Capabilities & Quality" section states test
scheduling now filters on `test_suites.scheduled_testing_eligible = TRUE`,
derived from `external_cost_cents = 0` and rewritten by a startup
migration on every boot; paid capabilities are not proactively tested any
longer. This row's audit ran before that scheduling change and does not
address it.

## Reversal conditions

None recorded on the row beyond the shipped-Outcome text quoted above
(`Superseded By` is null in the source). A future test-infrastructure
audit against the current 342-manifest population, cited with a receipt
per the T15 evidence-receipts regime, would be the natural successor to
this row's one-time 2026-03-05 remediation.
