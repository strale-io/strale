## Decision

Close the capability-onboarding coverage gap as one staged structural fix:

1. extend readiness to check output-field reliability and active limitations,
   initially in warning mode;
2. route administrative and seed creation through `persistCapability`, and
   block accidental direct inserts with a PostgreSQL trigger requiring a
   transaction-local token;
3. backfill eligible active capabilities through live discovery, while parking
   cohorts that are intentionally excluded or lack valid fixtures; and
4. make the new readiness dimensions blocking after the backfill boundary is
   established.

Use live `--discover` output rather than fallback-derived metadata so the fix
does not encode semantically thin guesses as the onboarding standard.

## Context

The audit behind `DEC-20260422-C` found that the post-insert hook did not
populate reliability or limitations and that `auto-register.ts` was unrelated
to database insertion. Thirty-four capabilities across six cohorts were
affected through multiple historical paths, and readiness did not block the
missing fields.

## Rationale

Warning-first rollout exposed the actual remediation set without immediately
breaking served capabilities. A shared persistence path reduced application
bypasses, while a database trigger covered inserts from other clients. Live
discovery preserved evidence quality, and parking unready cohorts avoided
activating fabricated metadata merely to complete a backfill.

## Consequences

Five commits implemented the staged change. Eighteen of twenty-one targeted
active backfills passed; three fixture-blocked capabilities joined nine
permanently parked UK-property capabilities, while four legacy-deactivated
rows remained intentionally incomplete. Reliability and limitation checks then
became blocking.

Current code retains the persistence and readiness controls, but the original
trigger migration file was later removed during migration consolidation and no
current trigger-creation DDL is present in repository source. This candidate
therefore records the decision and historical implementation, not proof of
fresh-database or production trigger state. The source-gap report defines the
required read-back before M4.

## Reversal conditions

Supersede or amend this decision only if a stronger control closes every
capability creation path, derives contract metadata from equivalent or better
evidence, blocks activation when readiness is incomplete, and proves the
control fires on fresh and existing databases. Individual implementation
components may be replaced, but silent bypasses or fallback-only completion
are not acceptable substitutes.
