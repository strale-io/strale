## Decision

Fix the solution batch trust endpoint's freshness-staleness check to
`ORDER BY schedule_tier DESC` (the least-frequent tier), replacing an
`ASC` order that picked the most-frequent tier and mismatched the
staleness threshold.

## Context

The row's stated basis, from its own Rationale: "The solution batch
trust endpoint used ORDER BY schedule_tier ASC, picking tier A (6h).
Capabilities with tier A suites not tested in >24h appeared 4x overdue
(24/6=4). Correct behavior: pick the least-frequent tier (DESC → tier
C, 72h) so staleness threshold matches the longest scheduled interval.
This aligns with the single-capability endpoint which already used the
correct tier. Bug caused all solutions to show ⏱ Stale on
strale.dev." The row's own Outcome field states: "All solutions now show
improving or stable. lei-lookup correctly shows stable instead of
stale."

The historical Notion scope field on this row was `global`. It is
recorded here as `scope: technical`: it is a specific query-ordering bug
fix inside a routes file, not a company-wide strategic decision. The
row's own text does not name any other Decision ID, so no relation edge
is recorded here.

## Rationale

The rationale, as the row states it: picking the most-frequent test tier
(ASC, tier A at 6h) as the staleness reference made every solution with a
mixed-tier step set look overdue relative to a 6-hour clock even when its
slower-tier steps were on schedule; ordering by the least-frequent tier
(DESC, tier C at 72h) is the correct staleness reference because it
matches the longest interval any step is actually scheduled against.

## Consequences

Status verified on 2026-09-05, against `main`.

**No `ORDER BY schedule_tier` of either direction exists in either file
the row names today.** A direct search
(`grep -n "schedule_tier\|scheduleTier\|ORDER BY"
apps/api/src/routes/solutions.ts apps/api/src/routes/internal-tests.ts`)
finds `schedule_tier` referenced only in `internal-tests.ts` (an
admin/internal route, not the customer-facing "solution batch" endpoint
the row names), and no `ORDER BY schedule_tier` clause in either file. A
repo-wide search
(`grep -rln "schedule_tier\|scheduleTier" apps/api/src --include=*.ts`,
excluding tests) finds it in `db/backfill-schedule-tiers.ts`,
`db/schema.ts`, `lib/capability-onboarding.ts`, `lib/meta-monitoring.ts`,
`lib/piggyback-monitor.ts`, `lib/startup-migrations.ts`, and
`routes/admin.ts`, none of which is the customer-facing solutions
endpoint this row describes.

**The closest thing today is a different mechanism: freshness computed
per step and reduced to the worst label, not an ordered tier pick.**
`apps/api/src/routes/solutions.ts` imports `worstFreshnessLevel` from
`apps/api/src/lib/trust-labels.ts` and calls it as
`worstFreshnessLevel(steps.map((s) => s.freshnessLevel ?? "fresh"))`
(line 96). This computes freshness from a stored, precomputed
`freshnessLevel` label per capability and takes the least-fresh label
across a solution's steps, rather than sorting live rows by
`schedule_tier` and picking one row's tier value as a staleness
reference. It reaches a comparable outcome (a solution is only as fresh
as its stalest step) through a labeled-aggregation approach rather than
the `ORDER BY ... DESC` query the row's fix describes; this record does
not attempt to date when the row's original SQL-level fix was replaced
by this label-based approach, only that the SQL clause no longer exists.

## Reversal conditions

None recorded beyond the row's own Outcome text ("All solutions now show
improving or stable"), which describes the immediate effect of the fix
at the time, not its long-term survival. The current
`worstFreshnessLevel`-based mechanism in `solutions.ts` is the closest
surviving artifact; whether it descends directly from this fix or
replaced it separately is not established by this record.
