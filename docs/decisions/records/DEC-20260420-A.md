## Decision

Abandon `drizzle-kit generate` entirely. Hand-write migrations going forward.
This formalises what the team had been doing since migration 0008 anyway: the
last 40 migrations were all hand-written, and the snapshot folder only
reflected the first 8.

Drizzle remains the source of truth for ORM query building (`schema.ts`
defines the shape code reads). `drizzle-kit migrate` remains the tool that
applies migrations against prod (working correctly post the SCF-5 fix below).
`drizzle-kit generate` is not used; the `db:generate` npm script was kept in
`package.json` at adoption time but was not to be invoked.

Migration authoring workflow adopted:

1. Update `schema.ts` with the intended column/table change.
2. Hand-write the SQL migration file at `apps/api/drizzle/NNNN_descriptive_name.sql`,
   matching the style of existing 0008-0047 files.
3. Append a matching entry to `apps/api/drizzle/meta/_journal.json` with
   `idx`, `version` '7', `when` (current epoch ms), `tag` (filename stem),
   `breakpoints: true`.
4. Commit both the SQL file and the journal update together.
5. After deploy (per the always-enforce Rule 1): `cd apps/api && npx drizzle-kit migrate`,
   verify via `psql`.

This supersedes the implicit assumption that `drizzle-kit generate` was the
migration-authoring tool. The cc-prompts skill's Drizzle deployment rule
(Rule 1) is unchanged: `drizzle-kit migrate` after deploy is still the
pattern named at adoption time.

## Context

SA.2a's deploy failure exposed two drift problems: SCF-5 (`_journal.json`
and `__drizzle_migrations` tracker both out of sync with applied prod state)
and its sibling (`meta/*.json` schema snapshots stopping at migration 0007).

The tracker drift (SCF-5) was fixed by hand-backfilling `_journal.json` to
include migrations 0008-0047 and inserting 49 matching rows into the prod
`__drizzle_migrations` table (commits `25a91ba`, `df7d611`). `drizzle-kit
migrate` worked correctly after this fix.

The snapshot drift was NOT fixed. Three options were weighed:

- **Option A** — backfill 40 snapshots by reverse-engineering schema state.
  Rejected: too brittle and time-consuming.
- **Option B** — use `drizzle-kit introspect` to dump current prod as a
  single head snapshot. Rejected: it worked mechanically, but encoded a
  fiction — there is no single historical moment that corresponds to "the
  0048 snapshot." It is a lie that would propagate into future diffs.
- **Option C (chosen)** — abandon `drizzle-kit generate` entirely and
  hand-write migrations going forward, formalising the pattern already in
  use since migration 0008.

SCF-3 (an untracked external workflow writing to
`transactions.integrity_hash_status`) remains the structural problem this
decision reveals: if the team had owned that workflow, the snapshot drift
would not have mattered, because schema.ts and migrations would have been
regenerated together. Deferred to a later session's scope at adoption time.

Source: `https://github.com/strale-io/strale/commit/71f6c49`. Confidence:
high.

## Rationale

Hand-writing migrations against a known-drifted snapshot folder is more
honest than generating a snapshot that asserts a historical moment that
never existed as a coherent, diffable state. It also matches the pattern the
team had already been running for 40 consecutive migrations, so the decision
formalises existing practice rather than introducing a new one.

## Consequences

Status verified on 2026-09-04, against `main`. This decision's own scope
(abandon `drizzle-kit generate`; hand-write SQL migration files under
`apps/api/drizzle/`) was itself superseded on 2026-05-11 by `DEC-20260511-C`,
which replaced hand-written Drizzle SQL migrations with in-TS
`startup-migrations.ts` blocks and deleted the `apps/api/drizzle/` directory,
`drizzle.config.ts`, and the `drizzle-kit` devDependency entirely (per that
row's Outcome, verified as of 2026-05-13). `DEC-20260511-C`'s own Rationale
states it preserves this record's no-auto-generation, hand-written
discipline — "we still hand-write; just in TS, not SQL files" — so the
underlying convention (no `drizzle-kit generate`, hand-authored migration
logic) survives, even though the concrete `apps/api/drizzle/*.sql` +
`_journal.json` mechanism this record describes does not. On main today,
`apps/api/drizzle.config.ts` exists again and `drizzle-kit` is once more a
devDependency, but only to bootstrap the ephemeral integration-test database
in CI (`.github/workflows/ci.yml` runs `drizzle-kit push --force` in the
integration-db lane); production schema changes still go through the
ledgered in-TS blocks in `apps/api/src/lib/startup-migrations.ts` (see
`DEC-20260511-C` and `npm run migrations:check`, T15 of `CLAUDE.md`), not
through `drizzle-kit generate` or hand-written SQL files. `apps/api/package.json`
carries no `db:generate`/`db:migrate`/`db:push` script today.

## Reversal conditions

This record's concrete mechanism (hand-written `apps/api/drizzle/*.sql` files
plus a manually maintained `_journal.json`) was already superseded by
`DEC-20260511-C`. Any further change to how schema migrations are authored
should be represented as a new decision with an explicit `supersedes` or
`amends` relationship targeting the current convention record, rather than
editing this protected historical record in place.
