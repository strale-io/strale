## Decision

Build a web provider abstraction layer (`web-provider.ts`) that all 47
scraping capabilities route through, giving retry, cache, and failover
hooks instead of direct Browserless coupling in each capability.

## Context

The row's stated basis, from its own Rationale: direct Browserless
coupling in 47 capabilities meant zero retry, zero caching, and zero
fallback. Rather than patching each capability individually, the fix is
a shared abstraction that gives every consumer retry with exponential
backoff and jitter, an in-memory LRU response cache (5-minute TTL, 200
entries), and a provider-agnostic interface. `swedish-company-data`
additionally gets LLM fallback parsing via `parseWithFallback()`. Future
providers (Notte, Firecrawl, Stagehand) plug into one file.

The row's own Outcome field states: "Shipped. 47 capabilities upgraded
via re-export in browserless-extract.ts. Three new functions:
fetchRenderedHtml (cached+retry), fetchRenderedHtmlFresh (no cache),
fetchCompanyPage (registry-tuned). Zero consumer changes required."

The historical Notion scope field on this row was `global`. It is
recorded here as `scope: technical`: it specifies an internal executor
abstraction, not a company-wide strategic or positioning decision.

## Rationale

The rationale, as the row states it: centralizing retry, caching, and
failover logic in one file lets every consumer benefit without individual
capability changes, and gives future scraping-provider swaps (Notte,
Firecrawl, Stagehand) one integration point instead of 47.

## Consequences

Status verified on 2026-09-05, against `main`.

**`web-provider.ts` exists and is reached today, but through an
intermediary re-export layer rather than direct import, exactly as the
row's own Outcome field described at the time.**
`apps/api/src/capabilities/lib/web-provider.ts` exists. Its retry, cache,
and provider-agnostic interface functions
(`fetchRenderedHtml`/`fetchRenderedHtmlFresh`/`getBrowserlessConfig`) are
re-exported from `apps/api/src/capabilities/lib/browserless-extract.ts`,
whose own header comment states: "fetchRenderedHtml and
getBrowserlessConfig are re-exported from web-provider.ts." A direct
`import ... from "./web-provider.js"` (or `lib/web-provider`) appears in
only 2 files under `apps/api/src/capabilities`
(`web-extract.ts` and its test), matching the row's own description of
the architecture: capabilities import `browserless-extract.ts`, which
re-exports from `web-provider.ts`, not the other way round.

**Today's importer count is 36, not 47.** `grep -rl "browserless-extract"
apps/api/src/capabilities` (excluding test files) returns 36 non-test
capability files that import the re-export layer and therefore route
through `web-provider.ts` transitively. This is fewer than the 47 the row
states was true when shipped; some capabilities may have been retired,
consolidated, or moved to a different fetch path since 2026-03-05, and
this record does not attempt to reconcile which ones, only that the
current count differs from the historical one.

**The Browserless v1/v2 split named in this batch's brief is visible in
the same file.** `browserless-extract.ts` contains an explicit comment
distinguishing "Browserless v2 cloud (production-*.browserless.io)" from
an implied v1 path, in the context of the `?token=` query-parameter and
`LAUNCH_ARGS` handling Browserless v2 requires — the split the project
memory records separately as `project_browserless_v1_v2_split.md`.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null
beyond the shipped-Outcome text quoted above). A future capability count
audit reconciling the 47-to-36 gap, or a decision retiring the
re-export layer in favor of direct imports, would be the natural
successor; until then the architecture (all scraping capabilities
transitively routing through `web-provider.ts`) matches the row's intent
even though the raw count has drifted.
