## Decision

Protocol integration scaling strategy: Strale becomes a node in the MCP,
A2A, and Visa TAP networks. Unit 2 (from `DEC-20260227-P-q7r8`'s
three-unit architecture) is reframed as the A2A reputation registry,
filling a gap the A2A spec explicitly leaves open. Unit 3 may become
unnecessary if commerce protocols mature.

## Context

The row's stated basis, from the row's own Rationale: A2A (led by Google
and the Linux Foundation, with 150+ member organizations) explicitly
delegates discovery, registry, and reputation to implementers rather than
building them itself; Solo.io publicly identified this as a gap. The row
positions Strale's Unit 2 to fill that gap by indexing A2A Agent Cards
ecosystem-wide and annotating them with quality scores drawn from
marketplace transaction data. Scaling is described as shifting from
marketing-driven to protocol-adoption-driven: every new A2A client would
discover Strale automatically, and every Visa TAP agent could purchase
without separate onboarding. Unit 3 (the Commerce Protocol) is described
as possibly unnecessary if A2A, Visa TAP, and Supertab mature on their
own, because the row states Strale's endgame is the reputation layer, not
another competing protocol.

The historical Notion scope field on this row was `global` in the
workspace's old vocabulary. It is recorded here as `scope: product`: this
is a company-architecture strategy decision, not a single technical
integration.

**Relation to `DEC-20260227-P-q7r8`.** This row names "Unit 2" and "Unit
3" directly, the same numbered units `q7r8`'s three-unit architecture
introduced the day before, and explicitly revises what Unit 2 is (a
reputation registry, not a generic reputation engine) and questions
whether Unit 3 is still needed; this row `amends` `q7r8`.

## Rationale

The rationale, as the row states it: A2A's own spec leaves discovery,
registry, and reputation to implementers, and no other party had filled
that gap; Strale's marketplace transaction data is the raw material for
doing so, so Unit 2 is reframed specifically as an A2A registry rather
than a generic reputation product, and the growth mechanism shifts from
marketing to automatic protocol-level discovery.

## Consequences

Status verified on 2026-09-05, against `main`.

**An MCP server and an A2A surface both exist on `main`; Visa TAP appears
nowhere.** `packages/mcp-server/` exists as its own package with a
`README.md` and `server.json`. `apps/api/src/routes/a2a.ts` exists,
alongside `a2a-card.test.ts` and other A2A-specific test files, indicating
a live A2A Agent Card surface. A case-insensitive grep of
`apps/api/src` for "visa" or "tap" as this row's specific network names
found no matches beyond unrelated strings (an "visa/work permit" domain
capability and airline codes reading "TAP Portugal" in
`flight-status.ts`); no Visa TAP integration of any kind was found.

**No "A2A reputation registry" indexing Agent Cards ecosystem-wide with
quality scores was found built.** The A2A route in `apps/api/src/routes/a2a.ts`
serves Strale's own Agent Card and capability surface; this verification
found no code path that indexes or scores third-party A2A Agent Cards
ecosystem-wide, which is what this row's reframed Unit 2 describes. The
platform's actual trust mechanism is the quality floor
(`DEC-20260812-A`'s quarantine/deactivation thresholds), which scores
Strale's own capabilities on real-traffic completion, not an
ecosystem-wide registry of other agents' reputations.

**The "Unit 3 may become unnecessary" question this row raises was
effectively resolved by later strategy in a different direction than
either outcome this row poses.** Neither "Unit 3 becomes unnecessary
because A2A/Visa TAP/Supertab matured" nor "Unit 3 was built as a
standalone Commerce Protocol" describes what happened; x402
(`apps/api/src/lib/x402-gateway.ts`) shipped as the commerce rail instead,
a specific payment protocol rather than either of this row's two
scenarios for Unit 3's fate.
