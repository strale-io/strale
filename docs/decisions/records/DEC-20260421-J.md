## Decision

Strale had not retired a capability before this row. How the Singapore (SG)
KYB drop was executed becomes the template for future capability retirement.
The pattern:

1. Soft-deactivate dependent solutions via `UPDATE solutions SET
   is_active=false` (not `DELETE`) — preserves history and avoids FK cascade
   risk.
2. Remove entries from `seed.ts` and `seed-kyb-solutions.ts` — prevents a
   fresh-DB bootstrap from re-creating retired entries.
3. Remove from `fix-lifecycle-anomalies.ts`'s ANOMALOUS list — the state is
   intentional, so stop re-flagging it every sweep.
4. Leave the capability executor file and the `auto-register` DEACTIVATED
   map entry in place — deletion adds no value and risks broken imports.
5. Regenerate distribution artifacts, e.g. `sitemap.xml`, in the same
   session as the backend retirement — dead surfaces must stop being
   crawled, and ordering matters: backend deploys first, then the sitemap
   regen pulls the post-deactivation state.
6. Keep the retirement script as a repo artifact for audit and as a template
   for future retirements.
7. Document the retirement with rationale (this row) so a future session
   finds it before re-adding the capability.

Notable side-benefit observed during the SG retirement: the sitemap regen
also caught 14 unrelated stale URLs because the previous regen predated
other capabilities being suspended. Regen-as-part-of-retirement is therefore
an implicit staleness sweep.

Out-of-scope observation recorded at adoption time: seven code files
referenced `singapore-company-data` alongside other deactivated capabilities
(`amazon-price`, `hong-kong-company-data`, `indian-company-data`) —
`seed-limitations.ts:835`, `dependency-manifest.ts:101`, `error-codes.ts:92`,
`audit-capabilities.ts:75`, `audit-tests.ts:65`,
`backfill-maintenance-class.ts:282`, `manual-test-rerun.ts:17` — evidence of
a cohort of dead capabilities left behind the same way. A cohort-cleanup
pass was flagged as cheap if handled together and tracked as a To-do at
adoption time.

## Rationale

Pattern codified and validated by the SG KYB retirement. First capability
retirement Strale has done; template for future retirements. Side benefit
validated: running the sitemap regen as part of retirement also catches
unrelated staleness — the SG regen cleaned up 14 stale-drift URLs from other
previously-suspended capabilities whose sitemap entries had been carrying
forward since an older 2026-04-16 regen. Soft-deactivation preserves audit
history, enables trivial revival, and avoids FK cascade risk. `drop-sg-kyb.ts`
was kept in the repo as the executable artifact.

## Consequences

Status verified on 2026-09-04, against `main`:

- `apps/api/scripts/archive/drop-sg-kyb.ts` exists, moved under `archive/`
  by the 2026-08-17 Phase 3 debloat sweep (commit `c4c871f6`); the retirement
  commit itself, `be0c7888`, resolves on `main`
  (`https://github.com/strale-io/strale/commit/be0c7888`). The Outcome's
  second commit, `972b860`, does not resolve as a commit object on `main` in
  this repository — it is cited in prose only; the pattern's sitemap-regen
  step (rule 5) runs in the sibling frontend repository, and this is likely
  a commit there rather than a missing artifact here.
- **Step (2) is now historical, not current.** `seed.ts` was deleted in
  PR #79; capabilities enter and leave the system through the manifest
  pipeline (`manifests/*.yaml`, `apps/api/scripts/onboard.ts`) plus the
  `auto-register.ts` DEACTIVATED map (rule 4), documented in `CLAUDE.md`'s
  "Adding New Capabilities" section. `apps/api/scripts/seed-kyb-solutions.ts`
  still exists on `main` today, so the seed-removal step for KYB solution
  bundles specifically is still live; the general capability-seed-removal
  step described in rule (2) no longer applies because there is no general
  `seed.ts` to edit. `apps/api/src/jobs/fix-lifecycle-anomalies.ts` (rule 3)
  also still exists on `main`.
- **A third lifecycle path exists that this 2026-04 pattern predates.**
  `DEC-20260812-A`'s quality floor (quarantine below 70%, deactivation
  proposal below 30%, on 10+ real calls/30d) now deactivates and quarantines
  capabilities automatically via the x402-enabled flag
  (`apps/api/src/lib/capability-promotion.ts`), with auto-promotion on
  recovery. This pattern is unchanged by the quality floor's existence: the
  quality floor is an automated, reversible enforcement mechanism, while
  this record describes a deliberate, manual, human-initiated retirement of
  a capability with no revival intent. The two do not conflict, but a
  quality-floor quarantine or deactivation is not evidence that a capability
  was retired under this pattern, and vice versa.
- **A record is never proof of production state.** `CLAUDE.md`'s
  "Predecessors that overlap the KYB families" paragraph warns that
  production contradicted a recorded deactivation on 2026-08-14; the same
  caution applies here directly and materially. `singapore-company-data`,
  the exemplar capability this record's Outcome names as the validated
  retirement case (Type 3, "un-revivable at current economics" per the
  companion row DEC-20260421-L), was in fact reactivated eight days later:
  commit `bd25bc57` ("feat(singapore-company-data): migrate Tier-1 scrape ->
  data.gov.sg ACRA API") migrated it off the banned OpenCorporates scrape
  onto the compliant `data.gov.sg` CKAN API, and `manifests/singapore-company-data.yaml`
  exists on `main` today with the capability back in production, no longer
  in the `auto-register.ts` DEACTIVATED map. The retirement pattern itself
  (steps 1-7) was executed correctly and remains a valid template; the
  specific claim that SG KYB was a permanent, un-revivable retirement did
  not hold in production. This is exactly the class of drift `CLAUDE.md`
  warns a decision record cannot detect on its own — read `is_active` /
  `x402_enabled` / the DEACTIVATED map before treating a retirement as
  current state.

## Reversal conditions

Reconsider this pattern if the manifest pipeline or the DEACTIVATED map
mechanism changes in a way that removes the anchor points steps 2-4 depend
on, or if the quality floor's automated deactivation path is extended to
also perform the seed/manifest/distribution cleanup this pattern describes,
which would fold the two lifecycle paths into one. Represent such a change
through a new decision and an explicit `supersedes` or `amends` relationship
rather than editing this protected record in place.
