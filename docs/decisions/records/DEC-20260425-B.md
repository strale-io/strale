## Decision

F-AUDIT-02 Contain phase. The three audit-trail builders in `routes/do.ts`
hardcoded `processing_location: "eu-west (Railway EU)"` while the API
service runs on Railway `us-east-4`. Every audit record since that hardcode
landed carried a factually false `processing_location` in a record
explicitly claiming EU AI Act Art. 12 / GDPR Art. 30 compliance.

This decision sets the runtime-env-var approach as the authoritative
resolution for `processing_location` in audit records:

1. Prefer `RAILWAY_REPLICA_REGION`.
2. Fall back to `STRALE_PROCESSING_REGION` for backwards compatibility.
3. Fall back to `"unknown"`, with a warning.

Contain phase only. The semantic question of what `processing_location`
should mean when processing spans multiple regions (API replica,
Browserless, LLM provider) is deferred to `DEC-20260425-A` (pending chat
session at adoption time) and the structural Harden fix ships inside R1 of
the Session F remediation plan.

Commit `d165ae2` (2026-04-21). Decision logged against the
`DEC-20260425-B` ID pre-allocated by the originating prompt; the actual
decision and ship date is 2026-04-21, four days before the `DEC-20260425-A`
row this row's own text names as the successor that resolves the deferred
semantic question.

## Consequences

Status verified on 2026-09-04, against `main`:

- `RAILWAY_REPLICA_REGION` is still the source of `processing_location`.
  `apps/api/src/lib/processing-location.ts`'s `getProcessingLocation()`
  implements exactly the three-step resolution order this row sets: prefer
  `process.env.RAILWAY_REPLICA_REGION`, fall back to
  `process.env.STRALE_PROCESSING_REGION`, fall back to `"unknown"` with a
  one-time `console.warn`. `config/env-manifest.yaml` documents
  `RAILWAY_REPLICA_REGION` as `required_in: [production, test]`, `set_in:
  [railway]`, with purpose text "used to derive the EU AI Act
  data_jurisdiction / processing-location marker," and documents
  `STRALE_PROCESSING_REGION` as "Not set in production on 2026-09-02
  (Railway audit)": the legacy fallback this row named is registered but
  currently unused in production.
- The actual `processing_location` value emitted today is a Railway region
  string (e.g. `us-east-4`), read by `apps/api/src/routes/audit.ts`'s
  `AuditRecord.processing_location` field from `profile.processing_location`
  (`apps/api/src/lib/compliance-profile.ts`), which itself calls
  `getProcessingLocation()`. This is the resolved value this row's fix
  produces, not the hardcoded `"eu-west (Railway EU)"` string the Decision
  describes as the bug being contained. The single-region approach adopted
  here (no multi-region composition) is exactly what `DEC-20260425-A`
  affirms as still correct on adoption ("processing_location keeps its
  current F-AUDIT-02 Contain behaviour"); see that record for the semantic
  question this row deferred to it.
- Commit `d165ae2` (full sha
  `d165ae2ee7902c30d117410a4f27766c8621f59f`, subject "fix: read
  processing_location from RAILWAY_REPLICA_REGION instead of hardcoded
  string (F-AUDIT-02 Contain)") resolves as a commit object on `main`
  (`https://github.com/strale-io/strale/commit/d165ae2`).

## Reversal conditions

Reconsider this decision if `RAILWAY_REPLICA_REGION` stops being Railway's
documented runtime env var for replica region, or if a hosting-provider
migration away from Railway removes the env var this resolution order
depends on. Represent such a change through a new decision and an explicit
`supersedes` or `amends` relationship rather than editing this protected
record in place.
