## Decision

Supersede the prior Gate 4 plan (run every solution end-to-end on the
scheduler, estimated ~€1,500/month) with a four-layer test pyramid. Layer A,
static solution graph validator (free): parse every `$input.X` and
`$steps[N].Y` reference, verify type compatibility and step ordering, verify
context propagation does not collide with explicit mappings; catches six of
seven identified solution-level bug classes at zero cost. Layer B, dry-run
solution execution (free): run the full step chain with mock responses to
catch runtime composition failures. Layer C, piggyback validation on real
traffic (free, always on): validate every real customer response against
declared output fields, the validation block, and latency bounds. Layer D,
scheduled real execution (paid, weekly, representative subset): run one
representative solution per category against canonical inputs, estimated
~€16/month, a 99% cost reduction against the naive plan. Rollout order:
Layer A first, Layer B second, Layer C when real traffic exists, Layer D
deferred until evidence shows a bug class that needs it. Scoring impact:
Layer A is onboarding-time with no score impact; Layers B through D feed a
new solution-level Reliability Profile factor, separate from capability-level
QP/RP scoring.

## Context

The row's own Rationale states: "Supersedes DEC-20260409-C. Original Gate 4
plan was 'run every solution end-to-end on the scheduler,' which would cost
~€1,500/month at full enablement (100 solutions × 24h cadence × avg
€0.50/run). Most solution bug classes don't actually require live execution
to catch." It enumerates seven bug classes (input mapping, step chaining,
type coercion, missing required inputs, context propagation collisions,
sequencing, and runtime composition failures), of which only the seventh
"genuinely requires live end-to-end execution." The row cites the
SpendLatch `kyb-complete-de` bug as "a class 1 bug — static, zero-cost to
detect." No record for `DEC-20260409-C` exists in this repository (it is an
unresolved collision id in `docs/decisions/id-collisions.yaml`), so no
`amends`/`supersedes` relation edge to it is recorded here.

## Rationale

The row's cost analysis is the stated rationale for the layering: static
analysis (Layer A) and mock dry-runs (Layer B) are free and catch the large
majority of bug classes; piggyback validation (Layer C) is free once real
traffic exists and gives "the strongest quality signal when it is" active;
only genuinely runtime-dependent failure modes (upstream data drift,
intermittent failures, changing regulator lists) justify the cost of Layer D,
and even then at a fraction of the naive plan's cost. The row also lists
"scoring integrity" constraints: this decision adds a new solution-level
factor and explicitly does not modify `sqs.ts`, `computeFromRows`,
`isUpstreamFailure`, `persistDualProfileScores`, matrix lookup, or capability
QP/RP computation.

## Consequences

Status verified on 2026-09-05, against `main`.

**Layer A and Layer B shipped and are named in code by this decision's own
gate numbers.** `apps/api/src/lib/onboarding-gates.ts` implements gate1
(input mapping), gate3 (schema coherence), and gate4a (step ordering / step
reference validation), together the static graph checks Layer A describes.
`apps/api/src/lib/gate4b-solution-dryrun.ts` is headed "Gate 4b — Solution
Dry-Run Composition Check (DEC-20260409-D Layer B)" and its own docstring
describes exactly Layer B: "Runs the full solution step chain with mock
outputs generated from each capability's output_schema. Catches composition
failures where step N's output doesn't satisfy step N+1's input mapping
without spending money on real API calls."

**Layer C (piggyback validation) exists as a general platform mechanism but
is not labelled to this decision.** `test-runner.ts` and the scheduler
exclude `test_type = 'piggyback'` suites from scheduled runs and populate
them from real traffic via `recordPiggybackResult()` (CLAUDE.md Test
Infrastructure Cost Principle C), which satisfies the row's Layer C
description in substance, but no file in the repository cites
`DEC-20260409-D` for this piece.

**Layer D was never built.** `apps/api/src/jobs/test-scheduler.ts` runs a
`weekly-sweep` task on a 7-day interval, but its own code comment identifies
it as a health probe, not a solution-execution layer: "Weekly health sweep
(7d)" dispatching to `runWeeklyHealthSweep()` in `../lib/health-sweep.js`, a
URL/dependency health check, not "one representative solution per category
against canonical test inputs" as the row specifies. No scheduled job in the
repository runs a representative-solution weekly execution. A separate
comment in the same file, "Daily SQS snapshot retired with the SQS engine
(DEC-20260503-B)," confirms the solution-level Reliability Profile factor
this decision proposed to feed was itself downstream of the SQS engine that
`DEC-20260503-B` later deleted, so even if Layer D had shipped, its scoring
destination no longer exists.

**Gate 5 is a separate, later decision, not part of this pyramid.**
`apps/api/src/lib/gate5-path-coverage.ts` is headed "Gate 5 — Path Coverage
Enforcement (DEC-20260411-B)," a different decision from this one, despite
the adjacent gate number.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null). The
row's own rollout order defers Layer D "until there's evidence of a bug
class that needs it"; that evidence has not been produced in this
repository, so Layer D's absence is consistent with the row's own deferral
condition rather than a dropped commitment.
