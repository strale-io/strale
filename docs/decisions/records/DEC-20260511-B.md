## Decision

Decouple `scheduled_testing_eligible` from `external_cost_cents` (PR A):
deliver the schema, the dispatch swap, and a derivation bridge (startup
block 0066) that re-derives eligibility from cost at every boot. PR B (a
separate, later change) forces explicit `scheduledTestingEligible`
declarations at all INSERT sites and removes block 0066.

## Context

The row's own Rationale states the trigger and the design choice: "The May
2026 Haiku token spike (PRs #84/#85/#86/#87) was structurally possible
because external_cost_cents = 0 did double duty as billing data and
scheduling signal — a compound-PR pattern (cadence flip + deferred
cost-bump) silently turned billing-data lag into a scheduling regression for
73 LLM capabilities for 7 days. Decoupling these concerns removes that class
of failure. The PR A / PR B split keeps each diff reviewable... Refines
DEC-20260503-B (source_health doctrine) without superseding." The row
explicitly states it refines `DEC-20260503-B` and changes the derivation
mechanism behind that decision's "hourly, free-only" schedule rule (that
rule was, per CLAUDE.md, keyed on `external_cost_cents = 0` alone before
this row); `amends DEC-20260503-B` is recorded on that basis, consistent
with the row's own explicit disclaimer that it does not supersede it.

## Rationale

As the row states it: the compound-PR pattern that caused the incident
(cadence flip plus a deferred cost bump) is prevented by decoupling
scheduling eligibility from billing cost entirely. The PR A / PR B split
keeps each diff reviewable: PR A ships schema, dispatch, and a temporary
cost-derived bridge (block 0066); PR B later forces every INSERT site to
declare eligibility explicitly and removes the bridge.

## Consequences

Status verified on 2026-09-05, against `main`.

**PR A's Phase B rollout is reported complete on the row itself.** The
row's own `Outcome` field states: "Phase B complete 2026-05-12 via PRs
#98-102. 287 caps classified. STRICT-mode active (COST_CLASS_MODE=STRICT
Railway 16:02 UTC). Boot invariant unclassified_count=0. First
cost-class-invariant-pass log line in fleet history."

**PR B did not remove block 0066; instead, block 0066 and a later block
0069 now partition the table, and CLAUDE.md's boot-time-derivation warning
is still true, but only for a shrinking subset of rows.** Reading
`apps/api/src/lib/startup-migrations.ts` directly: block 0066
("`runMigration0066_ensureEligibilityColumnAndReconcile`") still runs on
every boot and its own comment states its current, narrowed scope: "The
rows block 0066 owns: suites whose capability carries no `cost_class`...
Blocks 0066 and 0069 derived the SAME column from two different sources —
0066 from `test_suites.external_cost_cents`, 0069 from
`capabilities.cost_class` — and both ran on every boot, in that order. For
any suite where the two disagreed, each boot flipped the flag twice... Both
halves are fixed here: the two blocks now partition the table (0069 owns
classified capabilities, 0066 owns the rest)." The block's own reconciling
UPDATE reads: `UPDATE test_suites ts SET scheduled_testing_eligible =
(ts.external_cost_cents = 0) WHERE <suite's capability has no cost_class>
AND ts.scheduled_testing_eligible IS DISTINCT FROM
(ts.external_cost_cents = 0)`. So CLAUDE.md's statement, "A startup
migration rewrites the flag on every boot: `SET scheduled_testing_eligible =
(external_cost_cents = 0)`... hand-editing `scheduled_testing_eligible` is
silently reverted at the next deploy," is still literally true today, but
only for capabilities that have never been assigned a `cost_class`; every
classified capability is instead governed by block 0069's `cost_class`-keyed
derivation, which is the decoupled mechanism this row asked for. This is the
largest contradiction in this batch: the row's own text frames PR A/B as a
full decoupling, but the boot-time cost-derivation bridge PR A introduced
was never fully removed; it was scoped down to unclassified capabilities
rather than deleted, per a later incident (2026-08-21, per block 0066's own
comment) that found the original unscoped overlap silently corrupting
fixture-baseline `updated_at` timestamps.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` fields other than
the Phase B completion note above are null). Block 0066's own header states
PR B's originally intended full removal of the reconciliation UPDATE did not
happen as planned: "PR B will force explicit `scheduledTestingEligible`
declarations at the 12 INSERT call sites and remove the reconciliation
UPDATE; whether the ADD COLUMN portion stays here or moves to a dedicated
block is a PR B design choice." The block that exists today keeps the
UPDATE, scoped to unclassified capabilities only.
