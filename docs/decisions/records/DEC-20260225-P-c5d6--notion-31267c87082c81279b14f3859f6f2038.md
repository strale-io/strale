## Decision

Add a `failed_requests` table to the MVP schema. Log every
`no_matching_capability` response, capturing `task`, `category`,
`max_price_cents`, and `user_id`. The table turns unmet demand into
provider-recruitment data for Phase 2.

## Context

The row's stated basis, from its own Rationale: a Gemini review
suggested an "Unmet Demand Ledger" concept, logging failed requests as a
live signal of what the agent economy needs built. The row estimates one
hour of implementation cost (one table, one INSERT on the failure path)
and describes the future recruitment pitch directly: "Here are 47
requests for Finnish company data this month at avg €1.20 budget. Build
it and capture the revenue." It also notes the data would feed future
content marketing (aggregate demand data).

This historical ID is reused by a second, unrelated Notion row (a GTM
strategy decision made the same day) and was an unresolved registry
collision until this batch; the two rows are resolved together in
`archive/sessions/2026-09-05-decision-collision-resolution-DEC-20260225-P-c5d6.md`
with distinct source-qualified record keys. This record covers only the
failed_requests table row.

## Rationale

The rationale, as the row states it: logging failures is cheap (one
table, one INSERT) and converts a cost center (unmatched demand) into an
asset, a concrete, quotable recruitment signal for the Phase 2 provider
marketplace, and raw material for demand-driven content marketing.

## Consequences

Status verified on 2026-09-05, against `main`.

**The table exists substantially as specified, with more columns than
the row named.** `apps/api/src/db/schema.ts` defines `failedRequests`
(table name `failed_requests`) with `id`, `userId` (nullable, references
`users.id`), `ipHash`, `task`, `category`, `maxPriceCents`,
`failureType` (default `"no_match"`), `errorDetail`, `userAgent`, and
`createdAt`. The four fields the row named explicitly (`task`,
`category`, `max_price_cents`, `user_id`) are all present; `id` and
`created_at` (also named) are present too. `ipHash`, `failureType`,
`errorDetail`, and `userAgent` are additions beyond the row's four named
fields, not contradictions of them, `userId` is nullable specifically
"to capture unauthenticated free-tier failures," per the schema's own
comment, which the row's original text did not anticipate.

**The write path is live.** `apps/api/src/routes/do.ts` inserts into
`failedRequests` at four call sites (failure branches of the request
path), consistent with the row's "one INSERT on the failure path"
framing, expanded to cover more than one failure branch.

CLAUDE.md's MVP Decisions list still carries this row verbatim as
"DEC-20260225-P-c5d6: 6th table, failed_requests (id, user_id, task,
category, max_price_cents, created_at) logs every no_matching_capability
response," confirming continuity between the historical decision and the
schema comment `// ─── failed_requests (DEC-20260225-P-c5d6) ───` in
`apps/api/src/db/schema.ts`.

This verification did not confirm whether the recruitment-pitch use case
(quoting aggregated demand to prospective providers) or the
content-marketing use case the row anticipated have ever been executed;
only the logging mechanism itself was checked.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null in
the source). A future decision removing the `failed_requests` table, or
replacing it with a differently-shaped demand-signal mechanism, would
supersede this row.
