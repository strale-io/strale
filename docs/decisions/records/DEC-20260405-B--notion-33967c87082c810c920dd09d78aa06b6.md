## Decision

Store solution executions using Variant A1: a nullable `capability_id` +
`solution_slug` pair on the transactions table, with an XOR constraint
between them, rather than parent/child rows or a parallel table.

## Context

The row's stated basis, from its own Rationale: Variant A1 was chosen
over parent/child rows or a parallel table because solution steps do
not write their own transaction rows, and it matched `/v1/do`'s
two-phase write pattern and status vocabulary exactly. `audit_trail` was
constructed inline with a TODO for future helper extraction. Migration
0043 was applied via raw SQL in a transaction, bypassing drizzle-kit,
because the tooling state (an empty tracking table, a journal missing 36
entries) was broken in a way that required a separate reconciliation
session to fix properly. The row records verification via a production
smoke test: two-tier response shape, a transaction row with correct
fields, `audit_trail` per-step breakdown, wallet debit + refund, balance
math reconciled, XOR constraint functional tests passed. The row's
Outcome: Phase 1 complete, infrastructure PASS on smoke test; execution
failed due to a pre-existing `swedish-company-data` upstream reliability
issue (a Browserless timeout scraping Allabolag.se, SQS 46), a separate
workstream via the Bolagsverket API migration, not a Phase 1.4
regression.

This historical ID is reused by a second, unrelated Notion row
(deactivating `credit-report-summary`, dated seventeen days later
despite sharing the ID) and was an unresolved registry collision until
this batch; the two rows are resolved together in
`archive/sessions/2026-09-05-decision-collision-resolution-DEC-20260405-B.md`
with distinct source-qualified record keys. This record covers only the

This row is named by a different collision's row in this same batch:

step structure). See Relations on that record.

## Rationale

The rationale, as the row states it: a nullable-pair-plus-XOR shape on
the existing `transactions` table reuses the table's established
two-phase write pattern and status vocabulary, avoiding a new
parent/child schema or parallel table when solution steps do not
themselves need transaction rows.

## Consequences

Status verified on 2026-09-05, against `main`.

**The nullable capability_id/solution_slug pair exists on the
transactions table exactly as described, not as a separate table.**
`apps/api/src/db/schema.ts` defines `transactions.capabilityId` as
nullable "solution executions have no single capability" and
`transactions.solutionSlug` as `text("solution_slug")` with the comment
"set for solution executions, null for capability executions." No
`solution_executions`, `solution_run`, or `parent_transaction` table
exists in `schema.ts`; a grep for those three names finds none. This
confirms Variant A1 (one table, nullable pair) rather than the rejected
parent/child or parallel-table alternatives.

**A later migration block's own comment independently confirms the
shape in production.** `apps/api/src/lib/startup-migrations.ts`'s block
0101 comment states: "A solution execution writes one transaction with
`capability_id = NULL` and its step outcomes inside an `output.steps`
JSONB blob... Verified against production: 694 solution rows, all with a
null `capability_id`, and 126 sub-calls in the trailing 30 days recorded
nowhere else." That block was written for a different purpose (giving
per-capability invocations inside bundles their own visibility for the
quality floor), but its verified production figures corroborate this
row's storage model as still in effect, well after this row's decision
date.

This record did not independently locate a database-level `CHECK`
constraint enforcing the row's stated XOR between `capability_id` and
`solution_slug` in `schema.ts` or `startup-migrations.ts`; if the
constraint exists, it is enforced at the application layer rather than
as a named SQL constraint this batch could grep for.

## Reversal conditions

None recorded on the row (`Superseded By` is null in the source). A
