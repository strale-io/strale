## Decision

Only successful executions are billed; failures caused by upstream
(external) services are never charged to the customer.

## Context

The row's stated basis, from its own Rationale: "Agents should not pay
for failures caused by external services. This is a trust signal aligned
with Strale's brand: 'we don't charge you for problems we didn't cause.'
Worst-case cost for vat-validate retry path = €0.12 (one success + fallback),
not €0.32 (3 retries). Reduces agent cost anxiety and encourages retry
strategies."

The historical Notion scope field on this row was `global`. It is
recorded here as `scope: technical`: it specifies a billing mechanism
inside the execution path, not a company-wide strategic decision. The
row's own text does not name any other Decision ID, so no relation edge
is recorded here.

## Rationale

The rationale, as the row states it: charging for failures the customer
did not cause damages trust and discourages the retry behavior the
platform wants agents to use; the stated cost math (€0.12 vs €0.32 on a
three-retry vat-validate path) is the concrete case used to justify it.

## Consequences

Status verified on 2026-09-05, against `main`.

**The sync path today implements exactly this rule, and CLAUDE.md names
it as DEC-14.** `apps/api/src/routes/do.ts` contains a function
`executeSync`, under the header comment "Sync execution: lock → execute
→ debit on success (DEC-14)." The same file's x402 settlement helper
`settleReceiptFor` carries the comment "the settle step runs only after
the capability has produced output (DEC-14)"; inside `executeSync`'s own
transaction the debit is written after the executor returns, and on failure "the catch block treats that as
`execution_failed` and refunds nothing (no debit committed)": no
charge is ever placed for a failed execution to begin with, on the sync
path. CLAUDE.md's own Active Decisions list records DEC-14 as "Don't
charge before execution succeeds — lock → execute → deduct on success"
confirming this is the same rule the row is asking for, filed under a
different id (DEC-14 predates this row by three weeks).

**The async path debits upfront and refunds on failure, a different
mechanism reaching the same customer-facing outcome.**
`apps/api/src/routes/do.ts` labels this path "Async execution: debit
upfront → 202 → background → refund on failure" with comments
describing the refund-on-failure handling ("Failure: refund wallet +
update transaction in a single tx"). The net effect for the customer is
the same as the sync rule (no charge survives a failed execution), but
the money moves in the opposite order (debit-then-refund rather than
never-debit), because the async path cannot know at request time
whether execution will succeed.

**x402 follows the same verify-execute-settle ordering, not a different
one.** `apps/api/src/lib/x402-gateway.ts` states directly: "WP4 removed `verifyX402Payment`, a combined
verify-and-settle helper" and keeps the "verify → execute → settle
ordering (DEC-14); both callers below are unchanged,"
and refers to a dedicated pinning test,
`x402-gateway-v2.settlement-order.test.ts`. Settlement (the on-chain USDC
transfer) happens only after execution succeeds, via a separate
`settleX402Payment` call following a prior `verifyX402PaymentOnly`; a
comment on the file states the module "removed `verifyX402Payment`, a
combined verify-and-settle helper" specifically to prevent
charge-before-execute from being reintroduced by a single convenient
function. So x402 does not differ from the wallet path in principle: no
settlement occurs before execution succeeds, on either payment rail.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null).
DEC-14 (predating this row, and named directly in the current code
comments) is the platform's standing name for the rule this row states
independently; both remain the same live behavior today under three
different execution paths (sync, async, x402).
