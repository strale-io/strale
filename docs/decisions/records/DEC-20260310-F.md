## Decision

Expand the data completeness rule so every capability must have: (1)
limitations with titles and workarounds, (2) test suites with
structurally valid validation rules (fields must exist in all output
paths, test types must match intent), and (3) all required metadata.
`audit-tests.ts` runs as a periodic diagnostic; seed validation runs as a
preventive gate.

## Context

The row's stated basis, from its own Rationale is the rule statement
itself: it names the three requirements and the two enforcement points
(a periodic diagnostic script and a preventive seed-time validation
gate).

The historical Notion scope field on this row was `global`. It is
recorded here as `scope: technical`: it specifies validation rules and
enforcement mechanisms for capability onboarding, not a company-wide
strategic or positioning decision.

## Rationale

The rationale, as the row states it (implicit in the rule's own text):
structurally invalid test validation rules (fields that don't exist in
all output paths, test types that don't match their stated intent) are a
silent-failure class distinct from a capability simply lacking a test;
catching them requires validating the test design itself, not only
running the tests.

## Consequences

Status verified on 2026-09-05, against `main`.

**The three completeness requirements this row named survive today, as
part of the canonical onboarding pipeline, though not necessarily through
the exact `audit-tests.ts` diagnostic this row names.** CLAUDE.md's
"Adding New Capabilities" section requires a manifest with `limitations`
("at least 1 (every capability has limitations)"), requires the pipeline
(`apps/api/scripts/onboard.ts`) to generate all five test types, and
lists field-reliability rules (`guaranteed`/`common`/`rare`) governing
which fields get `not_null` assertions — directly matching this row's
requirement that "fields must exist in all output paths" before being
asserted on. This is the same underlying discipline the row calls
"structurally valid validation rules."

**No `docs/decisions/records/DEC-20260305-*.md` or
`DEC-20260306-*.md` record was found naming a "data completeness rule"
by that phrase**, so per this batch's brief instruction, no `amends`
relation is created from this row to an earlier data-completeness
decision; the phrase "expanded" in this row's title cannot be resolved
to a formal predecessor record on the current PR head, and stands as

**`onboard.ts` is the canonical pipeline**, per CLAUDE.md: "the pipeline
generates all 5 test types... and verifies the known_answer test passes
against live output," which functions as the preventive gate this row

independently confirmed to still exist as a separate periodic diagnostic
distinct from the onboarding pipeline; this record does not assert either
way beyond noting `onboard.ts`'s confirmed role.
