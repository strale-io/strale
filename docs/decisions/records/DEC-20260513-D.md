## Decision

Acknowledge that `danish-company-data`'s circuit breaker auto-recovered
without operator action; supersede the `DEC-20260506-D` manual 30-day pin.

## Context

The row's own Rationale states the finding: "DEC-20260506-D pinned the DK
CVR circuit breaker manually for 30 days pending Danish registry keeper
response on rate-limit issue. The 2026-05-13 SK rate-limit diagnostic
session incidentally observed that capability_health.state for
danish-company-data is now closed (auto-recovered between 2026-05-06 and
2026-05-11; precise auto-recovery timestamp not preserved). CVR upstream
quota cleared without operator action, half-open probe succeeded, breaker
closed. No follow-up from the Danish registry keeper was required.
DEC-20260506-D superseded — DK is back to live. Pending: the planned
follow-up email to the registry keeper is now moot." The row's own text
states "supersede DEC-20260506-D manual pin" directly; `DEC-20260506-D` is a
superseded row with no formal record in this repository (verified: no
record exists for it), so this supersession is recorded in prose only, not
as a graph edge. `Source` is null on the row.

## Rationale

As the row states it: the finding was incidental, surfaced while
investigating an unrelated Slovak rate-limit issue on the same day; the CVR
upstream quota cleared on its own between 2026-05-06 and 2026-05-11, the
breaker's own half-open probe succeeded, and no operator or registry-keeper
action was required.

## Consequences

Status verified on 2026-09-05, against `main`.

**No dedicated "manual pin" mechanism or "auto-recovery" flag exists in the
schema; both the pin and its release are the same `state` transition
`capability_health` already models.** As found for `DEC-20260513-B` in this
same batch, `apps/api/src/db/schema.ts`'s `capability_health` table has only
a `state` column (`'closed' | 'open' | 'half_open'`), with no distinct
column recording whether a `closed` state was reached by an automatic
half-open probe succeeding or by a manual admin reset
(`POST /v1/admin/reset-circuit-breaker`). This record cannot verify, from
schema state alone, whether `danish-company-data`'s breaker is closed today
because of the auto-recovery this row describes, a later manual reset, or a
later re-opening and re-recovery; no `opened_at`/`last_success_at` history
beyond the current row is retained per capability.

**`danish-company-data` is independently named in this batch's
`test-scheduler.ts` evidence as the subject of a duplicate-suite execution
bug, unrelated to this row's own topic.** `findOverdueSuites`'s comment (see
`DEC-20260513-C`'s record) states: "danish-company-data's 4 duplicate
known_answer suites — produced 4 identical (slug, testType) rows here...
a batch of N due suites did N x N executions, not N." This is reported here
because it names the same capability this row discusses, not because this
row's own text mentions it.

**The manifest for `danish-company-data` today documents a `mixed`
transparency tag and a data-freshness limitation, not a rate-limit
limitation.** `manifests/danish-company-data.yaml` states: "Financial data
from annual reports — can be up to 12 months old," with
`data_source: CVR / Danish Business Authority (Erhvervsstyrelsen)` and
`transparency_tag: mixed`; this record found no limitation entry in the
current manifest naming the CVR rate-limit issue this row and
`DEC-20260506-D` describe.
