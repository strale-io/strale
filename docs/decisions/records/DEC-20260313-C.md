## Decision

Show an "Unverified" SQS state on a capability's card while keeping the
capability listed, rather than hiding it or removing it from the catalog.

## Context

"Unverified" is distinct from "Building track record" (tests exist but not
enough runs have accumulated yet): "Unverified" means the capability is
structurally unable to be tested at all (for example, a paid capability
with no zero-cost health probe available). The historical Notion scope
field on this row was `global`. It is recorded here as `scope: product`
under this repository's decision-record vocabulary: this decision governs
what a customer sees on the catalog for a capability the platform cannot
score, a product/trust-display concern.

## Rationale

Three reasons given: honesty (claiming a quality signal the platform does
not actually have would be worse than admitting the absence of one); market
incentive (a visible "Unverified" state gives Phase 2 third-party providers
a reason to enable testability rather than staying opaque); and no removal
of working functionality (a capability that works but cannot be
proactively tested should not disappear from the catalog merely because it
cannot be scored).

## Consequences

Status verified on 2026-09-04, against `main`.

**The reason a capability goes untested changed shape, but the underlying
principle — list it anyway — survives in the current test-scheduling
rule.** CLAUDE.md states the current mechanism: "Paid capabilities are not
proactively tested; quality signals come from production observability,
piggyback test suites, and any zero-cost auth-less probes the vendor
permits," driven by `test_suites.scheduled_testing_eligible`, which a
startup migration rewrites from `external_cost_cents = 0` on every boot.
This is a different mechanism than this row's 2026-03-13 framing (SQS-era
"structurally can't test" vs. today's cost-driven scheduling filter), but
the practical outcome this row wanted holds only on the API side:
`scheduled_testing_eligible` gates proactive test scheduling, not catalog
listing or `is_active`, so an untestable capability stays in the API
catalog. It does not hold on the website: the header comment of
`apps/api/src/routes/capabilities.integration.test.ts` records that the
frontend's `isSQSUnqualified` filter hides capabilities labelled
"Unverified", the opposite of what this row decided (status on
2026-09-04; the frontend repository is outside this record's evidence).

**No literal "Unverified" SQS label exists in the code today; a narrower
boolean field carries the same information.** A case-sensitive and
case-insensitive repository search for "Unverified" as an SQS-state string
across `apps/api/src` finds no match tied to a trust/quality display path.
`apps/api/src/routes/public-trust.ts` instead exposes `tested: boolean`
alongside `pass_rate: number | null` on every capability and solution, so
an untested capability is represented as `tested: false` with a null pass
rate rather than as a labeled "Unverified" grade — the same "still listed,
signal absent rather than faked" principle this row states, expressed as a
plain boolean instead of an SQS-specific label. The route's own comment
states the badge "asserts... that Strale runs its own tests against this
capability — not that the capability is currently healthy," which is this
row's honesty rationale in different words.

**The SQS engine this row's label named was deleted.** Per DEC-20260503-B
(PR1 shipped 2026-05-05; CLAUDE.md), the SQS engine, `min_sqs`, and the
public `/v1/quality/:slug` endpoint no longer exist, so there is no SQS
score for a capability to be "Unverified" on in the first place.

## Reversal conditions

Reconsider this decision if a future catalog change begins hiding or
delisting untestable-but-working capabilities from public listings; that
would directly reverse the "still listed" principle this row establishes.
Represent such a change through a new decision rather than editing this
protected record in place.
