## Decision

Fix a defect where the solution executor wrote `totalLatencyMs` but not
per-step `latencyMs` into the audit trail, even though `DEC-20260405-B`
specified per-step latency as required.

## Context

The row's stated basis, from its own Rationale:
`DEC-20260405-B` explicitly specified per-step `latencyMs` as required.
The implementation at the time wrote `totalLatencyMs` but not per-step.
The fix was cheap (roughly a 15-line Sonnet session using the same
timing primitive already in use), unblocked tighter Prompt B assertions,
and closed the one divergence the Phase 1 audit found. Deferral was
rejected because no broader observability workstream was planned until
customer volume justified one. The row's Outcome: shipped in commit
`5b1c2e1` (3 files changed, 16 insertions, 2 deletions).
`solution-executor.ts` wraps each step with `Date.now()` timing on both
success and failure branches and pushes `{capabilitySlug, latencyMs}` to
a `stepTimings` array returned in `SolutionExecutionResult`.
`solution-execute.ts` maps these timings into
`audit_trail.steps[i].latencyMs`. `solution-execution-smoke.mts`'s
assertion was tightened from "number or null" back to "> 0" on every
step entry. The row's design note: collecting timings in a separate
array at the executor level, rather than mutating `audit_trail` inline,
keeps the executor's measuring concern separate from the endpoint's
audit-writing concern, simplifying the eventual `buildFullSolutionAudit()`
helper extraction when the shape stabilizes.

This historical ID is reused by a second, unrelated Notion row
(consolidating working rules for Claude/CC/Notion governance, made the
same day) and was an unresolved registry collision until this batch;
the two rows are resolved together in
`archive/sessions/2026-09-05-decision-collision-resolution-DEC-20260406-A.md`
with distinct source-qualified record keys. This record covers only the
per-step-latency fix row.

**Relation to `DEC-20260405-B--notion-33967c87082c810c920dd09d78aa06b6`:**
