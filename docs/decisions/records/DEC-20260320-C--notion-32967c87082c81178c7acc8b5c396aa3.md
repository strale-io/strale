## Decision

Fix auto-register so it filters out `.d.ts` declaration files (a file
whose name without extension ends in `.d`) rather than attempting to
import them as executors, and add a startup health gate: the server
refuses to start (`process.exit(1)` with a FATAL log) if fewer than 200
executors register.

## Context

The row's stated basis, from its own Rationale: a production incident.
`auto-register.ts` scanned `dist/capabilities/` and found both `.js`
executor files and `.d.ts` declaration files. It tried to import the
`.d.ts` files as executors; all 264 imports failed, leaving 0 executors
registered. All `/v1/do` calls returned 503. The website appeared normal
because it reads from the DB, not the executor registry. The alert
system correctly detected the mass failure and emailed, but classified
it as "unknown" since "no executor" was not a recognized failure
pattern; self-healing could not remediate because the failure sits below
the layer it monitors. Root cause: the file filter in auto-register
excluded `index.ts` and `auto-register.ts` but not `.d.ts` files.

This historical ID is reused by a second, unrelated Notion row (the
au-company-data ABR onboarding, made the same day) and was an unresolved
registry collision until this batch; the two rows are resolved together
in
`archive/sessions/2026-09-05-decision-collision-resolution-DEC-20260320-C.md`
with distinct source-qualified record keys. This record covers only the
auto-register hotfix row.

## Rationale

The rationale, as the row states it: filtering `.d.ts` files fixes the
immediate incident; the startup health gate is a structural prevention
so a future variant of this failure (any cause reducing the registered
executor count) crashes the server loudly at boot rather than serving
503s silently in production.

## Consequences

Status verified on 2026-09-05, against `main`, and this row's mechanism
has since been replaced, not merely patched.

**Neither the `.d.ts` filter nor the `MIN_EXPECTED_EXECUTORS` startup
health gate exists in `auto-register.ts` today.** The file's own header
comment states why: "The previous filesystem-glob discovery pulled in
test files (`.test.ts`) and any unrelated `.ts` file, producing spurious
errors and masking real failures. Manifest is the source of truth —
matching validate-capability, onboard, and smoke-test." The current
`autoRegisterCapabilities()` reads `manifests/*.yaml`, extracts each
declared `slug`, and dynamic-imports `./<slug>.js` directly — there is
no directory scan of `dist/capabilities/` for the function to
misclassify a `.d.ts` file against, so the specific defect this row
fixed cannot recur under the current architecture. There is also no
`process.exit(1)` FATAL startup gate keyed on an expected executor
count anywhere in the file: distinct, labelled log outcomes
(`auto-register-executor-file-missing`, `auto-register-import-failed`,
`auto-register-no-executor-after-import`) replace it, incrementing an
`errors` counter that is logged but does not halt startup.

This is not a reversal of the row's Decision text, which is kept above
exactly as recorded; it is a later architectural replacement (manifest-
driven registration superseding filesystem-glob discovery) that made
this row's specific fix and its startup gate moot rather than wrong.
Neither the superseding change's decision ID nor date is named in this
repository's decision records, so no supersession relation is recorded
here.
