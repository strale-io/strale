## Decision

Correct a divergence between the shipped code and the Cluster 2 design
doc: C1 (commit `8f6eff9`) placed the `onCapabilityCreated` hook inside
`db.transaction`, per the prompt's literal instructions, diverging from
design doc §4.3, which specifies firing the hook outside the transaction.
The row's own three reasons for outside-tx: the hook can make "30s+
external calls," holding a Postgres connection/row lock that long risks
pool pressure; if the hook succeeds but the commit itself fails, the hook
fires without the row persisting; and hook-failure semantics stay
unchanged via a separate short `UPDATE` setting
`lifecycle_state='hook_failed'` after the main transaction commits. The
correction was bundled into C2 (commit `a070ba0`) rather than shipped
standalone.

## Rationale

The rationale, as the row states it: correctness (a hook firing on a row
that never committed is a bug the outside-tx design closes) and
performance (holding a DB connection open through a 30s+ external call is a
pool-pressure risk under concurrent onboarding load), both already
identified in the design doc and only corrected here after C1's literal
prompt-following diverged from it.

## Consequences

Status verified on 2026-09-05, against `main`.

**The corrected placement is present in the codebase today.**
`apps/api/src/lib/capability-persistence.ts` states directly: "OUTSIDE the
transaction. Design doc §4.3 — `onCapabilityCreated` can" [make 30s+
