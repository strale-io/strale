## Decision

Stripe's x402 deposit mode is US-only, so Strale uses the open x402
protocol with the Coinbase CDP facilitator instead. Do not pursue a US
entity via Stripe Atlas at this stage.

## Context

The historical Notion scope field on this row was `global`. It is recorded
here as `scope: technical` under this repository's decision-record
vocabulary: this decision picks the payment rail and settlement mechanism
for x402, an infrastructure choice.

## Rationale

Ben Berke (Stripe Crypto, Chicago) confirmed that Stripe's x402 deposit mode
and crypto payment methods are only available for US-based Stripe accounts.
Strale's account (`acct_1T6JQKFVB83qVk59`) is registered in Sweden and
cannot be enabled. Stripe suggested creating a US entity via Atlas ($500,
weeks of setup). This was rejected as unnecessary because: (1) Strale's
x402 use case is API micropayments, not consumer checkout — the open x402
protocol with the Coinbase CDP facilitator is the correct path; (2) the
entire x402 ecosystem (Firecrawl, Hyperbolic, Neynar, etc.) uses the open
protocol, not Stripe's managed version; (3) Stripe's managed x402 is
designed for merchants already on Stripe checkout, not API-first
platforms; (4) pursuing Atlas would consume time and money with no
immediate benefit. The open protocol has zero geographic restrictions. The
relationship with Stripe's machine-payments team was maintained for future
optionality.

## Consequences

Status verified on 2026-09-04, against `main`.

**The rail this row chose is what production runs today.**
`apps/api/src/lib/x402-gateway.ts` imports `createFacilitatorConfig` from
`@coinbase/x402` and documents an explicit `X402_FACILITATOR` selection
switch (`auto` / `cdp` / `legacy`) whose `auto` default routes to the
Coinbase CDP facilitator on Base mainnet when CDP keys are present,
falling back to the legacy HTTP facilitator otherwise; `cdp` mode "always"
uses Coinbase's CDP facilitator and refuses to start without
`CDP_API_KEY_ID` + `CDP_API_KEY_SECRET`. `config/env-manifest.yaml`
documents both `CDP_API_KEY_ID` ("Coinbase Developer Platform API key ID
for the x402 CDP facilitator (verify/settle USDC payments on Base)") and
`CDP_API_KEY_SECRET`, plus `X402_FACILITATOR_URL` as the legacy fallback
read indirectly through `resolveFacilitatorSelection`. CLAUDE.md's "x402
Payment Gateway (March 2026)" paragraph confirms settlement is USDC
payments on Base mainnet and that the rail is DB-driven (adding a
capability to x402 needs only `UPDATE capabilities SET x402_enabled =
true`). No Stripe Atlas US entity exists; the open-protocol path this row
chose was not reversed.

**Choosing the Coinbase CDP facilitator over Stripe's US-only mode carried
a real, later, cost: a 21-hour revenue outage on 2026-08-14.**
`handoff/_general/from-code/2026-08-14-settlement-outage-and-monitoring.md`
records that Coinbase's CDP x402 facilitator allows 1,000 settlements per
calendar month free, then refuses (a paid tier exists at roughly
$0.001/settlement after the free tier), and Strale crossed that threshold
mid-month, producing a 21-hour, nobody's-fault revenue outage before the
defects it exposed were fixed. This is a consequence of the rail this row
selected, not a reason to reverse it: the same handoff frames it as a
capacity-planning gap in an otherwise-correct choice, not a facilitator
failure.

## Reversal conditions

Reconsider this decision if Stripe's x402 deposit mode becomes available
for non-US accounts, if a US entity becomes necessary for unrelated reasons
that would also unblock Stripe's managed mode, or if the Coinbase CDP
facilitator's free-tier or pricing terms make the open-protocol path
materially worse than the Stripe alternative. Represent a change of this
decision through a new decision rather than editing this protected record
in place.
