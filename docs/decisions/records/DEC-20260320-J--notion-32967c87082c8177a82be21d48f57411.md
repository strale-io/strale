## Decision

Methodology text (capability counts, solution counts, and test suite
counts) must never be hardcoded. It must always query live data at
runtime.

## Context

The row's stated basis, from its own Rationale: an evaluation found the
methodology text said ~1,348 tests but the actual count was ~1,500, and
MCP tool descriptions said 229 capabilities but the actual count was
256. Hardcoded values drift every time capabilities are added, and the
row states this class of bug will recur forever unless the architecture
changes. The row's Outcome: the methodology tool and MCP descriptions
should query live counts at runtime, with a meta-monitor to detect
drift.

This historical ID is reused by a second, unrelated Notion row
(pep-check's transparency tag, made the same day) and was an unresolved
registry collision until this batch; the two rows are resolved together
in
`archive/sessions/2026-09-05-decision-collision-resolution-DEC-20260320-J.md`
with distinct source-qualified record keys. This record covers only the
dynamic-methodology-counts row.

The historical Notion scope field on this row was `global`. It is
recorded here as `scope: product`: it is a content-accuracy rule for a
public-facing page and public tool descriptions, not a technical
implementation choice by itself.

## Rationale

The rationale, as the row states it: hardcoded counts drift on every
capability or solution addition, and drift in public-facing quality
claims is itself a trust problem for a platform whose product is
verified data.

## Consequences

Status verified on 2026-09-05, against `main`.

**A live-data architecture for these facts exists and its own header
comment names the free-tier list as a further drift instance, beyond
the two the row named.** `apps/api/src/lib/platform-facts.ts`'s module
header documents a "Drift problem (cert audit 2026-04-30)" with several
bullets, including this one verbatim: "free-tier list: 5 in marketing,
11 in manifests, 5 different in production." That bullet is separate
from the row's own two named drift instances (test count, capability
count) but confirms the same class of defect recurred at least once
more, on a different fact, before this architecture existed. The module
computes `capability_counts` and `solution_count_active` from the
database rather than a constant, per its own "Architecture" section:
"Live values (capability counts, country counts, free-tier slugs) are
computed from the DB on demand and cached at the route layer."

**The current frontend Methodology page does not display capability,
solution, or test-suite counts at all**, at
`strale-io/strale-frontend@04c9fca9:src/pages/Methodology.tsx`: it calls
`usePlatformFacts()` but only reads `facts?.static.vendors.sanctions`
(for the vendor-name drift class named in a separate, later cert-audit
finding), not any capability/solution/test count. This record cannot
confirm whether that reflects the row's Outcome being implemented and
later the counts being removed from this particular page, or whether
they were never added to it; either way, the specific stale-count defect
the row named (methodology text showing ~1,348 vs ~1,500 tests, or 229
vs 256 capabilities) cannot recur on this page today because the page
does not show those figures.

## Reversal conditions

None recorded on the row (`Superseded By` is null in the source). A
future decision reintroducing a hardcoded count on a public surface
would contradict this rule and require an explicit reversal.
