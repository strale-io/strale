## Decision

When a pull request adds or changes a code path that depends on deploy-pipeline
behavior, verify the real deploy mechanism before merge. Relevant dependencies
include database migrations, environment-variable loading, build steps,
startup hooks, scheduled jobs, and cron triggers.

The verification must:

1. name the exact deploy step or runtime condition required for the path to
   execute;
2. inspect the actual entrypoint, Dockerfile or build configuration, package
   scripts, startup wiring, workflow, scheduler, or cron definition that is
   supposed to reach it;
3. prove reachability through the specific import or invocation path rather
   than relying on a historical convention; and
4. after deployment, query the resulting production artifact or state for the
   expected effect.

A clean build or log line is not sufficient proof that a migration ran, a row
was written, an environment variable affected behavior, a scheduled job fired,
or the intended build reached production. If the artifact-level check is
missing, report the change as unverified rather than complete.

## Context

PR #42 caused roughly twenty-eight minutes of customer-facing errors on
2026-05-04 because a migration depended on
`apps/api/scripts/apply-migrations.ts`, a file that was neither compiled by the
API TypeScript configuration nor invoked by the container entrypoint. The
pre-merge review examined the change itself but did not prove that production
would execute the migration path. Later update blocks were also stranded by
the same dead-file mechanism.

PR #51 moved the migration runner onto the boot-blocking application import
path. PR #52 made the startup path and manual admin path use the same runner,
removing their duplicate block lists. Those fixes demonstrated the distinction
between code correctness, deploy reachability, and observed production effect.

## Rationale

Repository code can be internally correct and fully tested while remaining
dead at deploy time because it is outside a build root, absent from an import
graph, omitted from a container command, gated by an unread variable, or never
registered with a scheduler. Reviewing the mechanism that carries a change
into production closes that gap. Checking the resulting artifact closes a
second gap: execution logs show that a line ran, not that the intended state
transition succeeded.

## Consequences

Every triggered change must identify its deploy-pipeline dependency and cite
the concrete file or configuration path that reaches it. Session closeout must
record the production query or equivalent artifact-level check and its result,
or state plainly that deployment verification remains incomplete.

This decision is `related_to` `DEC-20260504-B` because one change may require
both reachability proof and a controlled workload-resumption strategy. Neither
decision retires or weakens the other. This protocol also does not relax the
capability-onboarding, distribution-integrity, audit-follow-up test, or
bulk-operation deploy protocols. The source's historical scoring-integrity
boundary remains context rather than a dependency on a retired implementation.

## Reversal conditions

Supersede or amend this decision only if the deployment platform provides a
stronger, structurally enforced proof that every relevant code path is built,
reachable, executed, and validated against its resulting production artifact.
Build success or logs alone are not enough to meet that condition. Any change
must be represented by a new decision rather than editing this protected record
in place.
