## Decision

Fix `checkValidationQueueStuck` and `checkProbationTimeout` to anchor
staleness on `lifecycle_transition` event timestamps rather than
`capabilities.updated_at`, and surface stuck capabilities via GitHub Issues
in `strale-io/strale` (the daily digest, the original candidate surface, was
broken 27+ days, per `DEC-20260511-F`).

## Context

The row's own Rationale states the diagnosis and the fix: "checkValidationQueueStuck
already existed and was firing correctly (5 times on 2026-05-11 alone, all
flagging SI) — the real gap was that its tier-2 health_monitor_events row
went to a table nothing else reads, plus an updated_at brittleness bug that
intermittently masked the alert when background processes touched the row.
Locked surface: GitHub Issues in strale-io/strale (digest was the original
candidate but is broken 27+ days — see DEC-20260511-F). Symmetric bug fix
applied to checkValidationQueueStuck and checkProbationTimeout: anchor on
lifecycle_transition event timestamps, not capabilities.updated_at." The row
names `DEC-20260511-F` directly as the reason the digest was rejected as a
surface; `related_to DEC-20260511-F` is recorded (that record exists on the
PR head).

## Rationale

As the row states it: `capabilities.updated_at` is bumped by routine
background touches (the test scheduler among them), which intermittently
masked a genuinely stuck capability's alert. Anchoring on the
`lifecycle_transition` event into the target state instead gives a
definitive, non-resettable timestamp. GitHub Issues was chosen over the
daily digest specifically because the digest pipeline was independently
found broken (`DEC-20260511-F`).

## Consequences

Status verified on 2026-09-05, against `main`.

**Both halves of the fix survive exactly as the row states, with the code's
own comments citing this Decision ID directly.** `apps/api/src/lib/meta-monitoring.ts`
carries the anchoring rationale verbatim in its own header comment:
"Staleness anchor for lifecycle-state checks. Uses the MAX(created_at) of
any lifecycle_transition event into the target state (definitive: a
transition happened then), falling back to capabilities.created_at for rows
that originated in the target state and have never transitioned.
capabilities.updated_at is NOT safe here — the test scheduler bumps it on
routine touches and silently resets the apparent 'stuck' age. SI was stuck
2026-05-07 -> 2026-05-11 but the original updated_at-based query
intermittently missed it because background updates kept resetting the
clock. Per DEC-20260511-E." Both checks are exported and scheduled: `checkValidationQueueStuck`
(documented "Check 11: Validation queue stuck (DEC-20260511-E)... anchored
on the lifecycle_transition event into 'validating'... On detection,
surfaces each stuck row as a [stuck-validating] GitHub Issue in
strale-io/strale via the existing GITHUB_TOKEN env var. Issues are
idempotent (existing one gets a comment, not a duplicate)... Surface =
GitHub Issues (not the daily digest — pipeline confirmed broken for 27+
days, see DEC-20260511-F)") and `checkProbationTimeout` ("anchored on
lifecycle_transition into 'probation', not capabilities.updated_at. Per
DEC-20260511-E"), both registered in the check registry at `daily` schedule.
