## Decision

Release the manual 30-day circuit-breaker pin on `swiss-company-data`. The
root cause was a bad manifest fixture (a non-existent Swiss UID), not a
Zefix tier scope limitation.

## Context

The row's own Rationale states the correction: "Earlier 2026-05-13 sessions
diagnosed CH as 'Zefix free tier returns only cancelled entities' and pinned
the swiss-company-data circuit breaker manually for 30 days. The
credentials-diagnostic session (T11/T12) disproved that diagnosis: the
manifest's known_answer.input.uid (CHE-105.805.977) was not a real Swiss
UID. Strale's Zefix-Credentials account is fully entitled to read ACTIVE
entities across all four UID endpoints. Bad fixture, not vendor scope.
Fixture corrected to CHE-101.602.521 (Roche Holding AG, ACTIVE) in PR #107
(commit 5375535). Manual pin released same day at 10:23Z. Two verification
probes returned populated ACTIVE data (Roche Holding + Société des Produits
Nestlé). CH back to Live." No other Decision ID is named in the row's own
text, so no relation edge is recorded.

## Rationale

As the row states it: the original diagnosis blamed the vendor's free-tier
scope; the actual cause was a fixture value that was never a valid Swiss
UID, which the credentials-diagnostic session disproved by confirming the
account's own entitlement covers ACTIVE entities on all four UID endpoints.

## Consequences

Status verified on 2026-09-05, against `main`.

**The corrected fixture is live in the current manifest, exactly as the row
states.** `manifests/swiss-company-data.yaml`'s `known_answer.input.uid` is
`CHE-101.602.521`, matching the row's stated fix, not the original bad value
`CHE-105.805.977`.

**The row's own `Outcome` field states the fix closed a four-phase bug-fix
cycle, shared with `DEC-20260513-C`:** "Bug-fix cycle fully closed across
all four phases. Phase 1 Contain: PR #107 (commit 5375535, CH bad-fixture
replaced CHE-105.805.977 → CHE-101.602.521 Roche). Phase 2 Understand:
joint course-correction Journal 35f67c87082c81ceab3cdfa08b6391a2. Phase 3a
Harden (runtime sentinel): PR #109 (commit 22ac530) — strict-missing-only
assertion in known_answer suite. Phase 3b Harden (onboard + PR-time gate):
PR #111 (commit 666f6db) — static manifest-consistency check +
onboard-time strict-missing helper. Path A (full PR-time dynamic gate)
downgraded to Path B (static + onboard-time + 1-hour runtime sentinel
composition) per CI infrastructure constraints; Path A re-entry triggers
documented in apps/api/scripts/manifest-consistency-allowlist.txt header:
(a) multiple concurrent contributors merging manifests, (b) CH-class
recurrence damaging production within 1-hour window, (c) CI infra
provisioned for unrelated reasons. 22 manifests grandfathered in allowlist
with individual fixes tracked as To-dos. Three
composing gates now active: onboard-time strict-missing, PR-time static
consistency, hourly runtime sentinel." This record did not independently
verify the PR #109/#111 commit shas or the manifest-consistency-allowlist
contents against current `main`.

**No dedicated "manual pin" mechanism exists in the schema or the admin
routes; a pin is an operator action on the same state field a recovery also
uses.** `apps/api/src/db/schema.ts`'s `capability_health` table has only a
`state` column ("'closed' = healthy, 'open' = suspended, 'half_open' =
testing"), `consecutive_failures`, `backoff_minutes`, and related fields,
with no boolean `pinned` or `manual_override` column. The release mechanism
this row describes ("Manual pin released same day at 10:23Z") corresponds
to the admin route `POST /v1/admin/reset-circuit-breaker`, which runs
`UPDATE capability_health SET state = 'closed', consecutive_failures = 0,
updated_at = NOW() WHERE capability_slug = $slug`, the same statement a
genuine vendor recovery would use, since the schema does not distinguish a
manually pinned
breaker from an automatically opened one.
