## Decision

Codify the in-startup-migrations.ts blocks pattern (called from `index.ts`
via `runStartupMigrations()`, before `validateSchema()` and before the API
listens) as the official schema-change convention, and remove the
misleading dual-track Drizzle SQL migration pipeline it had quietly
replaced.

`DEC-20260420-A`'s no-auto-generation / hand-written discipline is preserved:
the project still hand-writes migration logic; just in TS, not SQL files.
`DEC-20260420-B`'s `schema.ts` sync rule is preserved: `schema.ts` edits
still ship alongside the corresponding in-TS block.

## Context

Phase 2 of the PR #88 bug fix surfaced that the Drizzle SQL pipeline was
never wired into deploy: the Dockerfile CMD does not invoke `drizzle-kit
migrate`, and the production `drizzle.__drizzle_migrations` tracking table's
last applied entry was from roughly April 4, 2026. The in-`startup-migrations.ts`
blocks had been doing the actual schema work since April. PR #88 violated
that convention by adding a Drizzle SQL file (which never ran) instead of an
in-TS block; the deploy failed healthcheck on the missing column. Codifying
the working pattern as the official convention closes the deploy-order
regression class and removes the misleading dual-track.

## Rationale

The in-TS blocks were the code path that had actually been running in
production since April; the Drizzle SQL migration pipeline had silently
stopped running months earlier without anyone noticing, because nothing in
the deploy mechanism invoked it. Making the working path official, and
retiring the path that only looked authoritative, closes a class of
deploy-order regression rather than leaving two conventions where only one
is real.

## Reversal conditions

Reconsider this convention if the CI-lane use of `drizzle-kit push --force`
ever expands beyond ephemeral test-database bootstrap into anything that
writes production schema, which would reopen the exact dual-track this
record closed. Any change to the production schema-change convention itself
must be represented as a new decision with an explicit `supersedes` or
`amends` relationship targeting this protected record, not an edit in place.
