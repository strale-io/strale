## Decision

`DEC-20260421-J`'s retirement pattern assumed capabilities could be
hard-deleted once `solution_steps` dependents were handled first. Reality,
surfaced during Phase 4b.2 execution: capabilities with production
transaction history have `transactions.capability_id` foreign-key
references that must be preserved as audit trail. Hard `DELETE` is blocked
by that FK and would be semantically wrong even if it were allowed —
removing capability rows that have historical transactions would orphan
audit records.

Refinement: retirement now has two variants, chosen by an FK check.

- **Variant 1 (clean retire, `DEC-20260421-J`).** No transaction history.
  Soft-deactivate dependent solutions, delete `solution_steps`, `DELETE` the
  capability row, update seeds, regenerate the sitemap. Used for the SG KYB
  retirement (`singapore-company-data` had no production transactions).
- **Variant 2 (tombstone retire, new here).** Transaction history exists.
  Soft-deactivate the capability row (`lifecycle_state=deactivated`,
  `visible=false`, `is_active=false`), leave the row in the database as an
  audit tombstone, update seeds, do not attempt `DELETE`. Used for
  `amazon-price`, `hong-kong-company-data`, `indian-company-data` (already
  in this state from a 2026-04-01 admin sweep at adoption time).

The variant is determined by the FK check in Step 3 of the retirement
prompt: implementation is that retirement prompts should check
`transactions.capability_id` count before attempting `DELETE`. If the count
is greater than zero, the tombstone path applies. If zero, the full-delete
path applies.

Four reasons for choosing tombstone over delete when transactions exist:

1. Audit trail immutability is a load-bearing property of Strale's value
   proposition — every capability call produces a signed audit record, and
   deleting the capability would break that chain.
2. Re-use of a slug after delete would silently connect to orphaned
   historical records.
3. The deactivated state already prevents the capability from serving new
   traffic, which was retirement's functional goal.
4. The disk cost of one tombstone row is negligible against the clarity
   loss of deleting audit substrate.

The `amazon-price` / `hong-kong-company-data` / `indian-company-data`
capabilities are natural tombstones by this criterion; at adoption time they
were already in the correct state and needed no action. Future retirements:
check the FK count first, then pick the variant accordingly.

## Rationale

The retirement pattern needed this variant anyway; Phase 4b.2 surfaced it
explicitly. Preserving audit history for FK-bound capabilities is a
straightforward consequence of the platform's own audit-trail commitment,
and the disk cost of a tombstone row is negligible compared to the value of
never breaking a signed audit chain.

## Consequences

Status verified on 2026-09-04, against `main`:

- `amazon-price` remains in the `auto-register.ts` DEACTIVATED map today
  ("Amazon CAPTCHA blocks datacenter IPs"), consistent with the tombstone
  state this row records. `hong-kong-company-data` and
  `indian-company-data` also remain in the DEACTIVATED map, each with a
  probe-dated comment (2026-04-29) explaining why no clean source exists
  yet — both are tombstoned in the sense this record describes (soft
  deactivated, not deleted), and neither has been reactivated.
- **A third lifecycle path exists that this 2026-04 pattern predates.**
  `DEC-20260812-A`'s quality floor now deactivates and quarantines
  capabilities automatically via the x402-enabled flag
  (`apps/api/src/lib/capability-promotion.ts`), with auto-promotion on
  recovery. This refinement is unchanged by the quality floor's existence:
  the quality floor is an automated, reversible enforcement mechanism keyed
  on real-traffic pass rate, while this record's variant selection is keyed
  on whether `transactions.capability_id` FK references exist for a
  capability being deliberately retired. The two operate on different
  triggers and do not conflict.
- **A record is never proof of production state.** `CLAUDE.md`'s
  "Predecessors that overlap the KYB families" paragraph warns that
  production contradicted a recorded deactivation on 2026-08-14. This
  record's parent, `DEC-20260421-J`, documents a directly analogous case for
  the SG KYB retirement this refinement was extracted from:
  `singapore-company-data` was reactivated eight days after the retirement
  this row refines, once a compliant data source (`data.gov.sg`) was found
  (commit `bd25bc57`). This does not affect the tombstone-vs-delete
  refinement itself — SG KYB used Variant 1 (clean, `DELETE`-based) and had
  no transaction history to tombstone — but it is the same underlying
  caution: whether a capability's current lifecycle state matches a
  Decision row's record must be checked against `is_active` /
  `x402_enabled` / the DEACTIVATED map in production, never assumed from the
  row.
- `apps/api/src/lib/capability-readiness.ts` documents a later, larger
  application of the tombstone concept: 12 capabilities parked under
  `DEC-20260423-B` Stage C.2 with `deactivation_reason` values prefixed
  `park_permanent_...`, using the same "leave the row, mark it, don't
  delete" discipline this record establishes for FK-bound capabilities,
  though that later cohort is a park action (per `DEC-20260421-L`), not a
  retirement.

## Reversal conditions

Reconsider this refinement if the FK check in Step 3 of the retirement
prompt is automated into the retirement tooling itself (currently a manual
step per the retirement prompt), or if a schema change removes the
`transactions.capability_id` foreign key this variant selection depends on.
Represent such a change through a new decision and an explicit `supersedes`
or `amends` relationship rather than editing this protected record in
place.
