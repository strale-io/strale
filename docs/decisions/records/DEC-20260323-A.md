## Decision

All trust data is served from DB columns; write-time decay only (never
computed on read); one score everywhere. The legacy single-composite model
is retained only for the `legacy_score` field.

## Context

A Phase 1 audit found 20 inconsistencies (2 critical) caused by 4 different
data paths serving SQS scores with different processing. Root cause:
catalog endpoints read a cached DB column with no read-time decay; quality
endpoints computed the score live with no freshness decay; trust endpoints
computed the score live with freshness decay applied; and daily snapshots
captured the score at snapshot time. The same capability could therefore
report a different score depending on which of the 16 endpoints was
called. The historical Notion scope field on this row was `global`. It is
recorded here as `scope: technical` under this repository's decision-record
vocabulary (the batch-9 brief classifies this row as the one data-path
decision among the six, distinct from the five display/positioning rows).

## Rationale

The fix: all 16 endpoints read from the same DB columns (`matrix_sqs`,
`matrix_sqs_raw`, `trend`, `freshness_level`, `last_tested_at`,
`freshness_decayed_at`). `persistDualProfileScores()` and a 2-hour
staleness-refresh job are named as the only writers. No live SQS
computation is permitted on any read path.

## Consequences

Status verified on 2026-09-04, against `main`.

**The single-source-of-truth principle survives; the specific mechanism it
names does not.** `persistDualProfileScores`, the writer this row names
as one of exactly two, was itself removed with the SQS engine.
`apps/api/src/lib/test-runner.ts` states this directly in its own
"Removed" section: "`computeAdaptiveInterval`, `getLastTestRun`,
`runAdaptiveScheduler`, `startScheduledTests`, `repairStaleScores`, and
`persistDualProfileScores` were retired with the SQS engine
(DEC-20260503-B)." There is therefore no writer left for the columns this
row names, and consequently no write-time decay computation running
either — not "read-time decay eliminated, write-time decay in force" as
the row states, but neither happening, because the score those columns
held is no longer computed at all.

**The named columns still exist on `main`, frozen.** `apps/api/src/db/schema.ts`
declares `qp_score`, `rp_score`, `matrix_sqs`, `matrix_sqs_raw`, `trend`,
and the `guidance_*` columns this row's data path fed, plus the
`sqs_daily_snapshot` table the audit's "4 data paths" finding named as one
of the four. CLAUDE.md confirms these are residual: "PR2 will drop the
residual schema columns (`qp_score`, `rp_score`, `matrix_sqs`,
`matrix_sqs_raw`, `trend`, `guidance_*`) and the `sqs_daily_snapshot`
table." A repository-wide search for `legacy_score` (the field this row
says the legacy single-composite model is retained under) finds zero
matches in `apps/api/src` — that field does not exist under that name on
`main` today.

**`capability_health` has not yet been renamed to `source_health`.**
CLAUDE.md's stated plan ("rename `capability_health` -> `source_health`")
has not landed: `apps/api/src/db/schema.ts` still defines the
`capability_health` table, and `apps/api/src/lib/lifecycle.ts`'s own
comment treats `source_health` as future-tense ("A future per-product
routing engine may reintroduce automatic transitions keyed on
`source_health.status` once that substrate exists") — confirming no
`source_health` table exists on `main` as of 2026-09-04. A repository-wide
search for `source_health` across `apps/api/src/db/schema.ts` finds no
match.

**A new single-source-of-truth surface replaced the one this row
built.** `apps/api/src/routes/public-trust.ts` reads `test_suites`,
`solutions`, `solution_steps`, and `capabilities` directly per-request (not
the frozen `matrix_sqs`/`qp_score`/`rp_score` columns this row's mechanism
named) and is the one place `pass_rate` and `tested` are computed today for
public consumption, per its own file-header design note. This preserves
this row's underlying goal (one score, one computation, not four divergent
paths) with a different, simpler mechanism than the one this row
specifies.

## Reversal conditions

Reconsider this decision if a future routing-engine or trust-scoring
rebuild reintroduces multiple divergent read paths for the same score
(the exact class of bug this row's Phase 1 audit found); that rebuild
should re-adopt the single-source-of-truth principle explicitly against
whatever table and writer exist then, not against the specific
`matrix_sqs`/`persistDualProfileScores` mechanism this row names, which is
dead. Represent such a change through a new decision rather than editing
this protected record in place.
