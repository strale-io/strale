## Decision

All new capabilities must use the manifest-driven pipeline
(`scripts/onboard.ts`), never the old `seed.ts` file plus onboarding hook
path.

## Context

Session A had built 14 capabilities via the old `seed.ts` path. The
onboarding hook on that path only generated 2 of the 5 required test types
(`schema_check` and `negative`). The full pipeline (`onboard.ts`) generates
all 5 test types from a manifest YAML. `phone-type-detect` shipped with SQS
39.3 because `known_answer` tests were never generated on the old path. The
old path does not scale to third-party providers. CLAUDE.md was updated
with mandatory instructions.

The historical Notion scope field on this row was `global`. It is recorded
here as `scope: technical` under this repository's decision-record
vocabulary: this is an engineering process mandate about how capabilities
enter the codebase.

## Rationale

The old `seed.ts` + onboarding hook path only produced 2 of the 5 test
types the platform relies on for onboarding quality, and required no
manifest, so nothing enforced field reliability, limitations, or full test
coverage. Mandating the manifest-driven pipeline for every new capability
closes that gap and, per the row's own text, is "the workflow that scales
to third-party providers."

## Consequences

Status verified on 2026-09-04, against `main`.

**The prohibition is now structural, not just a policy.** `seed.ts` was
deleted in PR #79. A repository search for a `seed.ts` file under
`apps/api` finds none; `git ls-files` returns no match. There is nothing
left to accidentally use instead of the pipeline — the old path this row
prohibits does not exist to be chosen. CLAUDE.md's "Adding New
Capabilities (MANDATORY PIPELINE)" section states the same fact directly:
"The historical seed.ts file was deleted in PR #79; it duplicated manifest
content and only generated 2 of 5 required test types via its onboarding
hook. The canonical pipeline is `apps/api/scripts/onboard.ts`... and is the
only sanctioned path for capability creation."

**The pipeline itself is current.** `apps/api/scripts/onboard.ts` exists on
`main` and its flag parsing (`process.argv.slice(2)`) still recognizes
`--dry-run`, `--backfill`, `--strict`, `--fix`, and `--discover`, plus
newer flags this row predates (`--batch`, `--force`,
`--force-override-authority`). `apps/api/src/capabilities/auto-register.ts`
exists and auto-imports executors from `manifests/*.yaml` at startup,
matching CLAUDE.md's "Auto-registered" step.

**phone-type-detect.** This row and `DEC-20260318-B` (recorded separately
in this batch) both name `phone-type-detect` as the capability whose gap
motivated the change; this row's Rationale states it "shipped with SQS
39.3 because known_answer tests were never generated." The SQS score named
here is historical: the SQS scoring engine was deleted per DEC-20260503-B
(PR1, 2026-05-05); `sqs.ts`, `EXTERNAL_SERVICE_PATTERNS`,
`isExternalServiceFailure`, and `computeFromRows` no longer exist. Test
scheduling now filters on `test_suites.scheduled_testing_eligible`, a flag
a startup migration rewrites from `external_cost_cents` on every boot
(CLAUDE.md, "Capabilities & Quality"). `phone-type-detect`'s SQS 39.3
figure cannot be re-verified today because the scoring mechanism that
produced it is gone; the underlying gap it illustrates (missing
`known_answer` fixtures) is what `--discover`/`--fix`/execute-and-verify
in `DEC-20260318-B` and Gate 5 (`DEC-20260411-B`, also in this batch)
address structurally.

## Reversal conditions

Reconsider this decision only if a future engineering session reintroduces
a capability-creation path outside `manifests/*.yaml` plus
`apps/api/scripts/onboard.ts` plus the `auto-register.ts` DEACTIVATED map.
Represent such a change through a new decision rather than editing this
protected record in place.
