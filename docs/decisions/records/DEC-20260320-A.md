## Decision

Four structural changes to capability onboarding: (1) an auto-register
mechanism replaces the manual, 312-line `app.ts` import list — new
executors are discovered at startup automatically; (2) a 6-dimension,
cached, API-exposed readiness checker becomes the single source of truth
for production readiness; (3) test generation adopts a 4-tier field
reliability classification (DB metadata, then schema required, then
baselines, then heuristics), so only guaranteed fields get `not_null`
assertions; (4) a seed script guard and an audit CLI provide immediate
onboarding feedback. Scoring integrity is preserved: no change to SQS
scoring logic.

## Context

An onboarding audit found 88.8% readiness (229 of 258 capabilities). Root
causes named: the manual `app.ts` import list was the most common failure
point; there was no enforcement gateway to verify onboarding completeness;
test assertions on optional output fields caused false negatives; missing
latency estimates defaulted capabilities to the synchronous execution path.
The four structural changes above address each root cause directly. Result
stated in the row: 254 of 258 capabilities fully onboarded (98.4%); the
remaining 4 were intentionally deactivated.

The historical Notion scope field on this row was `global`. It is recorded
here as `scope: technical` under this repository's decision-record
vocabulary: this is an engineering hardening pass on the onboarding
pipeline's internals.

## Rationale

A manual import list is a single point of human error that scales linearly
with capability count; auto-discovery from the manifest set removes that
failure mode structurally. A readiness checker that is the single
enforcement gateway (rather than one of several partial checks) prevents
capabilities from reaching production in an inconsistent state. Tiered
field reliability prevents asserting on fields that are legitimately absent
for some inputs, which the row's Rationale ties to false test failures.

## Consequences

Status verified on 2026-09-04, against `main`.

**Auto-register exists and is current, but the discovery mechanism this
row names has changed shape since 2026-03-20.**
`apps/api/src/capabilities/auto-register.ts` exists on `main` and its
header comment states it reads `manifests/<slug>.yaml`, checks the
DEACTIVATED map, dynamic-imports the matching executor, and verifies
`getExecutor(slug)` registered a handler — auto-discovery from the
manifest set, matching this row's intent. The file's own comment describes
what it replaced as "the previous filesystem-glob discovery," not the
"manual, 312-line `app.ts` import list" this row's Rationale names; both
descriptions agree the old mechanism was error-prone and manual/implicit
rather than manifest-driven, but this record cannot verify the specific
"312-line" figure against current source, since the file it would have
lived in is gone. Stated as a wording discrepancy, not a contradiction of
substance.

**The readiness checker exists, is the current gateway, and cache-checks
as described, but its dimension count has grown from 6 to 8.**
`checkReadiness` in `apps/api/src/lib/capability-readiness.ts` is
described in its own file header as "single source of truth for 'is this
capability fully onboarded and ready for production traffic?'" and caches
results (`CACHE_TTL_MS`), matching this row's "cached" claim. Its
`ReadinessCheck.dimensions` object today carries 8 fields: `has_executor`,
`has_db_row` (with `is_active`), `has_test_suites`, `has_latency_estimate`,
`has_transparency_tag`, `has_input_schema`/`has_output_schema`,
`has_reliability`, and `has_limitations` — not the "6-dimension" figure
this row states. The file's own comment attributes the growth to
`DEC-20260423-B`: "The last two dimensions [reliability and limitations]
were added per DEC-20260423-B (Stage A, warning mode)... 34 caps shipped
to prod with NULL reliability." This is a dated, source-attributed change
after this row's 2026-03-20 decision, not an error in this row; the
dimension count is stated here as historical (6, as recorded) versus
current (8, verified on `main`).

**A single insert-capabilities gateway exists in code.** A repository
search for `db.insert(capabilities)` and `INSERT INTO capabilities`
outside `apps/api/scripts/archive/` finds one production call site:
`apps/api/src/lib/capability-persistence.ts` (`tx.insert(capabilities)`),
which `apps/api/scripts/onboard.ts` calls. No other current code path
inserts a capability row, supporting this row's "single enforcement
gateway" framing at the DB-write level, distinct from the readiness
checker's read-time gate.

**4-tier field reliability classification.** This row's Rationale names
the ordering ("DB metadata → schema required → baselines → heuristics")
but this batch did not locate a single named function implementing exactly
that four-step ordering as such; `output_field_reliability` as a concept
(guaranteed/common/rare) is documented in CLAUDE.md's "Field reliability
rules" and is the mechanism `checkReadiness`'s `has_reliability` dimension
gates on. The ordering claim is preserved verbatim above and not
independently re-verified against a single source file.

**Seed guard.** `seed.ts` was deleted in PR #79 (see `DEC-20260318-A`'s
Consequences in this batch); a guard against writing to a file that no
longer exists has no current object to guard. **Audit CLI.**
`apps/api/src/db/audit-onboarding.ts` exists on `main` today and matches
this row's "audit CLI" description functionally.

**SQS scoring integrity note.** This row states scoring integrity was
preserved with no change to SQS scoring logic. The SQS engine itself was
later deleted in full per DEC-20260503-B (PR1, 2026-05-05); `sqs.ts` and
its supporting functions no longer exist, and `scheduled_testing_eligible`
(derived from `external_cost_cents` on every boot) replaced SQS-driven
scheduling. This row's SQS-preservation claim was accurate for its own
2026-03-20 date and is now superseded by that later, unrelated deletion.

## Reversal conditions

Reconsider this decision if a future onboarding redesign removes the
auto-register mechanism, the readiness checker as the enforcement gateway,
or tiered field reliability without replacing the guarantees they provide.
Represent such a change through a new decision rather than editing this
protected record in place.
