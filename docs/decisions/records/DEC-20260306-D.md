## Decision

Fix 6 metric-display consistency issues found by an audit across all
trust-and-quality display surfaces.

## Context

An audit found 6 metric consistency issues: (1) a solution's "Last tested"
timestamp mismatched between the trust card and the run log; fixed by
aligning both to complete-runs-only. (2) A "Tests Passing" count mismatch
(12/12 suites vs. 36/36 executions); fixed by aligning the counting method.
(3) "Success Rate" vs. "Test Pass Rate" naming confusion; renamed to "Test
Pass Rate," sourced from test data. (4) Raw milliseconds vs. formatted
seconds; fixed with a shared `formatDuration()` helper. (5) Three different
relative-time formatters; consolidated to `formatLastTested()`. (6) Color
thresholds of 95/80 that disagreed with the design system's documented
90/70 rule; aligned to 90/70. The historical Notion scope field on this row
was `global`. It is recorded here as `scope: product` under this
repository's decision-record vocabulary: this decision governs how
customer-facing metric surfaces present numbers consistently, a product
concern rather than an internal engineering convention. This row's
`Outcome` field was empty in the source export and its `Reviewed` flag was
`__NO__`; nothing further is stated as verified by the source itself beyond
the six fixes the Rationale names.

## Rationale

The audit's premise was that the same underlying number (a test count, a
last-tested time, a pass rate) rendered differently depending on which
component displayed it, which is itself a trust problem independent of
whether any individual number was wrong. Each of the six fixes replaces an
ad hoc per-component calculation or formatter with one shared function or
one shared threshold.

## Consequences

Status verified on 2026-09-04, against `main`.

**The subject these fixes governed no longer computes live.** All six
fixes concerned SQS-era test-pass-rate and quality-metric display. The SQS
engine was deleted per DEC-20260503-B (PR1 shipped 2026-05-05; CLAUDE.md:
"SQS scoring engine deleted"). The specific helper names this row does not
state directly (it names the fix, not a function name, except by
implication), so no specific symbol from this row's Rationale can be
grep-verified as present or absent on `main`; this differs from
DEC-20260305-G, decided the day before, whose companion row does name
`calculatePassRate()` directly (see that record's Consequences for the
"dead symbol" finding).

**A narrower successor metric exists today.** `apps/api/src/routes/public-trust.ts`
(`/v1/public/ops/trust/*`) exposes `pass_rate` as one of exactly five
fields (`badge`, `badge_label`, `tested`, `last_tested_at`, `pass_rate`),
a single canonical value per capability or solution rather than the
per-component recalculation this row's issue (2) and (3) describe. The
route's own header comment frames its narrow field set as a deliberate
choice not to "recreate a scoring surface the platform decided to stop
publishing."

**The wire-shape rule for trust endpoints postdates this row and
subsumes its intent.** CLAUDE.md's "Wire-shape rule for
`/v1/public/ops/trust/*` endpoints" requires money as integer cents, scores
as 0-100 integers or 0-1 decimals, dates as ISO 8601, and forbids
pre-formatted display strings — a stricter, machine-verifiable version of
this row's consistency goal. It was adopted after a 2026-04-30 cert-audit
finding traced a broken fallback card to a serializer that emitted a
formatted currency string instead of an integer cents field, and now
governs the surface this row's fixes targeted.

## Reversal conditions

Reconsider this decision if a future audit finds the same class of
per-component metric drift on the current `/v1/public/ops/trust/*` surface
or its successor; that audit's fix should cite the wire-shape rule and the
current route rather than reviving this row's named helper functions.
Represent such a change through a new decision rather than editing this
protected record in place.
