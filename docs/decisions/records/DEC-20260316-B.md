## Decision

SQS display hierarchy: the SQS score renders as a number-plus-word
headline (e.g. "82 Good"), with QP (Quality Profile) and RP (Reliability
Profile) letter grades shown only as compact secondary detail, never
competing with or replacing the headline.

## Context

The decision states an S&P-style analogy: SQS is the issuer rating (the
headline signal), and QP/RP are BRP/FRP-equivalent inputs feeding that
rating. Cards show the SQS score and label as the primary signal (top-left,
visually dominant); QP and RP letter grades appear as compact secondary
context (bottom-left) explaining why the SQS is what it is. QP/RP use
letters only on cards ("Quality A · Reliability B"); descriptive labels for
QP/RP only appear on methodology/documentation pages. The rule exists to
prevent competing vocabularies: SQS uses number+word, profiles use letters,
never mixed inline. The historical Notion scope field on this row was
`global`. It is recorded here as `scope: product` under this repository's
decision-record vocabulary: a card-layout and typography-hierarchy rule for
a customer-facing trust signal.

## Rationale

Two parallel vocabularies (a numeric score and letter grades) presented at
equal visual weight would produce exactly the "which is the real rating"
confusion DEC-20260316-A separately addresses for the Combined Trust
Grade. Fixing the *hierarchy* (SQS dominant, QP/RP secondary) and the
*vocabulary boundary* (numbers on cards, letters only as secondary detail,
never mixed inline) is this row's distinct concern from that companion
decision, decided the same day.

## Consequences

Status verified on 2026-09-04, against `main`.

**The dual-profile QP/RP model this hierarchy governs was deleted.** Per
DEC-20260503-B (PR1 shipped 2026-05-05; CLAUDE.md: "The dual-profile model
(QP + RP + 5x5 matrix)... are all gone"), there is no QP score and no RP
score computed live for any capability, so there is nothing left to
subordinate to an SQS headline. `apps/api/src/db/schema.ts` still declares
the `qp_score` and `rp_score` columns (residual, pending removal in PR2 per
CLAUDE.md), but no code path writes them: `persistDualProfileScores`, the
only writer this row's companion decision (DEC-20260323-A) names, was
itself removed with the SQS engine (confirmed by
`apps/api/src/lib/test-runner.ts`'s own "Removed" comment naming it
explicitly).

**No card-layout or typography code for this hierarchy exists in this
repository today.** This row's rules (top-left dominant placement,
bottom-left secondary letters, "never mixed inline") describe a frontend
rendering layout. No such component exists under `apps/api`, the only app
directory present on `main`; `apps/web` (the DEC-20260902-A website
redesign target) does not yet exist on `main` as of 2026-09-04. The
S&P/issuer-rating analogy and the number-vs-letter vocabulary boundary this
row states are preserved here as historical design intent, not verified
against any live layout.

**`apps/api/src/lib/trust-grade.ts` still exposes letter grades (`A`
through `D`, or `A`-`C` for freshness) for freshness and latency, narrower
than the QP/RP letters this row governs.** Those are a different pair of
letter-grade dimensions (freshness, latency) than QP/RP (quality profile,
reliability profile); this row's specific hierarchy rule does not apply to
them directly, but the same "letters as secondary, never the primary
headline" principle is consistent with how `computeFreshnessGrade`'s output
is used in `apps/api/src/routes/do.ts` — as one field among several in a
capability's provenance/metadata payload, never as a standalone headline.

## Reversal conditions

Reconsider this decision if a future trust-display redesign reintroduces a
letter-grade-based quality signal (QP/RP or an equivalent) at headline
prominence; that redesign should state its own hierarchy rule against
whatever score exists then, rather than reviving this row's SQS-era
number+word rule verbatim. Represent such a change through a new decision
rather than editing this protected record in place.
