## Decision

Require third-party providers to submit test fixtures with
`known_answer` data as a non-negotiable condition of onboarding a
capability.

## Context

The row's stated basis, from its own Rationale: "Biggest failure mode in
marketplace quality is providers submitting capabilities with no tests
or trivial tests. Requiring known_answer fixtures with guaranteed field
expectations ensures every provider has thought about what their
capability promises."

The historical Notion scope field on this row was `global`. It is
recorded here as `scope: technical`: it specifies a requirement inside
the capability onboarding pipeline, not a company-wide strategic
decision. The row's own text does not name any other Decision ID, so no
relation edge is recorded here.

## Rationale

The rationale, as the row states it: without a mandatory known-answer
fixture, a provider can ship a capability that has never been asked to
prove it returns anything specific; requiring guaranteed-field
expectations up front forces the provider to state what the capability
actually promises.

## Consequences

Status verified on 2026-09-05, against `main`.

**No third-party provider exists to apply this rule to.** CLAUDE.md's
Active Decisions list records DEC-4: "Founder is the only provider for
first 3 months," and no later record in this repository documents a
third-party provider ever onboarding (T10 batch 13's DEC-20260224-P-a1b2
record and batch 14's DEC-20260227-P-a1b2 record both state, with their
own evidence, that the third-party provider programme never onboarded a
provider). This rule was written for a marketplace surface that has not
existed in practice at any point since.

**The requirement survives today, but as the onboarding pipeline's own
universal rule for every capability, not a provider-specific gate.**
`apps/api/scripts/onboard.ts` is, per CLAUDE.md, "the only sanctioned
path for capability creation," and its own documentation comment (near
line 6) lists step 2 as: "Test suites (known_answer + dependency_health
from manifest fixtures ...)"; a second comment (near line 244) describes
the pipeline's job as generating tests from "known_answer fixtures and
verify via production traffic / piggyback." The script enforces a
known-answer fixture for every capability CLAUDE.md's own onboarding
section confirms this: "The known_answer test input (a real entity
you've verified works)" is listed under "What the pipeline does NOT do
(human must provide)" required from every author, Strale included, not
only from a hypothetical third party. So the row's specific target
(a third-party provider requirement) never had an occasion to apply, but
its substance (mandatory known-answer fixtures) is now simply how every
capability, including Strale's own, is onboarded.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null).
DEC-4 (no third-party providers for the platform's first three months,
and none since, per the batch 13/14 records) is why this rule has never
had a provider to apply to; the onboarding pipeline's own known-answer
requirement is the substance of this row surviving in a different form.
