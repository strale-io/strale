## Decision

`GET /v1/transactions/:id` unauthenticated lookups always return a redacted
envelope: 13 non-PII fields plus a quality object plus `body_redacted: true`
plus a `body_redacted_reason` prose string, at HTTP 200. The five PII fields
(input, output, error, provenance, audit_trail) are absent from unauth
responses; authenticated responses are unchanged. The marker is asymmetric
(present only on unauth responses). `GET
/v1/transactions/:id/verify` is untouched: it is a hash-only receipt with no
body fields ever served.

## Context

The row's own Rationale states the basis: "F-A-005.a audit surfaced 6 open
questions; all 6 decided and shipped as F-A-005.b (single commit a253d91)."
The design path chosen was "always-redact," rejecting a per-capability
PII-flag-driven approach because it "inherits the manifest-drift surface
SA.2b.b discovered" (three drift classes found across 15 sampled
manifests, so a flag-driven design "would leak silently" for any capability
onboarded without declaring PII status), and rejecting an HMAC-token
unauth-lookup path because it "breaks the no-signup-no-auth free-tier UX
that makes the endpoint valuable." Six further open questions were decided:
include the quality object (SQS/quality_grade/reliability_grade are
operator-domain signals already public elsewhere); name the marker
`body_redacted` (aligned with SA.2a's `redacted_at` semantics); include a
prose reason (cheap, and helps agents that hit the response without reading
docs first); return HTTP 200 rather than 206 (206 "requires Content-Range
per RFC 7233 which doesn't map to field-level redaction"); make the marker
asymmetric (zero byte cost and zero regression risk for existing authed
callers); and defer the Python SDK to a standing ticket. The verify
endpoint was explicitly left alone: "Adding body_redacted marker would
confuse API clients that handle this response as a hash receipt."

The row's own References list further prior decisions in the same
migration series: "DEC-20260420-A (hand-written migrations), DEC-20260420-B
(SA.2a read-path), DEC-20260420-C (SA.2a DELETE handler), DEC-20260420-D

## Rationale

The rationale, as the row states it: an always-redact design is
drift-resistant by construction where a per-capability-flag design would
inherit the manifest-drift risk SA.2b.b had just discovered, and it
preserves the no-signup free-tier UX that an HMAC-token design would break;
the cost is that authenticated access (already free to obtain) is the only
path back to the redacted body fields.

## Consequences

Status verified on 2026-09-05, against `main`.

**The design shipped and remains in the codebase essentially as described.**
`apps/api/src/routes/transactions.ts` carries the comment "F-A-005:
explicit body redaction marker. input, output, error, ..." at its
`body_redacted: true as const` and `body_redacted_reason` construction, and
"F-A-005: Unauthenticated lookups return a redacted envelope — body fields"
at the branch that builds it. The verify-endpoint carve-out is preserved
under a different, later hardening decision: `apps/api/src/routes/verify.ts`
still returns only hash-chain fields, now under tighter depth and rate
limits (this batch's `DEC-20260420-G` row, F-A-012).
