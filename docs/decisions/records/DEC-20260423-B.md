## Decision

Retain capability onboarding as an always-enforce rule, but use the corrected
manifest-driven mechanisms:

1. validate the manifest at pull-request time;
2. populate `output_field_reliability` through live `onboard.ts --discover`
   execution and block readiness when coverage is absent;
3. compute `avg_latency_ms` from test execution and require it for readiness;
4. run structural validation through the onboarding hook; and
5. execute readiness before a capability becomes active.

New capability rows must use `persistCapability`. Historical seed writers must
declare reliability and limitations or use the discovery wrapper. Direct
application or raw-SQL inserts are forbidden and require structural database
enforcement. A short prompt never waives these steps, and incomplete readiness
must be reported rather than called done.

## Context

The original rule implied that one insert hook populated every required field.
The 2026-04-23 audit showed that reliability and limitations came from the
separate discovery path, leaving thirty-four capabilities incomplete. The
revised decision distributed its five authoritative steps across the lifecycle
points that could actually enforce them.

## Rationale

Naming the real writer, derivation path, validation point, and activation gate
turns a remembered checklist into a system whose gaps can be observed.
Keeping the prompt/pipeline separation preserves the valuable principle from
the superseded rule without retaining its false mechanism.

## Consequences

This decision supersedes `DEC-20260320-B` and is `related_to`
`DEC-20260423-A`, which implemented the corrected write and readiness controls.
Later changes removed or altered seed, SQS, scheduled-testing, and automatic
lifecycle mechanics without weakening the manifest, reliability, limitation,
structural validation, and readiness invariants.

Current entrypoints still name the superseded ID and point to a historical
spec containing retired mechanisms. They remain authoritative during M2, so
this batch does not edit them. M4 must replace both stale routes and resolve
the fresh-database trigger/read-back gap before activating this record.

## Reversal conditions

Supersede or amend this decision only if a replacement provides one canonical
capability-entry path, evidence-backed output contracts, explicit limitations,
structural validation, activation gating, and observable enforcement across
all writers. A more automated pipeline may replace individual steps; prompt
silence or documentation alone cannot make them optional.
