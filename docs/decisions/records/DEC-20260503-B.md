## Decision

Redesign SQS as a per-product routing engine. Simplify the testing schedule
to hourly, free-only. Tier the audit trail: basic on capabilities, full on
`*-Assurance` products.

## Context

`Superseded By` fields are all null. No other Decision ID is named in the
row's own text, so no relation edge is recorded here even though this
decision is widely referenced by later records and by CLAUDE.md.

## Consequences

Status verified on 2026-09-05, against `main`.

**The redesign this row announces was not a routing-engine redesign; it was
the deletion of the SQS scoring engine, per CLAUDE.md's own framing: "SQS
scoring engine deleted per DEC-20260503-B (PR1 shipped 2026-05-05). The
dual-profile model (QP + RP + 5×5 matrix), the `min_sqs` request parameter on
POST /v1/do, the platform floor SQS gate, the floor-aware solution SQS rule,
the public `/v1/quality/:slug` endpoint, and the automatic lifecycle
transitions (probation→active, active→degraded, degraded→active,
degraded→suspended) are all gone." Rather than a new per-product routing
mechanism, the outcome was removal of the scoring system this row's own text
implies would be "redesigned."

**PR1 (the deletion) shipped; PR2 (dropping the residual schema) has not.**
CLAUDE.md states: "PR2 will drop the residual schema columns (`qp_score`,
`rp_score`, `matrix_sqs`, `matrix_sqs_raw`, `trend`, `guidance_*`) and the
`sqs_daily_snapshot` table, and rename `capability_health` →
`source_health`." Reading `apps/api/src/db/schema.ts` directly confirms all
of these are still present: `qpScore: decimal("qp_score", ...)`, `rpScore:
decimal("rp_score", ...)`, `matrixSqs: decimal("matrix_sqs", ...)`,
`matrixSqsRaw: decimal("matrix_sqs_raw", ...)`, `trend: varchar("trend",
...)`, `guidanceUsable`, `guidanceStrategy`, `guidanceConfidence`, and a full
`sqs_daily_snapshot` table definition with its own unique and descending
indexes. PR2 has not shipped as of this record's verification date.

**The "hourly free-only" testing schedule survives as the base rule but has
been extended with a risk-tiered layer this row does not describe.**
CLAUDE.md states: "Test scheduling now filters on
`test_suites.scheduled_testing_eligible = TRUE` (DEC-20260503-B), with
`external_cost_cents = 0` as the underlying source of truth." That base
filter is confirmed live in `apps/api/src/jobs/test-scheduler.ts` (`AND
ts.scheduled_testing_eligible = TRUE` appears at two query sites). But the
same file has since added a risk-tiered cadence for finite-cost live/canary
suites that this row's "hourly free-only" description does not mention: "Paid
capabilities remain excluded from scheduled testing. Zero-cost fixture and
free-unlimited suites retain the established hourly cadence. Finite-cost
live/canary suites run at their declared risk cadence (A=6h, B=24h, C=72h),
with conservative daily/72h quota floors." So the rule this row states is the
floor, not the whole current schedule.

**The "tiered audit trail (basic on capabilities, full on *-Assurance
products)" this row describes was not built in that shape.** A search of
`apps/api/src/routes/audit.ts` for "tier," "basic," or "Assurance" returns no
matches. What exists instead is a per-capability GDPR Art. 22 classification
(`data_lookup` | `screening_signal` | `risk_synthesis`) assigned in the
audit body (`art_22_classification` field, with `case "risk_synthesis"` and
`case "screening_signal"` branches), which tiers by classification of the
individual capability's output, not by a `*-Assurance`-product-line split.
This is consistent with `DEC-20260812-A` (existing record), which retired
the Counterparty Assurance framing (the very product-line boundary this
row's tiering rule depended on) as primary product, so a tiering scheme
keyed to "*-Assurance products" had no stable product line left to key off
of by the time it might have been built.

**A later code comment independently confirms this decision's effect on a
different subsystem.** `test-scheduler.ts` contains the comment "Daily SQS
snapshot retired with the SQS engine (DEC-20260503-B)," directly at the point
in the scheduler where a daily snapshot job used to run, corroborating the
schema evidence above from a second, independent file.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null). PR2
(dropping the residual schema columns and `sqs_daily_snapshot` table,
renaming `capability_health` to `source_health`) is the outstanding follow-up
work CLAUDE.md itself names; completing it would close the gap between this
row's stated redesign and the engine's actual current (deleted, not
redesigned) state.
