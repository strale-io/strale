## Decision

Add a rule to the correctness test tier: if a capability's known_answer or
schema_check test returns a response where more than 50% of its declared
output fields are null or empty, the test fails instead of passes. The rule
applies only to capabilities with 3 or more declared output fields. Fields
marked optional in the output schema do not count toward the ratio. Nested
objects count as one field; recursive null-checking is out of scope for v1.
The rule changes only the pass/fail criteria of the existence-tier
correctness check; it does not touch grade thresholds, matrix values, or
factor weights.

## Context

The row's own Rationale gives the trigger directly: "The german-company-data
scraper returned all nulls for Robert Bosch GmbH on first customer contact
(SpendLatch evaluation 2026-04-09). The existing Tier C correctness test
('response has expected top-level structure, no error flags') passed because
nulls match the schema structurally. The test was too weak for the actual
failure mode — a capability returning mostly nulls is not working correctly,
even if the envelope is valid." The row also states this is "Phase 3
hardening for the german-company-data null-return class of bug identified
during the SpendLatch incident," following Gate 1 (solution input mapping
validator) and Gate 3 (schema coherence validator), with Gate 4 (solution
smoke tests) "still pending a separate DEC" at the time of writing; that
separate DEC is `DEC-20260409-D`, decided the same day.

## Rationale

Below 50% nulls typically indicates partial data (some fields genuinely
optional for that query); above 50% typically indicates upstream failure or
extraction breakdown. The row states the 50% threshold is "a reasonable first
cut; can be tuned with data," and that capabilities currently passing
correctness on mostly-null outputs would drop in score as an expected and
correct consequence, not a regression to work around.

## Consequences

Status verified on 2026-09-05, against `main`.

**The null-ratio rule shipped and survives, under a feature flag.**
`apps/api/src/lib/null-field-ratio.ts` implements exactly the rule this row
describes: its header comment reads "Gate 2: Null-output correctness tier
(DEC-20260409-A)," and its rules list matches the row field for field: "Only
applies to schemas with 3+ declared fields," "If >50% of declared fields are
null/empty → fail," "Fields marked as 'rare' or 'common' in
outputFieldReliability are excluded," "Nested objects count as single fields
(no recursion in v1)." `apps/api/src/lib/test-runner.ts` calls
`calculateNullFieldRatio` at the point in `known_answer` and `schema_check`
test evaluation the comment labels "Gate 2: Null-ratio check
(DEC-20260409-A)."

**The rule is gated behind `NULL_RATIO_RULE_ENABLED`, which defaults to
disabled in code.** The check reads: `const NULL_RATIO_RULE_ENABLED =
process.env.NULL_RATIO_RULE_ENABLED === "true"`, preceded by the comment
"Feature flag — defaults to disabled; enable with
NULL_RATIO_RULE_ENABLED=true." When the flag is off, a high-null-ratio result is logged
(`null-ratio-shadow-would-fail`) rather than failing the test, shadow mode,
not enforcement. `config/env-manifest.yaml` documents this exact variable
("Feature flag (DEC-20260409-A) enabling the null-output correctness tier in
test-runner.ts. Defaults to disabled.") and records it `required_in:
production` and `set_in: railway`, so per the manifest the flag is expected
to be turned on in the deployed environment, though the repository cannot
independently confirm the live value of a Railway environment variable.

**The SQS scoring context this rule was built for has since been deleted.**
CLAUDE.md states: "SQS scoring engine deleted per DEC-20260503-B (PR1 shipped
2026-05-05)." The correctness check itself is a test-pass/fail gate inside
`test-runner.ts`, independent of the SQS score computation, so it continues
to function as a test gate even though the scoring system it was originally
framed as protecting (the QP correctness factor named in the row's own
"SCOPE" section) no longer exists.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null). The
50% threshold is explicitly provisional in the row's own text ("can be tuned
with data"); a change to that threshold, or a decision to remove the feature
flag and enforce the rule unconditionally, would be the natural reversal or
amendment path.
