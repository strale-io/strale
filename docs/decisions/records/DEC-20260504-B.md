## Decision

Treat the first successful run after repairing a long-silent bulk operation as
a workload-resumption event, not as a routine execution. This applies to
retention, archival, reconciliation, batch processing, periodic cleanup, and
other operations that can release accumulated work after being broken or
unscheduled for more than twenty-four hours.

Before merge, query the affected data and document an estimate of accumulated
rows and bytes plus material downstream effects such as WAL volume,
replication lag, disk and memory pressure, connection-pool occupancy, and
upstream rate-limit consumption. Choose one deploy strategy explicitly:

- drain the backlog under operator supervision before deploying the recurring
  fix; or
- make the recurring fix self-throttling through bounded batches, pagination,
  time budgets, or equivalent per-tick limits.

Do not deploy the unbounded fix and assume infrastructure will absorb the
backlog. Do not call the repair deployed until the first successful run has
been observed and its rows processed, duration, and peak resource impact have
been reported. If the workload audit or first-run proof is missing, report the
gap rather than marking the work complete.

## Context

On 2026-05-04, a date-binding defect had made the retention operation fail
silently. After PR #44 repaired the defect, the first successful scheduled run
coincided with a Postgres disk-full crash loop and roughly twenty-eight minutes
of downtime. The follow-up implementation bounded retention work per batch and
time budget.

The incident Journal corrected its early backlog estimate to 937 rows measured
after recovery and left the exact disk-fill sub-cause partly uncertain. The
decision therefore rests on the demonstrated workload-resumption risk and the
danger of unbounded first runs, not on the original row estimate or a claim
that one unproven mechanism alone caused the crash.

## Rationale

Infrastructure operating normally during a silent failure is sized for the
failure state, not necessarily for all work that should have occurred during
that period. Fixing the code can abruptly release accumulated database writes,
network calls, or file work. Correctness review of the repaired loop does not
measure that operational burst. A pre-merge workload estimate and an explicit
drain or throttle strategy convert the burst into a bounded, observable
deployment.

## Consequences

Every triggered change must include the accumulated-workload estimate and its
chosen deploy strategy in the pull request or equivalent durable evidence. Its
session closeout must include the observed first-run outcome, or clearly state
that production verification remains incomplete.

This protocol can apply at the same time as `DEC-20260504-C`: one governs the
volume released when work resumes, while the other proves that the deploy
mechanism actually reaches the new path and produces the expected production
effect. It does not relax the capability-onboarding, distribution-integrity,
or audit-follow-up test protocols. The source also recorded the then-current
scoring-integrity boundary; the later retirement of that scoring implementation
does not weaken this deploy-safety rule or create a live dependency on it.

## Reversal conditions

Supersede or amend this decision only if a stronger, structurally enforced
deployment mechanism proves that accumulated work is automatically measured,
bounded, observed, and failed closed for every affected operation. A revised
incident analysis may correct historical causation without removing the
general workload-resumption control. Any change must be represented by a new
decision rather than editing this protected record in place.
