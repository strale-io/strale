## Decision

Switch the test scheduler from a per-capability hash-stagger to a per-suite
hash-stagger, globally (PR #108), to fix a rate-limit incident on
`slovak-company-data`.

## Context

The row's own Rationale states the diagnosis and the fix: "Phase 1 Contain
for SK rate-limit issue. Root cause: scheduler firing all 5 test suites
simultaneously on the :41 tick for slovak-company-data saturated Zenedge
CDN's sliding-window throttle (materially tighter than the documented 60
req/min on api.statistics.sk). PR #108 (commit cbb59a5) switched the
scheduler from per-capability hash-stagger to per-suite hash-stagger
globally: each capability's 5 suites now distribute across the hour, peak
load drops from 5 calls/sec to <=1 call/min per capability. SK breaker
auto-recovered same day at 10:41Z; /v1/do probe at 11:01Z returned populated
SEXES spol. s r. o. data." No other Decision ID is named in the row's own
text, so no relation edge is recorded (PR #108 is a pull request reference,
not a Decision ID; prose only).

## Rationale

As the row states it: the prior "structural rate limit Strale can't engineer
around" diagnosis was wrong in shape; it was Strale's own simultaneous
5-suites-per-tick burst pattern, not a hard vendor cap, so switching the
stagger key from `slug` alone to `slug:test_type` spreads the same
capability's suites across the hour instead of firing them all in the same
minute.

## Consequences

Status verified on 2026-09-05, against `main`.

**The per-suite hash-stagger this row describes is live in
`test-scheduler.ts`, exactly as stated, but the code's own comments cite a
different Decision ID for it than this row's own historical ID.** The
`slugStaggerMinute` function's header states: "Two-arg form:
`slugStaggerMinute(slug, testType)` — hashes `slug:testType`, which is the
per-suite stagger used by the scheduler post-DEC-20260513-D (per-suite
spread). Each of a capability's 5 active suites lands on a different
minute, preventing the simultaneous-burst pattern that saturated Zenedge for
`slovak-company-data` at the :41 tick." The `findOverdueSuites` query
comment repeats the same citation: "Per DEC-20260503-B + DEC-20260513-D
(per-suite spread)." Both code comments name `DEC-20260513-D`, but the
Notion source row for "SK slovak-company-data scheduler-spread — per-suite
hash-stagger globally (PR #108)" is this row, `DEC-20260513-C`; `DEC-20260513-D`
is a distinct row in this same batch, "Acknowledge DK danish-company-data
auto-recovery; supersede DEC-20260506-D manual pin," about a different
country and a different fix (an auto-recovered breaker, not a scheduler
change). This record states the discrepancy exactly as found (two files, two
citation sites, one wrong ID) without asserting a cause; it may be a
transcription slip in the code comments, or the two DECs may have been
renumbered at some point after the comments were written. Functionally, the
per-suite stagger mechanism itself matches this row's description in full:
the SQL predicate is `abs(hashtext(c.slug || ':' || ts.test_type)) % 60 =
EXTRACT(MINUTE FROM NOW())::int`, and the query comment states the same
motivating incident this row names: "burst-saturated Zenedge-fronted
upstreams (`slovak-company-data` / `api.statistics.sk` at the :41 tick).
Spreading by (slug, test_type) keeps any single upstream's egress to <=1
req/minute under steady state."

**A second, related bug the row does not mention is fixed in the same
function, per its own doc comment: duplicate suites sharing (slug,
testType) previously multiplied executions.** `findOverdueSuites`'s comment
states: "Before this, two suites sharing (slug, testType) — e.g.
danish-company-data's 4 duplicate known_answer suites — produced 4
identical (slug, testType) rows here, and each of the 4 loop iterations in
pollCycle() called runTests({capabilitySlug, testType}) *without* a suite
id, which reloaded and re-ran ALL 4 suites every time: a batch of N due
suites did N x N executions, not N." This is a separate finding
(cross-referencing `danish-company-data`, the subject of `DEC-20260513-D` in
this same batch) not stated on this row; it is reported here as evidence
found while verifying this row's claim, not as part of this row's own
Decision or Rationale text.

**The manifest for `slovak-company-data` documents the same rate limit this
row names, as a limitation.** `manifests/slovak-company-data.yaml` states:
"The Slovak RPO API limits anonymous traffic to 60 requests per minute per
IP. Sustained higher throughput requires..." consistent with the row's own
"documented 60 req/min on api.statistics.sk."
