## Decision

Lock the `ubo_availability` flag's semantic as capability state (does
Strale return UBO data today for this country) rather than jurisdictional
accessibility (does the country have a public UBO register). Keep the
3-value enum (`available` / `restricted` / `unavailable_no_registry`);
force the `reason` string to convey any jurisdictional nuance.

Practical effect: DK flips from `available` to `unavailable_no_registry`
(BODS integration `Status=Committed`); UK stays `available` (PSC
integration `Status=Live`).

## Context

PR #131 ("/go Pass B M-2") flagged that the `ubo_availability` flag was
being set per jurisdictional accessibility rather than capability state.
A customer reading the flag will reasonably expect a boolean answer to the
second question ("does Strale return this today"), not the first. Setting
it on jurisdictional grounds and surfacing capability state only via the
`reason` field leaks two-level complexity into a flag meant to be
directly actionable.

The historical Notion scope field on this row was `global`. It is recorded
here as `scope: technical` under this repository's decision-record
vocabulary: this decision fixes a field's semantics in the output
contract, not a product-scope choice.

The row's `Source` property is empty in the archive; PR #131 is named in
the Rationale text as the origin of the finding, and is cited above as
prose provenance (it is a Git pull request, not a formal decision record).

## Rationale

Silence or a jurisdiction-keyed answer on UBO availability is unacceptable
under the Evidence Tier framework (DEC-20260518-A), which requires the
`ubo_availability` flag to always be returned. Locking the semantic to
capability state keeps the flag directly actionable by a customer deciding
whether to trust the call's ownership data, while the `reason` string
carries the "why" (jurisdiction has no register vs. Strale has not built
the integration yet) without collapsing it into the flag itself.

## Consequences

Status on 2026-09-04, verified against `main`.

**The exact per-country outcomes this row specifies are implemented as
stated.** `apps/api/src/capabilities/danish-company-data.ts` sets
`o.ubo_availability = "unavailable_no_registry"` with
`o.ubo_availability_reason = "Danish beneficial ownership data integration
in progress; coverage in v1.1."` — matching this row's "DK flips ... to
`unavailable_no_registry`" outcome.
`apps/api/src/capabilities/uk-company-data.ts` sets
`o.ubo_availability = "available"` with `o.ubo_availability_reason =
"Beneficial ownership data available via UK PSC register."` — matching
this row's "UK stays `available`" outcome.

**PR #131 is confirmed merged 2026-05-18** as "feat(evidence-tier):
labeling sweep across 31 company-data handlers," the same day as this
decision and consistent with the row's account of a labeling sweep across
company-data handlers.

**The capability-state semantic is applied broadly, not only to DK/UK.**
`ubo_availability` and `ubo_availability_reason` appear together across
roughly thirty company-data executors, each pairing the flag with a
human-readable reason string, consistent with this row's rule that the
reason string carries jurisdictional nuance rather than the flag value
itself.

**DEC-20260812-A retired the Counterparty Assurance framing this field
serves, but the field semantics themselves are unaffected** — they are a
property of the company-data executors' output contract, which continues
to run in production independent of the retired product framing.

## Reversal conditions

Reconsider this decision if customer feedback shows the capability-state
semantic is less useful than a jurisdiction-keyed one, or if a future
product redesign of the ownership-disclosure output contract supersedes
the 3-value enum entirely. Represent a change of this decision through a
new decision rather than editing this protected record in place.
