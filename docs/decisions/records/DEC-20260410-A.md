## Decision

Two features, shipped silently (not announced on the pricing page). Progressive
unlock: after a successful free-tier call, 3 related capabilities become
temporarily free for the same caller. Agent self-signup: `POST /v1/signup`
returns an API key plus €2 in trial credit instantly, with no human
intervention.

## Context

The row's own Rationale explains the motivating data and the design logic:
"url-to-markdown is 45% of external traffic but almost no users try a second
capability. The barrier is signup friction, not awareness. Progressive
unlock removes friction for the second capability. Agent self-signup removes
friction for moving beyond free-tier. Both meet the agent where it already
is — in the API response — rather than requiring a human to visit a
webpage. Silent deployment avoids setting public expectations before
validating the conversion path."

## Rationale

The row frames both features as addressing the same underlying problem
(signup friction) at two different points in the funnel: trying a second
free capability, and moving past the free tier entirely, and frames silence
as deliberate: an unannounced experiment, not a committed public feature,
until the conversion path is validated.

## Consequences

Status verified on 2026-09-05, against `main`.

**Both features shipped and are live, matching the row's mechanics
precisely.** `apps/api/src/lib/progressive-unlock.ts` implements a
`UNLOCK_MAP` mapping five free-tier trigger capabilities
(`url-to-markdown`, `email-validate`, `dns-lookup`, `iban-validate`,
`json-repair`) to exactly 3 related capabilities each, with a 24-hour TTL
matching the row's "3 related capabilities per use" and the response message
`do.ts` sends: "These capabilities are free for you for 24 hours — no signup
needed." `apps/api/src/routes/do.ts` wires the check in directly. A header
comment reads "Check progressive unlock before rejecting (DEC-20260410-A)"
and a second reads "Progressive unlock: record + include in response
(DEC-20260410-A)", both citing this decision by id.

**Agent self-signup is live at the exact endpoint the row names.**
`apps/api/src/routes/auth.ts` defines `agentSignupHandler` under the header
comment "Agent self-signup (DEC-20260410-A)" and "POST /v1/signup —
autonomous agent signup. Returns API key + €2 instantly. Mounted at
/v1/signup in app.ts (not under /v1/auth)." The handler validates only an
email address, runs the same trial-eligibility authority as
`/v1/auth/register` (disposable-domain and MX checks, per the handler's own
WP11 comment), and requires at least one prior successful free-tier call from
the same IP before granting the signup, a friction-reducing but not
frictionless gate that the row's own text does not describe in this much
detail, so this is the implementation's own refinement rather than a
deviation from the decision.

**"Silent" (not on the pricing page) has not been independently verified
against the live pricing page** in this repository-only research pass; the
pricing page lives in `apps/web` / the frontend surface, outside this
batch's file-only evidence scope, so this record does not claim to confirm
or contradict that half of the row.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null). A
decision to publicize either feature on the pricing page, or to change the
unlock map's related-capability counts, would be the natural amendment path.
