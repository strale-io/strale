## Decision

Security architecture: provider-hosted execution is confirmed as the
permanent model, not just an MVP shortcut.

## Context

The row's title carries the whole decision; its Rationale supplies the
substance. The Provider Growth document had positioned provider-hosted
execution as an "MVP approach," with container or WASM sandboxing named
as future options. This row decides instead that provider-hosted
execution is the permanent architecture: Strale is a router, not a
compute platform. The stated reasoning: this minimizes security surface
area, eliminates hosting costs for provider code, and aligns with the MCP
model, where tools run in the provider's own environment.

The historical Notion scope field on this row was `global` in the
workspace's old vocabulary. It is recorded here as `scope: technical`:
this is an execution-architecture decision, not a company-wide strategic
or positioning decision.

## Rationale

The rationale, as the row states it: provider-hosted execution is chosen
over building sandboxed compute (containers or WASM) because it minimizes
Strale's own security surface, avoids hosting costs for third-party code,
and matches how MCP already expects tools to run, in the tool provider's
environment rather than the router's.

## Consequences

Status verified on 2026-09-05, against `main`.

**Every executor that exists today runs inside `apps/api`, and no
third-party or externally-hosted execution path was found.**
`apps/api/src/capabilities/auto-register.ts` is the manifest-driven
registration mechanism: for each `manifests/<slug>.yaml`, it dynamic-imports
`./<slug>.js` from the same package so the executor self-registers via
`registerCapability(slug, handler)`. Every one of the 342 manifests on
`main` (`ls manifests/*.yaml | wc -l`, dated 2026-09-05) resolves to a
first-party file under `apps/api/src/capabilities/`; this verification
found no mechanism by which a third party's own hosted code executes in
response to a Strale request. In that narrow sense, execution is
first-party-hosted, not provider-hosted in the row's original meaning of
"the capability's own provider runs the code."

**No third-party provider was ever onboarded to exercise this
architecture in the sense the row anticipated.** `DEC-20260225-P-g9h0`'s
Consequences establish that no external contractor or provider has ever
been given a capability to run; this row's "provider-hosted execution"
premise assumes an ecosystem of external providers each hosting their own
capability code, which this verification did not find evidence ever
existed. The row's stated goal (minimize security surface, avoid hosting
third-party code) has held by default, because no third-party code has
ever needed hosting, not because the sandboxing-versus-provider-hosting
architectural question was tested against a real external provider.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null in
the source). Untested by an actual third-party provider onboarding; a
future decision to onboard one would be the first real test of whether
"provider-hosted" (in the row's sense) or a sandboxed-compute model is
actually built, and would supersede or confirm this row depending on what
gets built.
