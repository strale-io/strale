## Decision

Post-MVP distribution: build a LangChain `StraleFallbackTool` as the
first post-validation feature. A single tool that drops into an existing
agent's tool array and activates on failure, intended as the primary
distribution mechanism.

## Context

The row's stated basis, from the row's own Rationale: all three external
LLMs consulted independently converged on framework integration as the
highest-leverage distribution channel, on the premise that developers
will not rewrite code to use a Strale SDK directly, but will add one tool
to an agent they already have. Target: week 5-6, immediately after MVP
validation, per the row.

The historical Notion scope field on this row was `global` in the
workspace's old vocabulary. It is recorded here as `scope: product`: this
is a distribution-channel choice, not a single technical integration
detail.

## Rationale

The rationale, as the row states it: three independent LLM consultations
converged on framework integration (adding one tool to an existing agent)
as higher-leverage than asking developers to adopt a standalone SDK,
because it removes the rewrite cost that would otherwise gate adoption.

## Consequences

Status verified on 2026-09-04, against `main`.

**A tool named exactly `StraleFallbackTool` exists on `main`, in the
TypeScript package, not under a plain `packages/langchain-strale/` name.**
`packages/langchain/src/index.ts` exports `export class StraleFallbackTool
extends Tool`, whose description reads: "Use this tool when you need
real-world data you can't access directly — company registries, invoice
parsing, VAT validation, web data extraction. Costs money per call.
Describe what you need in plain language." This matches this row's
"drops into existing agent tool arrays" description closely: the class
takes an API key and an optional `capabilitySlug`/`maxPrice`, and calls
`client.do(...)`. `packages/langchain/package.json` publishes it to npm
as `straleio-langchain`, not `langchain-strale`.

**`packages/langchain-strale/` is a separate, Python package, and does
not contain a fallback tool by this or any other name.** It publishes to
PyPI as `langchain-strale` per its `pyproject.toml`, and its
`langchain_strale/tools.py` defines a generic `Fallback input for
capabilities without a specific JSON Schema` input model rather than a
`StraleFallbackTool`-equivalent single always-available tool; grepping
`packages/langchain-strale/` for "Fallback" returns only that input-schema
docstring, not a tool class. CLAUDE.md's Project Structure block lists
`packages/langchain-strale/` as the LangChain package (annotated
"PyPI published"), which is accurate for the Python package's existence
but does not surface that the TypeScript package under the plain
`packages/langchain/` directory, not the `-strale`-suffixed one, is the
one carrying this row's specific `StraleFallbackTool` design.

**The row's stated distribution premise, one tool that activates on
failure inside an existing agent's tool array, is realized in the
TypeScript tool's design** (`this.name = "strale_fallback"`, description
framed as a data-access fallback), so the feature this row specifies
appears to have shipped, under a different package name than the row's
plain "LangChain" framing might suggest to a reader relying on CLAUDE.md
alone.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null in
the source). A future decision to rename, merge, or retire either
LangChain package would need to account for which one carries this row's
`StraleFallbackTool` design, and would supersede this row rather than
amend it in place.
