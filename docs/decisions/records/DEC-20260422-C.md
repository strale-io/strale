## Decision

Treat production capabilities with missing onboarding fields as evidence of a
structural pipeline-coverage question, not as a data-cleanup problem. Audit
every capability creation path, map affected slugs to those paths, and
determine whether generated fallback manifests must be replaced with values
derived from real execution.

The initial working hypothesis was that pre-rule capabilities or an
`auto-register.ts` path could bypass `onboard.ts`. Confidence was medium and
the hypothesis required investigation before a permanent fix.

## Context

Seventeen capabilities were initially believed to have null fields that the
always-enforce onboarding rule should have populated. Generator fallbacks made
the manifests appear complete but did not explain whether every database write
path actually executed the full pipeline.

The subsequent audit showed the hypothesis was directionally correct but
specifically wrong. `auto-register.ts` loaded executors at runtime and was not
a database insertion path. The actual scope was thirty-four capabilities
across six cohorts.

## Rationale

Fallback data can conceal a missing control without closing it. Auditing the
creation graph before patching individual rows distinguishes incomplete legacy
data from an enforcement path that can continue producing drift.

## Consequences

The investigation was elevated into structural remediation instead of another
manifest backfill. It identified direct inserts, seed behavior, a post-insert
hook that did not populate the claimed fields, and a readiness check that had
been decorative for those dimensions.

`DEC-20260423-A` superseded this record with the corrected diagnosis, larger
scope, and staged implementation. The rejected `auto-register.ts` explanation
must remain historical context, not be repeated as current architecture.

## Reversal conditions

This record is already superseded. Reopen its hypothesis only if new evidence
shows runtime executor registration directly writes capability rows. The
general rule—investigate structural creation paths before accepting fallback
data as a fix—may be carried forward through a new decision without reviving
the disproved mechanism.
