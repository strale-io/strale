## Decision

Classify `guaranteed_field_missing:*` failure reasons as a `manifest_drift`
failure category that does not trip the circuit breaker, in
`categorizeFailureReason`.

## Context

The row's Rationale states: "PR #109's runtime sentinel began emitting guaranteed_field_missing:* failure_reasons. Without classification, 3 consecutive failures on any of 4 currently-affected capabilities would trip the circuit breaker within ~3 hours, generating false-degraded signal across AVS / source_health / Coverage Matrix / strale-beacon. PR #112 adds a manifest_drift FailureCategory and an early-return in circuit-breaker.recordFailure mirroring the existing isUserInputError skip pattern."

## Rationale

Per the row: "Semantic claim: manifest-drift is maintainer signal (record in test_results for triage) not customer-blocking signal (skip breaker trip). Binary distinction preserved: HTTP 5xx, exception, timeout, auth, format, scraping_broken still trip the breaker via unchanged paths." The row also
records a counter-argument it acknowledges rather than dismisses: "if a customer-critical field is declared guaranteed and the executor doesn't populate it, the capability IS partially-broken; pre-launch context softens this, and the deferred non_empty: true opt-in annotation is the right post-launch tool for capability-specific empty-as-failure semantics."

## Consequences

The row's own `Outcome` field states: "Shipped via PR #112 (commit 03ffac6, 2026-05-13T13:15Z). Post-deploy verified at 13:16:11Z: llm-output-validate produced failed test_result with guaranteed_field_missing:auto_fixed_output, capability_health row not created, breaker not incremented. 6/6 unit tests pass." ## Reversal conditions

Supersede this decision if the deferred `non_empty: true` opt-in annotation
this row names is implemented and changes the breaker-skip behaviour for
specific capabilities, or if `manifest_drift` classification is found to be
masking genuine customer-facing breakage rather than maintainer-only drift.
