## Decision

Create a quality/cost optimization spec for the Strale Quality Score
(SQS) identifying ten enhancements, in priority order: C1 health ping,
C2 cached correctness, Q1 test classification, Q5 input rotation, C3
adaptive frequency, Q4 score change detection, Q2 freshness decay, C4
piggyback traffic, C5 dependency graph, Q3 multi-run correctness. The
test suite audit (this batch's `DEC-20260305-F`) is named as a
prerequisite.

## Context

The row's stated basis, from its own Rationale: SQS is Strale's core
trust signal, so improving how cheaply and how well it can be computed
matters directly. Ten enhancements were identified and ordered by
priority, with the test suite audit as the prerequisite step before any
of them could be built reliably.

The historical Notion scope field on this row was `global`. It is
recorded here as `scope: technical`: it is a cost/quality engineering
spec for a specific scoring subsystem, not a company-wide strategic or
positioning decision.

## Rationale

The rationale, as the row states it: SQS being the platform's core trust
signal justifies investing in making its computation both cheaper (the
C-prefixed items: health ping, cached correctness, adaptive frequency,
piggyback traffic, dependency graph) and higher-quality (the Q-prefixed
items: test classification, input rotation, score change detection,
freshness decay, multi-run correctness).

## Consequences

Status verified on 2026-09-05, against `main`.

**None of the ten enhancements this spec identified apply today, because
the SQS engine itself was deleted.** CLAUDE.md states: "SQS scoring
engine deleted per DEC-20260503-B (PR1 shipped 2026-05-05)," naming the
dual-profile model, the `min_sqs` parameter, the platform floor gate, the
public `/v1/quality/:slug` endpoint, and the automatic lifecycle
transitions as all gone. A cost/quality optimization spec for a scoring
engine that no longer exists has no live target to optimize; none of the
ten items (health ping, cached correctness, test classification, input
rotation, adaptive frequency, score change detection, freshness decay,
piggyback traffic, dependency graph, multi-run correctness) was found
implemented as an SQS-specific mechanism in `apps/api/src`.

**Some individual mechanisms this spec named survive in a different
context, unconnected to SQS.** "Piggyback traffic" (C4) has a live
analogue: CLAUDE.md's "Test Infrastructure Cost Principles" section
documents piggyback test suites receiving data exclusively from real
customer traffic via `recordPiggybackResult()`, excluded from proactive
scheduling — the same underlying idea this spec named, but as a general
test-infrastructure mechanism, not an SQS cost-optimization feature. This
record does not claim a causal link between the two; it notes the
coincidence of naming only.

**This row's stated prerequisite, `DEC-20260305-F`'s test suite audit,
is itself a formal record in this same batch**; the source text here
does not name it or any other decision by ID (it only says "Prerequisite:
test suite audit" in prose), so per this batch's relation rule (edges
must be source-stated, quoting the sentence naming the target), no
`related_to` edge is created from this row to `DEC-20260305-F`, or to
`DEC-20260306-G` (the SQS design row), or to any record purporting to be
the "SQS Constitution" — the source text names none of them explicitly.
