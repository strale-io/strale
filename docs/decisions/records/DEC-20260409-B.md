## Decision

Two-part decision. Part 1, code-based lookup: all company data capabilities
accept both `company_name` and `registration_number` as inputs, preferring the
code when provided; company data capabilities return `registration_number`,
`jurisdiction`, and `registration_type` in their output; the solution
executor automatically propagates `registration_number` + `jurisdiction` from
step 0 into context for all downstream steps; downstream capabilities
(lei-lookup, vat-validate, beneficial-ownership-lookup, adverse-media-check)
query by code when available, falling back to name otherwise. Part 2,
cross-validation layer: every company data capability runs consistency checks
before returning: name match (fuzzy threshold 85%), code match, jurisdiction
match, address cross-check, and cross-step consistency, each producing a
hard fail, a warning, or a pass, surfaced in a `validation` output block. The
cross-step validation logic lives in the solution executor, not duplicated
per capability.

## Context

The row's own Rationale names two incidents as the trigger: "(1) Bosch LEI
lookup during SpendLatch evaluation returned 'Robert Bosch Krankenhaus GmbH'
(subsidiary) instead of parent, because GLEIF search grabbed the first name
match. (2) Lithuanian scraper in Gate 2 shadow audit returned wrong results
because 'Lietuva' fuzzy matches dozens of companies." The row states
"Registration numbers are unique within a jurisdiction and eliminate
disambiguation bugs entirely. Cross-validation catches entity drift across
steps before it reaches the customer." The row explicitly marks itself
related: "RELATED: DEC-20260409-A (Gate 2 null-output correctness tier). Both
are hardening measures from the SpendLatch Bug Fix Framework Phase 3 work."

## Rationale

The row's stated architectural choice is to put cross-step validation in the
solution executor rather than each capability, because "the executor already
owns step sequencing and $steps[N] resolution... Capabilities stay
standalone — they accept registration_number as optional input and prefer it
when provided. One implementation, one test surface, one place to audit."
The severity model (hard fail on code/jurisdiction mismatch or a name
mismatch when a code was provided; warning on fuzzy name match without a code
anchor or on cross-step drift) is designed so ambiguous name-only lookups
degrade to a flagged warning rather than a silent wrong answer.

## Consequences

Status verified on 2026-09-05, against `main`.

**Part 1, the solution-executor propagation of `registration_number` and
`jurisdiction`, shipped and is live.** `apps/api/src/lib/solution-executor.ts`
implements exactly this: a comment reading "Context propagation: after first
group, extract registration_number + jurisdiction... without explicit
$steps[0].registration_number mappings in every solution definition," and
code that
reads `regNum = (step0 as Record<string, unknown>).registration_number` and
assigns it into `entityContext.registration_number` for downstream steps.
`apps/api/src/lib/onboarding-gates.ts` also treats `registration_number`,
`jurisdiction`, and `entity_name` as an `AUTO_INJECTED` set recognised by the
onboarding path-coverage gates.

**Part 2, the cross-validation layer, was built as a standalone module but
has zero capability callers.** `apps/api/src/lib/entity-validation.ts`
implements every function the row describes: `validateNameMatch`,
`validateCodeMatch`, `validateJurisdiction`, `validateAddressConsistency`,
`buildValidationBlock`, `validateCompanyResult`, and its header comment
labels itself "DEC-20260409-B Phase 1." But a search of every file in
`apps/api/src/capabilities/` for `validateCompanyResult`,
`buildValidationBlock`, or an import of `entity-validation` returns no
matches; the module's only consumer in the entire repository is its own test
file (`entity-validation.test.ts`). The `validation` output block the row
specifies is exported and unit-tested but never attached to any company data
capability's actual response.

**Net effect:** the context-propagation half of this decision is live and
wired into the solution executor; the cross-validation half is dead code,
implemented, tested in isolation, and never called from a capability. The
Bosch-class disambiguation bug the row cites as its trigger would today be
caught only by whichever capability already had its own ad hoc logic, not by
this module.

## Reversal conditions

None recorded on the row (`Superseded By` and `Outcome` are both null). Wiring
`entity-validation.ts`'s exported functions into the company data
capabilities that currently propagate `registration_number` but do not call
it would complete Part 2 without requiring a new decision.
