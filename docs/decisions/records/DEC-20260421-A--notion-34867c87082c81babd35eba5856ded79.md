## Decision

Split Cluster 2 Phase 3 (originally a single ~380-500 LOC commit) into two:
**C1** ships transactional `persistCapability`, hook wiring,
`processes_personal_data` fix, and DB-row-shaped call-site migration
(commit `8f6eff9`, +483/-44 across 4 files); **C2** ships hook relocation
(inside-tx to outside-tx per design doc §4.3), a Manifest-to-DB-row
normalizer, and migration of `seed.ts`, `capability-onboarding.ts`, and
`onboard.ts` backfill `UPDATE`s.

## Context

The row's own stated reasons for splitting: C1 and C2 have "different risk
profiles" (C1 adds new code at unchanged call sites; C2 rewrites existing
entry paths with shape normalization); C1 is "independently valuable if C2
slipped"; rollback granularity is finer; and C2 "deserved its own audit
because camelCase/snake_case divergence is runtime-bite territory, not
compile-time." The row states the design doc "(DEC-20260420-M)" frames
Phase 3 as a phase, "not a commit count": the split is an implementation
choice inside that phase. `DEC-20260420-M` has no record or
collision-registry entry in this repository at the time of this batch; it
is not targetable and is recorded here as prose only.

The row's own text names no other Decision ID and is not itself named by
id in its sibling row under this collision (the Payee Assurance input-spec
row); no relation edge is recorded between the two.

This historical ID is reused by a second, unrelated Notion row (the Payee
Assurance single-field input-spec decision, a product decision made the
next day) and was an unresolved registry collision until this batch; the
two rows are resolved together in
`archive/sessions/2026-09-05-decision-collision-resolution-DEC-20260421-A.md`

## Rationale

The rationale, as the row states it: same reasoning pattern as the earlier
C1/C2 split precedent it names for itself: independent value, finer
rollback granularity, differing risk profiles between adding new code and
rewriting existing entry paths.
