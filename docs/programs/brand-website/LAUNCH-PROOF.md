# Launch proof boundaries

Working evidence map, 5 September 2026. This is an authoring constraint for the next design batch, not a new public claims register. [claims.yaml](../../company/claims.yaml) retains that authority. Sources were inspected at repository baseline `4e66a410`; the earlier production observation remains dated in [discovery research](../../research/2026-09-05-brand-foundation-discovery.md). No new paid calls or customer records were queried for this batch.

| Message | Evidence and scope | Treatment in first applications |
| --- | --- | --- |
| Agents can search, extract and validate | Tool implementations/manifests describe these functions. Availability, access eligibility and pricing are dynamic. | Use an explicitly illustrative document-to-fields example. Revalidate its chosen tool against live facts before final copy or an executable demo. |
| Shared access reduces provider integration work | Shared Strale routes dispatch different tools; each tool still has its own input/output schema. | State the access mechanism; make no measured hours-saved claim and no universal-schema promise. |
| Source context helps explain a result | `/v1/do` builds provenance into its audit record. Fresh x402 tool success includes response provenance; solution and cached paths need separate treatment. | Keep source-context claims out of the initial extraction illustration. A customer-visible proof specimen follows route-specific verification. |
| Customers can inspect Strale execution | Existing audit/transaction interfaces and internally created newer receipts are different surfaces. Internal receipt creation does not establish public retrieval. | Do not draw a fictional receipt dashboard or claim complete agent observability. |
| Tests establish particular behaviours | `test-runner.ts` supports definition, fixture, known-answer, negative and canary paths. `piggyback-monitor.ts` checks required top-level values on its callers. | No generic reliability badge, score or testing counter in the hero. A methodology page must say what was checked, when and by which mode. |
| Pay per use / success | Charge outcome, valid output and factual correctness are distinct. Eligibility varies by access route. | Leave detailed commercial claims to the pricing/access proof batch. Do not invent sample prices. |

## Bounded proof work still required

Reconcile the illustration with that exact contract before it becomes an executable demo. The present invoice is a conceptual fixture, not a captured API response.
2. Trace customer access to source/execution information for fresh account calls, fresh x402 tool calls, x402 solutions and cached/replayed responses. Mark unavailable paths unavailable; do not infer parity from a shared internal type.
3. Specify only the minimum retrieval/parity fix needed for an intended launch claim, or omit the claim. Implementation needs the applicable money/audit protocols and its own bounded batch.
4. Add proposed outward claims to the existing register with evidence and obtain their existing approval; do not equate approval of the positioning with approval of every sentence.
