## Outcome

A website that communicates the product's actual value and enables relevant buyers to begin using it, supported by a coherent brand kit that people and agents can apply across channels. Commercial success is measured against [GOALS](../../company/GOALS.md), including payer diversity and repeat use, not just traffic, signups, or visual approval.

Initial release scope: the public website and essential developer conversion/discovery paths; a brand reference site and versioned machine-readable package; and a starter set for social, blog, email, PDF and product video. “Comprehensive” means each needed category has an explicit rule and extension path. It does not mean producing every imaginable asset before the website can launch.

## Editorial and density rules to prototype

These are proposed acceptance rules for T4/T5, not silently active tokens:

- Each marketing section answers one reader question, carries one dominant idea and has one principal visual. Its title should communicate something without requiring a subtitle.
- Body copy is optional where the visual and title already explain the point. A subtitle is not a mandatory component slot. Delete repetition before adding space or reducing font size.
- Technical schemas, test taxonomies and exhaustive feature detail have a deliberate detail-page destination. The homepage contains enough evidence to make the benefit believable.
- A CTA states the next action. Each section has at most one primary action; competing primary actions require an explicit purpose.
- Define different content budgets for hero, benefit, catalogue card, documentation, social and PDF. Calibrate word/line limits against approved real examples, mobile reflow and localised text. Never treat a universal words-per-screen limit as a measure of comprehension.
- Review rhythm across the whole page: alternate expressive, demonstrative, comparative and concise moments where the narrative warrants them. A succession of differently coloured card grids is not sufficient variation.

A section brief records audience question, message, evidence source, visible content, visual action, deeper destination, density class and acceptance screenshot. These are authoring records, not content shown to website visitors.

## Art-direction process

1. Assemble current logo/atmosphere/type assets and known versions into a comparison sheet, including light/dark variants, actual use sizes and crops. Record keep/refine/retire/unknown; the inventory is not approval.
2. Use references for particular principles such as typography, pacing or photographic treatment. Name what each reference may influence. Strale's adopted identity controls the result.
3. Compare preserved Quiet Material with a refined composition using identical real copy: homepage opening, a contrasting benefit/proof section, a social post and a PDF cover plus interior example. Use the rendered review to address repetition and competing hierarchy. Explore a further identity direction only if this comparison exposes a reason; a direction must work beyond one attractive hero.
4. Critique clarity, hierarchy, distinctiveness, cohesion, accessibility and production feasibility separately. Machine checks can verify constraints; a model score does not choose the founder's aesthetic preference.
5. Select one direction, freeze its anchor applications, and derive the initial component/asset library. Review assets both individually and in the assembled page. Supporting parts must remain subordinate where the composition needs them.

Every meaningful exported asset gets a brief, source master, approved variants, usage metadata and contextual acceptance. This is not a mandate to catalogue every DOM element. Add a missing asset deliberately to the shared library, then consume it; do not improvise a private copy inside one page.

## Human and machine source architecture

Retain existing authorities: `design/tokens/active.json` owns adopted runtime values by surface; `docs/company/claims.yaml` owns public claim rulings; `design/PROVENANCE.md` owns design lineage. Extend them rather than create competing copies inside brandkit-lab exports.

Proposed T5 additions, to specify after direction selection:

- `design/brand/` for versioned brand-rule records with stable IDs and explanatory Markdown. Structured fields reference token/claim/asset IDs; narrative supplies rationale and good/bad examples.
- `design/assets/` for an asset manifest and editable masters, with large binaries in the established release-asset store where appropriate.
- Shared components/templates consumed by `apps/web` and other supported renderers.
- Generated human guideline pages, CSS/type exports, design-tool variables, channel templates and a small task-routing skill. Each includes the source version; generated outputs are not edited as separate authorities.

Extend enforcement to actual website and channel consumers: imported tokens/components, allowed asset IDs and icon/font families, required claim evidence, stale generated output detection, accessibility, rendered content/overflow checks and image/video budgets. Pair deterministic checks with review of representative full compositions. A linter can refuse an off-token colour; it cannot certify that the result is beautiful or persuasive.

Brandkit-lab can supply schemas, provenance distinctions, lint generation and selected production adapters. Its input `basis` fields must preserve evidence versus founder choice versus inference. Do not import its full operating model, assume every experimental logo route is validated, or allow a generator to overwrite an adopted brand decision.

## Video and channel policy to test

Prototype one concise product story: a useful task, a tool call, a clear result and the inspection actually available to a customer. Consider a roughly 30–60 second click-to-play film plus shorter silent demonstrations. These are proposed formats, not fixed brand law. Provide captions, a meaningful poster, a static equivalent and reduced-motion behaviour. Keep demonstrations truthful and label illustrative fixtures. A video must earn its place through comprehension; it is not required merely because a reference site has one.

Use the same art direction and source masters across social, blog, email and PDF, with compositions adapted for each reading situation. A social post is not a shrunken homepage. Essential initial templates precede speculative future campaigns. First publication in a new channel and new external claims retain the founder gates in the charter.

## Canonical adoption and historical preservation

No existing design file is retired merely because this program exists. At adoption:

1. Inventory each current/candidate source with scope, owner, location/version, evidence and proposed disposition.
2. Record the approved replacement and supersession through the existing decision process; respect the pre-M4 Notion/repo boundary.
3. Update provenance and reciprocal pointers atomically with the new runtime source. Remove obsolete instructions from active entry points only after the replacement is complete.
4. Preserve older masters and documents under versioned archive/tag/release paths, with their date, status and replacement link. Never delete Notion material or edit historical decisions/Journal content; use the permitted new correction/decision records.
5. Ensure repository orientation, the brand guide, design tools and build consumers all resolve one adopted version. Historical candidates remain findable but cannot load as defaults.

DEC-20260902-A already places the new website in `apps/web`. The sibling frontend and its open work remain preserved references; this program does not reopen that architecture choice. Domain choice/redirects must be reconciled explicitly with the existing decision set before cutover.

## Completion and learning

Website acceptance must cover a visitor identifying the offered work, choosing a relevant tool/use case, understanding price/access, and reaching a successful first execution through supported paths. Machine discovery and schema/pricing/error surfaces must agree with the human site. Do not infer agent conversion from monitors or daily-rotating visit identifiers.

Measure first successful paid use, later-day repeat, revenue outside the largest payer and instrumented acquisition routes. Small-sample comprehension tests and one acquisition hypothesis are more useful initially than a large multivariate website test. No promise is made that a redesign alone will produce the revenue target.

Every batch ends with a precise `next_action`, evidence receipt, reviewed change and clean pushed work. Future sessions should be able to continue from this program without the original conversation.
