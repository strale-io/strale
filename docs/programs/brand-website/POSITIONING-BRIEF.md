# Strale positioning and creative brief

**The proposed promise: give your agents useful external tools without building each provider integration yourself.**

This is the working brief for the redesign, prepared following the founder's instruction to proceed. It makes the recommendation concrete for review; it does not adopt new public claims or replace existing strategy, voice rules or design tokens. [PROGRAM.md](PROGRAM.md) is the continuation entry point. The [discovery research](../../research/2026-09-05-brand-foundation-discovery.md) and [rendered redesign review](../../../archive/sessions/2026-09-05-quiet-material-review.md) supply the evidence and its limits.

## Positioning

The working category is **tools and data for AI agents**. Address developers and technical founders giving agents recurring research, extraction and validation work. Show the work they can accomplish first, then why using Strale makes it easier to add and operate those functions.

This audience is a commercial hypothesis supported by repeated, varied tool use. We do not know the largest customer's business, buying motivation or opinion of the audit features. Do not turn observed use into a fictional customer persona, quotation or case study.

Strale provides access to useful external functions through shared interfaces and commercial arrangements. The developer still owns the agent and its workflow. “One connection” explains a mechanism; it should support the value proposition rather than carry the entire positioning.

Keep the broad library strategy and the existing priority of x402 as a transaction route. A human developer should also be able to understand the offer and find the right access instructions. Leading with enterprise production readiness would outrun the customer evidence and the current availability of inspection features. Production concerns deserve credible supporting proof, with scope stated accurately.

## Benefit hierarchy and proof

| Reader benefit | What to demonstrate | Boundary |
| --- | --- | --- |
| Give an agent useful new functions | A concrete task with a legible input and useful result: extracting document fields, finding web evidence or validating data. | Choose examples from currently available tools; illustrations are labelled fixtures. Avoid suggesting Strale performs the agent's reasoning. |
| Spend less work connecting providers | How the same Strale access route reaches different tools, with discoverable inputs and pricing. | Shared access does not mean identical tool schemas or identical features on every route. This is a benefit hypothesis, not a measured time-saving claim. |
| Understand the work Strale performed | The execution information or source context a customer can actually retrieve on the demonstrated route. | Distinguish execution records, provenance and internal receipts. Do not promise a complete agent trace, verified upstream truth or universal receipt retrieval. |

Testing is supporting evidence for particular behaviours, not a fourth abstract hero promise. Explain a useful check and what it establishes on a tool or methodology page. Fixtures, live checks and production monitoring have different coverage; none alone proves every returned answer correct. The next product-proof batch must verify route coverage and customer retrieval before stronger inspection claims enter launch copy.

## Homepage story

The opening should answer “What useful work can I give my agent?” with one short statement and one demonstration. This copy is a direction sample, not approved launch text:

> **Give your agents more useful tools.**
>
> Search the web, extract document data and validate inputs through one Strale connection.
>
> Explore tools · Read the docs

Use one example at a time. A request to validate multiple email addresses must show a corresponding set of results, or the request must become singular. Show an outcome a reader can recognise before adding source metadata or implementation details.

Continue with a small number of purposeful changes in pace:

1. **Useful work:** an open, focused input-to-result demonstration that adds meaning beyond the hero.
2. **Breadth:** a compact catalogue organised around reader tasks, with links to tools and use cases.
3. **Less integration work:** a concise explanation of shared access, with a deeper technical destination.
4. **Evidence and control:** customer-visible execution information, qualified to the actual route.
5. **Begin:** clear pricing/access guidance and the next step toward a first successful call.

This is a narrative sequence, not a requirement for five identical sections. Each section gets one reader question, one dominant message, one principal visual and a clear destination for detail. Subtitles and body paragraphs are optional. If the picture and title make the same point as a paragraph, remove the paragraph before decorating it.

## Creative direction

Use **Quiet Material as the control**, then refine it in real applications. The folded forms, light/dark atmosphere, restrained type and black actions provide a promising shared vocabulary. The rendered review does not justify discarding them. It also does not establish that the logo, font selection or entire image library is ready for adoption.

The main correction is composition. Four successive large rounded use-case panels create repetition even when their colours and content change. Framed cards, shadows, badges, icon strips and checkmarks compete for emphasis. Introduce open demonstrations, compact lists and occasional strong framed moments according to the story. Compare these changes against the preserved design using the same content.

Make the proposed character observable:

- **Clear:** headlines name useful work; technical detail has a deliberate destination.
- **Composed:** one element leads each composition; supporting elements have quieter treatment.
- **Practical:** demonstrations show usable results rather than decorative counts or feature inventories.
- **Accountable:** examples match their source, invented data is identified, and claims have evidence.

Atmosphere supplies identity and pacing. Product illustration explains a task. Interface components support navigation and action. Establish separate rules for these roles; do not make every illustration a dashboard card. Recompose mobile examples around their essential proof instead of stacking every desktop element.

## Prove the system before expanding it

The next design batch should produce a homepage opening, a contrasting benefit section, a social post and a PDF cover with one interior content example. Use the same promise and one real task across them. Review each at its intended size, plus representative light/dark and narrow layouts. The PDF interior tests reading and information hierarchy beyond an attractive cover.

From the selected examples, define typography roles, density budgets, grids, colour/surface roles, icons, illustration, motion and component states. Then create the missing masters and channel templates. A small, coherent initial library with an explicit extension process is more useful than speculative assets for every future campaign.

Use video only where sequence helps explain the product. First storyboard one request-to-result story with a static equivalent. A short film can follow after the story and visual language work; it is not a prerequisite for this brief or the website opening.

## Conversion and learning

The intended journey is: recognise a useful task, find a suitable tool, understand its input, output, price and access route, then complete a successful call. Keep agent discovery and payment instructions accurate alongside the human site. Do not force a sign-up flow into a route that does not need it.

Judge the redesign first by whether readers can explain the offer and reach that first call. Then measure repeat use and payer diversity against [GOALS](../../company/GOALS.md), with acquisition attribution only where instrumentation supports it. A redesign alone is not a revenue forecast.

## Adoption and continuation

The concrete strategic choice is whether the homepage leads with useful agent work, supported by shared access and scoped execution evidence, or retains shared access as its dominant promise. Both are defensible; the first better connects the breadth of the offer to an immediate reason to use it. Retaining the current emphasis would require less editorial change but would leave more of that value for visitors to infer. Doing nothing leaves the mismatch between product, copy and composition unresolved.

Recommend adopting the first hierarchy. On founder agreement, record the decision and reconcile terminology: this brief proposes **tools** for marketing, while [VOICE.md](../../company/VOICE.md) currently prescribes **data services** as the alternative to technical “capabilities.” Do not silently amend that authority or publish the sample copy. Keep technical identifiers where developers need them.

The adoption batch must update the relevant strategy/voice pointers, proposed claim rulings and design provenance together. Existing tokens, historical decisions and the preserved frontend remain unchanged until their replacements are explicitly adopted. Routine design work within the selected direction should then proceed without repeated approval of individual cards, icons or layout choices.
